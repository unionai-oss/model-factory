RightSize Bench

Before a task runs, someone has to decide how much memory and CPU to request for it. Ask for too little and the task is killed for running out of memory; ask for too much and the cluster pays for capacity nobody uses. This benchmark measures how well different kinds of models make that decision on real code, run for real.

21,323 measured task runs (v2: 14,234 · v1: 7,089) 12 families of task code, 2 never shown in training 10 approaches, plus a pooled combination 600 live validation pods

Summary

  • Combining a tree model with a small LLM-based decision model is the best policy we found. On the main test set it reserves 20.8% more memory than a perfect oracle would, with 1.7% of tasks killed for running out of memory on the first try. A single static request reserves 255.6% more.
  • A Jev-style decision model reads the task's code and beats a tuned tree model. Built on Qwen3-4B, it reserves 25.8% more than the oracle, against 34.0% for gradient-boosted trees. Its probabilities are also the most accurate of any single model (lowest Brier score).
  • Choosing from a list beats writing the answer. On the same base model, data and training, a head that scores every request option at once beats a model that generates the request as text, and it answers 9 to 17 times faster.
  • Unseen code is still hard for everyone. On two workload families no model trained on, even the best approaches reserve 79% to 91% more than the oracle.
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of code (for example, a pandas job that joins two tables). A run is that task executed once on a particular set of input files. Each task in the benchmark is run three times, on inputs of different sizes.
Request
The memory and CPU a run asks the cluster for before it starts, like memory="3Gi", cpu=1. In Kubernetes the memory request here is also the hard limit.
Peak memory
The most memory the run actually held at any moment, measured by the operating system (the kernel's ru_maxrss, the maximum resident set size of the process).
OOM kill
Out of memory. If a run's memory use exceeds its request, the kernel kills it. The benchmark assumes the platform then retries the run with double the memory, until it fits.
Grid, cell
Requests are chosen from a fixed list rather than any number: 17 memory sizes (256Mi, 384Mi, 512Mi, 768Mi, 1Gi, 1.5Gi, 2Gi, 3Gi, 4Gi, 6Gi, 8Gi, 12Gi, 16Gi, 24Gi, 32Gi, 48Gi, 64Gi) and 7 CPU sizes (0.5, 1, 2, 3, 4, 6, 8 cores). One entry in the list is a cell. Neighbouring memory cells differ by about 1.4×.
Oracle
An imaginary approach that knows each run's measured peak in advance and always picks the smallest cell that fits. Nothing can do better, so every approach is scored against it.
Memory regret (headline metric)
How much more memory an approach reserves than the oracle, to get every run to finish, counting failed attempts and retries. 0% means as good as the oracle; 100% means twice the oracle's memory. Lower is better. Full definition under Scoring.
First-attempt OOM rate
The share of runs whose first request was too small and got killed.
Test split
Runs of tasks whose code no approach saw during training, drawn from the same 10 workload families used in training.
Unseen families (out of distribution)
Runs from two whole workload families (DuckDB SQL and image arrays) that were left out of training entirely. This tests whether an approach generalizes to a new kind of code.
Cold start, history
A run's history is the earlier runs of the same task: their input sizes and measured peaks, the way a platform's run log would record them. A cold-start run has no history; it is the first time the task runs.
Arm
One of the approaches being compared (a rule, a tree model, an LLM). Each arm may have several decoding variants: different ways of turning its output into a request.
Calibration
Whether a model's stated probabilities match reality. If a calibrated model says "10% chance this request runs out of memory" for 100 runs, about 10 of them do.
ECE
Expected calibration error. The predicted probability of an OOM at the chosen request is grouped into 10 bins, and ECE is the average gap between predicted and observed OOM rates, weighted by bin size. 0 is perfectly calibrated.
Brier score
The squared error between the predicted probability for each of the 17 memory cells and the true cell (1 for the right cell, 0 for the rest), summed over cells and averaged over runs. 0 is perfect, 2 is maximally wrong. It rewards being both accurate and well calibrated.
Expected-cost decoding
For an approach that outputs a probability for each memory cell, pick the cell with the lowest expected cost: weigh the cost of each possible outcome (fits, or OOM and retry) by its probability. The alternative, argmax, simply picks the single most likely cell.
Part 2 · Methodology

The dataset: real code, real inputs

Earlier versions of this project labelled workloads with formulas that estimated their memory. This benchmark instead runs every workload and records what it actually used. Each workload is generated from one of 12 families of task code. Within a family, a random generator picks the code-level choices that decide how input bytes turn into memory, and picks the shape of the input files.

From tasks to runs

Each generated task is run three times. Each run scales the task's input files by a factor drawn between 0.25× and 4× of the family's base size, so one task spans small and large inputs. The three runs are shuffled, so a task's history can contain both larger and smaller runs than the current one. Run 1 of a task has no history (cold start), run 2 sees run 1, and run 3 sees runs 1 and 2.

Two corpora were built. v1 has 200 tasks per family, 7,200 runs in total. v2 has 400 tasks per family with a different random seed, 14,400 runs in total. Every number on this page is from v2 unless it says otherwise; the live check used v1.

Splits

Tasks, not runs, are split, so all three runs of a task land in the same split and no approach ever trains on the code it is tested on. A hash of the task id sends 70% of tasks in the 10 training families to train, 10% to validation and 20% to test. Both held-out families go entirely to unseen.

How each run was measured

The label for a run is what its code really used. Measurement happens inside Kubernetes pods on the cluster, in three separate processes so their memory never mixes:

  1. Prepare. A child process writes the run's input files to local disk in chunks of about 32 MB, so creating a 3 GB parquet file costs a few hundred MB of memory, not 3 GB.
  2. Run. A fresh Python interpreter executes the task's code on those files.
  3. Observe. When that process exits, the operating system reports its peak resident memory (ru_maxrss) and its CPU seconds. A sampler thread also records memory every 20 ms, to find how far into the run the peak happened, and to kill a run that would exceed its allowance before it takes the whole pod down.

Measurement passes. In v2 each measurement pod (12 CPU, 24 GiB, on spot capacity) ran 4 workloads at once. That is safe because peak memory is recorded per process. Each workload had a 5.25 GiB allowance. The roughly 1,070 runs that exceeded it were re-measured alone on 24 GiB pods with a 20 GiB allowance; runs still above that (166 in v2) were excluded. The work was split into 240 shards of 60 runs and took 71.6 pod-hours.

From peak to label. A pod needs room for the Flyte task runtime as well as the workload, plus some slack. The required memory for a run is defined as (measured peak + 180 MiB) × 1.05, and the run's label is the smallest grid cell at or above that. The CPU label is the smallest CPU cell covering the measured average cores (CPU seconds ÷ wall-clock seconds).

Reproducibility. Library versions are pinned exactly (pandas 3.0.5, pyarrow 25.0.1, polars 2.0.0, duckdb 1.5.6, numpy 2.5.2, scikit-learn 1.9.0, scipy 1.18.1, torch 2.14.0, Python 3.13), because a library upgrade can change a workload's memory. Workloads set their own thread counts (at most 3), and BLAS libraries are pinned to one thread unless the code says otherwise.

What every approach is allowed to see

A fair comparison requires that every approach gets the same information a real scheduler would have when a run is submitted, and nothing more:

  • The task's source code, written as a Flyte task.
  • Each input file's metadata, only as much as its format exposes. Every format gives its size on disk. A parquet file's footer also gives the row count and column types. A numpy file's header gives its shape and data type. A CSV gives only its header line and a JSON-lines file only the keys of its first record; their row counts are unknown without reading them.
  • The task's history: earlier runs' input sizes and measured peaks.

No approach sees the generator's hidden code choices, the family name, or anything measured on the run being decided. Automated tests check that changing those hidden fields cannot change any approach's input. An earlier baseline in this project broke this rule by reading the generator's own parameters, which is why it was rebuilt. Here is the prompt the LLM-based approaches receive (abridged):

The non-LLM approaches receive the same information as numbers: input bytes per format, visible row and column counts by type, array shape and data type, the presence of 64 memory-relevant code tokens (such as chunksize, .toarray(), mmap_mode), the largest numeric literal in the code, and summaries of the history.

The approaches compared

Each approach has at most one or two settings that trade memory against OOM risk. All of them are tuned the same way: by trying each value on the validation split and keeping the one with the lowest memory regret. No setting is picked by hand.

Training the LLM-based approaches

The SFT and decision models share everything except their output: the same base model (Qwen3-1.7B), the same LoRA adapters (rank 16, alpha 32, on all attention and MLP projections), the same prompt, the same 8,457 training runs, the same 3 epochs and the same effective batch of 16 (8 per step, 2 accumulation steps). LoRA layers use learning rate 2×10⁻⁴ and the decision heads 10⁻³, with 5% warm-up then cosine decay. Their training target is the oracle's cell. The decision models minimize cross-entropy on the memory cell plus 0.3 × cross-entropy on the CPU cell; SFT minimizes cross-entropy on the answer tokens only. After training, the decision models' softmax temperature is fitted on validation to make their probabilities calibrated. The 4B decision model used Qwen3-4B, 2 epochs, and 4 per step with 4 accumulation steps to fit in GPU memory. Each model trained on a single NVIDIA T4 GPU in 16-bit floating point: about 5 hours for 1.7B and 6 hours for 4B.

Scoring: what it costs to finish every run

Each approach's request for each test run is replayed through a simulator that follows the measured facts of that run:

  1. If the request fits (memory cell ≥ required memory), the run reserves that memory for its duration. Every run counts as one nominal hour plus a 0.02-hour start-up overhead, because the benchmark's workloads are scaled-down versions of longer real tasks.
  2. If it does not fit, the run is killed part way through, at the fraction of its runtime where the peak was measured, plus start-up overhead. That memory was reserved and wasted. The platform retries with double the memory, and the cycle repeats (up to 8 attempts).
  3. A late result has a cost too. Each OOM adds a penalty equal to one oracle-sized run, for the delay to whoever waits on the result. Without it, the cheapest strategy is to accept OOMs on a third of runs, which no operator would.
  4. Memory regret = (total GiB-hours this approach reserved across all runs, including failed attempts and penalties) ÷ (total GiB-hours the oracle reserved) − 1. Bigger runs count more, as they do on a real bill.
Worked example

A run needs 3.0 GiB, and its peak comes halfway through. The oracle asks for 3Gi and reserves 3 GiB × 1.02 h = 3.06 GiB-hours.

  • Asking for 4Gi: fits, 4 × 1.02 = 4.08 GiB-hours, or 33% over the oracle.
  • Asking for 2Gi: killed at the halfway point, 2 × 0.52 = 1.04 GiB-hours wasted; retry at 4Gi, 4.08; delay penalty, 3.06. Total 8.18 GiB-hours, or 167% over the oracle.

CPU is held at the oracle's value for every approach in the headline, because almost every workload uses about one core and a CPU mistake would otherwise dominate any comparison of memory decisions. Each approach's own CPU choices are scored separately ("CPU exact": the share of runs where it picked the oracle's CPU cell). Dollar costs under node-packed and AWS Fargate pricing were also computed and rank the approaches the same way; they are in the research log rather than on this page.

A decision head beats generating the answer

The SFT model and the decision models share the base model, adapters, prompt, data and training. The only difference is the output. SFT writes {"memory": "3Gi", "cpu": 1} token by token. The decision model scores every option in one forward pass and attaches a probability to each. On v2 the 1.7B decision model has lower regret (33.2%, against 41.6% for greedy SFT and 39.1% for 8-sample SFT), and it answers in about a tenth of the time.

Median wall-clock time for one decision, on one NVIDIA T4 GPU at batch size 1. The 27B model ran on a shared hosted endpoint, so its time includes queueing; it generated about 630 tokens per answer and did not finish about half its answers within 1,024 tokens.

How to read this
  • The horizontal axis is logarithmic: each grid line is ten times the previous one.
  • Generating text costs one model pass per output token (about 14 tokens here); a decision head needs a single pass however many options there are. Sampling 8 answers to estimate probabilities multiplies the generation cost further.
  • The tree model's time is shown for reference. It is about a millisecond on a CPU.

Calibrated probabilities are a risk dial

An approach that outputs probabilities can pick the request with the lowest expected cost, and re-pick it under a different tolerance for OOMs without retraining. An approach that outputs a single number can only add or remove a safety margin.

v2 test split. Each curve is one trained model, swept across its risk setting.

How to read this
  • Each dot is one setting of one approach. Horizontal: the share of runs killed on the first attempt. Vertical: memory regret. Lower-left is better on both.
  • Solid curves are approaches that output probabilities. Their dots come from re-deciding with the same predictions while the OOM penalty goes from 0 to 16 oracle runs, with no retraining. Dashed curves are single-answer approaches, swept by adding −1 to +4 cells of margin.
  • A curve that sits below another wastes less memory at the same OOM rate. At a 1% OOM rate the pooled model reserves about 23% more than the oracle, the 4B decision model about 30% and the trees about 36%; margin-padded rules need several times that.
  • Points beyond 25% OOM or 350% regret are off the chart.

The decision model scales

The same pointer head on Qwen3-4B, trained on one T4, is the best single model in the benchmark. On test it reserves 25.8% more than the oracle, against 34.0% for the trees and 33.2% for the 1.7B decision model, and it has the lowest Brier score of any single model (0.265). It answers in 256 ms without generating any tokens. On unseen families it is level with the trees (86.6% against 84.9%). On v1, with half the training data, the 4B model had beaten the trees on unseen families by 6.7 points; with more in-distribution data it became more confident on familiar code, not more accurate on new code.

Pooled, they beat both

The trees handle numbers like input sizes well and cannot read code; the LLM reads code and treats numbers as text. Both output probabilities over the same 17 cells, so they can be combined directly. The pooled distribution is p ∝ ptreesw · pLLM1−w, with w = 0.7 and the 1.7B pointer model chosen on validation. It is the best approach on every column of the leaderboard.

Checked against the kernel

The simulator decides "fits" or "OOM" from measured peaks. To check it, we took 120 runs from v1's test and unseen splits (10 per family) and ran each one again in a real pod for five approaches, sized exactly as that approach chose for its first attempt. Retries were off, so an OOM kill was the observation. That is 600 pods, and all of them ran.

How to read this
  • The bar is the sum of all 120 first-attempt requests. Shorter means less memory reserved. The OOM rate is what actually happened in the pods, not a simulation.
  • The simulator is conservative: it adds a flat 180 MiB of runtime overhead and 5% headroom, while the real Flyte process held about 158 MiB and shared libraries are counted once per pod rather than once per process. Small workloads therefore fit in less than the label says, so the leaderboard's OOM rates are slight overestimates.

Assumptions and limits

  • Workloads are scaled-down kernels of real tasks: seconds rather than hours, and peaks up to 20 GiB. Memory regret is a ratio and does not depend on run length, but absolute costs would.
  • The retry policy is "double the memory on every OOM", and each OOM costs one oracle-sized run of delay. A different penalty moves every approach along its curve in the risk-dial chart; it does not change which curves are lower.
  • The trees' 64 code tokens were chosen by the person who wrote the workload generator, which makes the tree baseline generous.
  • The hosted 27B model often ran out of its 1,024-token budget before answering; given more tokens or a stronger model, zero-shot results would likely improve, at a higher cost per decision.
  • Unseen families are only two, and both models that generalize best there do so differently by corpus. Rotating which families are held out, and calibrating on a held-out family, is the next experiment.
  • v1 quirk. 774 v1 runs had thread counts of 4 while being measured on 3-CPU pods, so their CPU labels top out near 3 cores. Their memory labels are unaffected. v2 does not have this issue.
  • Live validation used v1 and five of the approaches.
