RightSize Bench

A task is about to run. How much memory should it ask for? We measured 21,323 runs of real Flyte task code and scored rules, gradient-boosted trees, autoregressive LLMs and a Jev-style decision model on what it costs to get every run to SUCCEEDED.

Same input size, very different memory

Memory is set by the code as much as by the input. Within one family, the ratio of peak memory to input bytes spans one to two orders of magnitude, depending on choices a scheduler never sees in the input metadata: streaming versus eager reads, .toarray(), float32 downcasts, Python objects versus columns.

Peak RSS ÷ input bytes, 10th to 90th percentile per family, log scale (v1 corpus, partial sample of 2,300 runs).

The leaderboard

Memory regret is the GiB-hours reserved to get every run to SUCCEEDED, including OOM-killed attempts and their retries at double the memory, relative to an oracle that asks for the cheapest request that fits. Zero is perfect. "Unseen families" are two workload types no arm trained on.

A decision head beats generation on serving cost

The SFT and decision-model arms share the torso (Qwen3-1.7B), LoRA, prompt, data and training steps. Only the output differs. The autoregressive model writes {"memory": "3Gi", "cpu": 1} token by token. The decision model replaces the LM head with a pointer head that scores every option in the prompt in one forward pass and returns a calibrated probability for each. On v2 the decision model is better (33.2% memory regret against 41.6% greedy and 39.1% sampled) and answers in a tenth of the time.

Median wall-clock per decision at batch size 1. LLMs on one NVIDIA T4; the 27B zero-shot model on a shared hosted endpoint, where it spent about 630 generated tokens per decision and still left about half its answers unfinished within 1,024 tokens.

Calibrated probabilities are the risk knob

A distribution over requests lets the platform pick the request with the lowest expected cost, and re-pick it under a different OOM penalty without retraining. A point estimate can only add margin. At a 1% first-attempt OOM rate the pooled model reserves about 23% more than the oracle, the 4B decision model about 30%, and the trees about 36%; margin-padded rules need several times that.

v2 test split. Each curve is one model as its knob moves: OOM penalty 0–16× for distributional arms, ±cells of margin for point estimates. Lower-left is better.

The decision model scales

The same pointer head on Qwen3-4B, trained on one T4, is the best single model in the bench: 25.8% memory regret in-distribution, 24% less waste than the trees (34.0%), and the best calibrated (ECE 0.004). It answers in 256 ms with no generated tokens. On v1, with half the data, it was also 6.7 points better than the trees on unseen families; on v2 the two are level there (86.6% vs 84.9%).

Pooled, they beat both

The trees read the numbers well and the code badly; the decision model reads the code and treats numbers as tokens. Both emit calibrated distributions over the same requests, so one weighted geometric mean, with the weight tuned on validation, combines them. The pooled model is the best arm on every column: 37 to 39% less waste than either member in-distribution, at the lowest OOM rate in the bench.

Built as a Union factory

Limits

  • Workloads are scaled-down kernels of real tasks: seconds, not hours, and peaks up to 20 GiB. Regret is a ratio, so it does not depend on run length, but absolute dollars would.
  • The trees' code features were hand-picked by the person who wrote the workload generator, which makes them a generous baseline.
  • CPU is held at the oracle in the headline because nearly every workload wants about one core. Each arm's own CPU calls are scored separately: decision models 97% exact, trees 84%.
  • Unseen workload families remain the hard case for every arm: 79 to 91% memory regret on v2. More in-distribution data improved the decision models on familiar code and made them more confident, not better, on new code.
  • Live validation used the v1 corpus and the v1 arms.
