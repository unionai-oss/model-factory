RightSize Bench

A task is about to run. How much memory should it ask for? We measured 7,089 runs of real Flyte task code and scored rules, gradient-boosted trees, autoregressive LLMs and a Jev-style decision model on what it costs to get every run to SUCCEEDED.

Same input size, very different memory

Memory is set by the code as much as by the input. Within one family, the ratio of peak memory to input bytes spans one to two orders of magnitude, depending on choices a scheduler never sees in the input metadata: streaming versus eager reads, .toarray(), float32 downcasts, Python objects versus columns.

Peak RSS ÷ input bytes, 10th to 90th percentile per family, log scale (v1 corpus, partial sample of 2,300 runs).

The leaderboard

Memory regret is the GiB-hours reserved to get every run to SUCCEEDED, including OOM-killed attempts and their retries at double the memory, relative to an oracle that asks for the cheapest request that fits. Zero is perfect. "Unseen families" are two workload types no arm trained on.

A decision head beats generation on serving cost

The SFT and decision-model arms share the torso (Qwen3-1.7B), LoRA, prompt, data and training steps. Only the output differs. The autoregressive model writes {"memory": "3Gi", "cpu": 1} token by token. The decision model replaces the LM head with a pointer head that scores every option in the prompt in one forward pass and returns a calibrated probability for each. Quality lands in the same place. The cost per decision does not.

Median wall-clock per decision at batch size 1. LLMs on one NVIDIA T4; the 27B zero-shot model on a shared hosted endpoint, where it also left 52% of answers unfinished within 1,024 tokens.

Calibrated probabilities are the risk knob

A distribution over requests lets the platform pick the request with the lowest expected cost, and re-pick it under a different OOM penalty without retraining. A point estimate can only add margin. At a 1 to 2% first-attempt OOM rate, the distributional arms reserve a fraction of what margin-padded point estimates need.

Each curve is one model as its knob moves: OOM penalty 0–16× for distributional arms, ±cells of margin for point estimates. Test split. Lower-left is better.

The decision model scales

The same pointer head on Qwen3-4B, trained on the same data on one T4, improves on the 1.7B model everywhere: 42.5% memory regret in-distribution, and 78.1% on unseen workload families, 6.7 points better than the trees. It answers in 272 ms with no generated tokens.

Pooled, they beat both

The trees read the numbers well and the code badly; the decision model reads the code and treats numbers as tokens. Both emit calibrated distributions over the same requests, so one weighted geometric mean, with the weight tuned on validation, combines them. The pooled model is the best arm on every column, and on unseen workload families it cuts memory regret by 9 points over either member.

Built as a Union factory

Limits

  • Workloads are scaled-down kernels of real tasks: seconds, not hours, and peaks up to 20 GiB. Regret is a ratio, so it does not depend on run length, but absolute dollars would.
  • The trees' code features were hand-picked by the person who wrote the workload generator, which makes them a generous baseline.
  • CPU is held at the oracle in the headline because nearly every workload wants about one core. Each arm's own CPU calls are scored separately: decision models 97% exact, trees 84%.
  • A second corpus (14,400 runs, twice the training data) is being measured; this page will update.
