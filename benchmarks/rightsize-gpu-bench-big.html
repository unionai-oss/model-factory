RightSizeGPU Bench

A GPU task has to pick its GPU before it runs. If the GPU is too small, the run dies with a CUDA out-of-memory error and is retried on a bigger one. If it is too big, the run pays for memory it never touches. This benchmark measures how well different approaches predict a PyTorch task's peak GPU memory and GPU utilization from its code, its inputs and its earlier runs. This page reports the big release, at the scale of the RightSizeMem bench.

Summary

  • With 5,000 training runs, memory accuracy finally moves. On the 104-run full release, no approach was much above 50% within ±20% of the measured peak. Here, gradient-boosted trees read as a distribution reach 71.3% on 1,413 test runs, and the 4B decision model reaches 64.9%.
  • On unseen families the models that read code lead, and the trees collapse. The 4B decision model scores 50.5% on the two held-out families, and the fine-tuned 1.7B models 45–47%. The trees fall to 25–26%, below a rule on input size (34.8%).
  • For dollars, read the models by argmax. Decoding for accuracy almost never asks for more than a T4, so every run that needs a bigger GPU fails once. The trees' point prediction has the lowest cost (8.4% over the oracle); the decision model by argmax has 13.1%.
  • Utilization is easy to predict and hard to use. 78% of runs average 90% or more by NVML's measure. The trained approaches are 94–97% within 10 points, and the zero-shot 27B 56%.
  • About 5% of runs need more than a T4. 9,066 of 9,566 usable runs fit the cheapest GPU. The rest are where the money is lost.
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of PyTorch code, such as training a small GPT-style model. A run is that task executed once on a particular input file. Each task runs twice, on inputs of different sizes, and the second run sees the first as history.
Peak GPU memory (first label)
The most GPU memory in use at any moment of the run, in GiB, as NVML reports it (what DCGM_FI_DEV_FB_USED shows). It includes the CUDA context, weights, gradients, optimizer state, activations, and what PyTorch's allocator holds in reserve.
GPU utilization (second label)
The share of time a kernel was running (DCGM_FI_DEV_GPU_UTIL), averaged over the run, in 10-point buckets.
Grid, cell
Memory predictions are one of 12 sizes: 1, 1.5, 2, 3, 4, 6, 8, 10, 12, 15, 22 and 44 GiB. The last three are the usable memory of a T4, an L4 and an L40S.
Oracle
Knows each run's peak in advance and picks the smallest cell that covers it, so it runs on the cheapest GPU that fits.
Within ±20% (headline)
The predicted peak is within 20% of the measured peak, or within 0.5 GiB for small peaks. Higher is better.
Within one cell
The oracle's cell or a neighbour.
OOM
Share of runs whose first GPU was too small (a CUDA out-of-memory error).
GPU regret
Dollars to get every run to finish, including failed attempts and a delay penalty per OOM, divided by the oracle's dollars, minus 1. Lower is better. See Scoring.
Fills the device
A run whose peak reached at least 95% of the GPU's memory and still succeeded. cuDNN and PyTorch's allocator grow into free memory, so the peak is the GPU's size, not the task's need. These runs are not scored.
Test, unseen
Test: runs of new tasks from the 6 training families. Unseen: runs from two families held out of training, a two-tower recommender (recsys_train) and nearest-neighbour search (knn_search).
Part 2 · Methodology

The device ladder

A memory prediction becomes a GPU: the cheapest single-GPU instance on the demo.hosted cluster whose usable memory covers it. Prices are on-demand, per GPU-hour, in us-east-1.

An A10G (g5.2xlarge, 22 GiB, $1.212) is on the cluster but never the cheapest choice: an L4 has the same memory for less.

The dataset: real PyTorch code

Every workload is generated from one of 8 families of PyTorch task code. Within a family, a generator varies the choices an ML engineer reasons about when sizing a GPU (width, depth, batch, sequence length, precision, what is kept on the GPU, block sizes), and the size of the input file. Each task is a complete Flyte task.

The big release has 625 tasks per family and 2 runs per task: 10,000 runs. Runs loop for 60, 90 or 120 seconds (median wall time 94 s), so each covers at least two of DCGM's 30-second samples. Tasks are split by a hash of their id: 70% of the 6 training families' tasks to train, 10% to validation, 20% to test; the 2 held-out families go entirely to unseen.

How each run was measured

  1. Pass 1, T4. 1,667 shards of 6 runs each on T4 pods (g4dn.xlarge). Each run is a fresh Python interpreter that imports the task's module and calls it; a sampler reads NVML's memory.used and utilization.gpu every 0.5 seconds. 7.6 hours.
  2. Pass 2, L40S. Runs that hit a CUDA OOM on the T4 are re-measured on an L40S, in 184 shards. 4.1 hours; 42 of those shards ran past their time limit and were lost.
  3. Labels. The memory label is the smallest of the 12 cells that covers the peak; the utilization label is the 10-point bucket of the mean.

What every approach is allowed to see

What a scheduler has at submission: the task's source code, each input file's metadata (bytes, format, shape, dtype), and the task's earlier runs (peak GPU memory, mean utilization, device and wall time). No approach sees the generator's hidden choices, the family or the driver. The LLMs read these as a prompt that ends with the two option lists (gpu_memory, gpu_util) and a JSON answer format; the trees read the same information as about 70 numbers, including 40 PyTorch API tokens, the sizes of Linear layers, the batch slice, and the history.

Rules

static
One request for every run: a quantile of training peaks, tuned on validation. big-1 chose the 0.75 quantile, 5.9 GiB, so every run asks for 6 GiB on a T4. Utilization: the training median (95%).
vpa
The largest peak this task has used, times a margin tuned on validation (big-1: 1.0×), rounded up to a cell. With no history, the static request. Utilization: the last observed value.
size rule
Peak memory as a power law of total input bytes, fitted as a quantile of the training runs (big-1: the median). With history, the nearest past run rescaled by the input-size ratio, times a margin (1.0×).

Gradient-boosted trees

Model
scikit-learn HistGradientBoostingRegressor with the pinball loss (300 rounds, learning rate 0.06, 31 leaves) on log₂ of peak GiB. gbt fits quantiles 0.5 to 0.95 and keeps the one best on validation (big-1: the median), then rounds up to a cell. gbt-dist fits all 19 quantiles from 0.05 to 0.95 and turns them into a probability per cell through a piecewise-linear CDF. Utilization is a separate median-regression model.

zero-shot 27B

A hosted 27B Qwen model (qwen38-27b on the cluster's shared vLLM) at temperature 0. The system prompt lists the device ladder with prices and explains the OOM retry. The last JSON object in its answer is parsed and rounded up to an option. Scored on a sample of about 300 runs per split.

SFT 1.7B: fine-tuned to write the answer

Architecture
Qwen3-1.7B (28 layers, hidden size 2,048) with LoRA adapters (rank 16, α 32, dropout 0.05) on all seven projections of every layer; about 17M trained weights. The output is the model's own language-model head.
Training
Next-token cross-entropy on the oracle's answer, {"gpu_memory": "6GiB", "gpu_util": "90-100%"}, with the prompt masked out and logits computed only for the answer window. 3 epochs over 5,129 training runs, effective batch 16 (8 × 2 accumulation), AdamW at 2×10⁻⁴ with warm-up and cosine decay, fp16 with a loss scaler and gradient checkpointing on one T4. The loss fell to 0.04 per answer token.
Inference
Greedy: generate about 22 tokens and parse; a tuned margin of k cells (big-1 chose 0). No answer failed to parse. 8 samples: generate 8 answers at temperature 1 and count each memory cell as a probability, then decode. Greedy and 8-sample decoding of about 4,600 evaluation runs is what pushed this arm past its first 8-hour limit.

Architecture
The same Qwen3 and LoRA adapters, loaded without the language-model head. Each option's token sits at a fixed distance from the end of the prompt, because prompts are cut from the left to 2,048 tokens. A shared LayerNorm and a query and key projection (to 256 dimensions) per decision score every option against the answer slot in one forward pass.
Training
Cross-entropy on the memory cell plus 0.3 × cross-entropy on the utilization bucket. 1.7B: 3 epochs, about 960 optimizer steps, adapters at 2×10⁻⁴ and head at 10⁻³; the loss went 1.78 → 1.28 → 0.85 across epochs. 4B (36 layers, hidden size 2,560): micro-batches of 4 with 4 accumulation steps to fit a 16 GB T4, 2 epochs (about 640 steps); loss 1.63 → 1.05.
Calibration
One temperature fitted on validation by negative log-likelihood (1.7B: T = 0.99).
Inference
One forward pass gives 12 memory probabilities and 10 utilization probabilities. No tokens are generated: 180 ms per decision for the 1.7B and 391 ms for the 4B on a T4.

Decoding: two read-outs

gbt-dist, SFT with 8 samples and the decision models end with a probability for each of the 12 cells. The decoded rows pick the cell most likely to be within ±20% of the peak (ties go up). The argmax rows pick the single most likely cell. The two behave differently at the top of the ladder: the 22 and 44 GiB cells are wide, and a within-±20% window rarely gathers enough probability there, so the accuracy decoder almost never leaves the T4. Argmax does.

Scoring: memory accuracy first, dollars alongside

  1. If the peak fits the chosen GPU, the run pays one nominal task-hour at that GPU's price, plus 5% for start-up.
  2. If it does not fit, the run dies with a CUDA OOM at the point its peak was measured, and is retried on the next GPU up, up to 4 attempts.
  3. Each OOM adds a delay penalty of one oracle-priced run.
  4. GPU regret = total dollars ÷ the oracle's dollars − 1.
Worked example

A run peaks at 18 GiB, 3% of the way in. The oracle picks an L4: $0.978 × 1.05 = $1.03.

  • Predicting 12 GiB picks a T4. It dies at 3% ($0.04), the retry on an L4 costs $1.03, and the OOM penalty another $1.03: 104% over the oracle.
  • Predicting 30 GiB picks an L40S: $2.35, 129% over.
  • For a run that peaks at 3 GiB, predicting 4 GiB or 12 GiB both pick a T4 and cost the oracle's $0.55. Dollars only separate approaches on the 5% of runs above 15 GiB, which is why accuracy is the headline.

Accuracy decoding and dollars pull apart

Static, gbt-dist and SFT with 8 samples have exactly the same OOM rate (6.4%) and regret (34.1%) on test: every one of them sends every run to a T4, so every run above 15 GiB fails once. The decision models decoded for accuracy are close behind (5.2% and 6.3% OOM). Their argmax rows ask for an L4 or L40S when the most likely cell is there, and cut the OOM rate to 1.7–2.9% and regret to 13–16%. The trees' single point prediction (gbt) has the lowest regret of all, 8.4%, with 94.0% of runs within one cell.

What this means
  • The best read-out depends on what the prediction is for. For packing GPUs or sharing them, the accuracy decoder's memory number is the better one. For choosing which GPU to launch, argmax or a cost-aware decoder is better.
  • On unseen families the cost side is flatter (15–22% for every approach except the zero-shot 27B, at 25%), because fewer unseen runs need more than a T4.

What 15× more runs changed

Share within ±20%. full-1: 104 test and 158 unseen runs scored on memory. big-1: 1,413 and 2,411. The big profile also shortened the runs (60–120 s instead of 120–180 s).

How to read this
  • Every trained approach gained 15–23 points on test. The rules and the zero-shot 27B, which do not train, stayed where they were.
  • On unseen families the code-reading models gained (the 4B from 27.8% to 50.5%), while the trees lost ground (32.3% to 25.7%).

What the big release supports

  • GPU memory is learnable from code, with data. With 5,000 training runs, the best approaches land 63–71% of test runs within ±20% and 82–94% within one cell, up from about 50% on the 640-run full release.
  • On new code, a decision model that reads the source is the best choice (50.5% for the 4B), and the trees are not (25.7%).
  • Choose the read-out by the use. Accuracy decoding underserves the 5% of runs that need a bigger GPU; argmax and the trees' point prediction cost 8–16% over the oracle.
  • Not yet shown: whether more families close the unseen gap, and whether a utilization label that measures how much of the GPU is used (SM activity) would separate approaches better.

Assumptions and limits

  • 165 runs that needed more than a T4 have no measurement, because their L40S shards timed out. The tail above 15 GiB is undercounted; with them, the OOM cost of T4-only decoding would be slightly higher.
  • Measured on a T4 (and an L40S for the large runs). Peak memory carries over to other GPUs approximately; utilization does not.
  • One nominal task-hour per run in the cost model, and on-demand list prices for single-GPU shapes.
  • Runs are 60–120 seconds, covering 2–4 DCGM samples.
  • The trees' 40 code tokens were written by the person who wrote the generator, which makes that baseline generous.
  • Unseen families are only two.
