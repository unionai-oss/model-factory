RightSizeMem Bench: choosing memory requests from code

Abstract

Every task asks for its memory before it starts. If the request is too small, the kernel kills the task and it must be retried; if it is too large, the cluster pays for memory nobody uses. RightSizeMem Bench measures how well different approaches make that choice. It contains 14,234 runs of generated Flyte task code from 12 workload families, each run executed on the cluster and labelled with the smallest of 17 memory sizes that fits its measured peak. Every approach sees only what a scheduler sees when a task is submitted: the source code, the input files' metadata, and the task's earlier runs. Each is scored on memory regret, the extra memory it reserves over a perfect oracle once killed attempts, retries and a delay penalty are counted.

A single static request reserves 256% more memory than the oracle. Gradient-boosted trees bring that to 34%. A Jev-style decision model, Qwen3-4B fine-tuned with a head that scores each request option, reaches 26%, with the most accurate probabilities of any single model. Pooling a 1.7B decision model with the trees reaches 21%, with 1.7% of runs killed on the first attempt. With the same base model and training, scoring the options beats generating the answer as text, and answers 9 to 17 times faster. On two workload families held out of training, even the best approaches still reserve 79% to 91% more than the oracle. A live re-run in 600 real pods found no run that the simulator said would fit and that was actually killed.

Five findings

  1. 20.8%The pooled model is the best policy. The trees read input sizes well but cannot read code; the decision model reads code but handles numbers as text. Because both output a probability for each memory size, they combine by a weighted geometric mean (70% trees, chosen on validation). The result beats both members on every column, at the lowest OOM rate in the benchmark.
  2. 25.8%A decision model that reads the code beats tuned trees. On Qwen3-4B, the pointer head reserves 25.8% more than the oracle against 34.0% for the trees, and its probabilities are the most accurate of any single model (Brier 0.265) and well calibrated (ECE 0.004, against 0.039 for the trees). It answers in 256 ms on one T4 GPU without generating any tokens.
  3. 33% vs 42%Scoring options beats writing the answer. The 1.7B decision model and the fine-tuned generator share the base model, adapters, prompt, data and training; only the output differs. The decision model has lower regret (33.2% against 41.6% greedy and 39.1% with 8 samples) and answers in 126 ms against 1.1 s and 2.1 s.
  4. 23% at 1%Calibrated probabilities make OOM risk a setting. Approaches that output probabilities can re-pick each request for a different OOM tolerance without retraining. Held to a 1% first-attempt OOM rate, the pooled model reserves about 23% more than the oracle, the 4B decision model about 30% and the trees about 36%. Picking the single most likely size instead of the lowest expected cost costs the decision models 11 to 23 points.
  5. 79–91%Unseen code is the open problem. On the two held-out families (DuckDB SQL and image arrays), the learned approaches' regret rises 2.5 to 4 times, to between 79% and 113%. The pooled model is still best (79.0%), and the 4B decision model and the trees are level (86.6% and 84.9%).

Live check: 120 runs were re-executed in real pods at the first-attempt request of each of five approaches (600 pods). None of the 550 pods the simulator expected to fit were killed, and re-measured peaks matched their labels within 0.91–1.06× (median 1.00). On those runs the 1.7B decision model requested 57% less memory than the static request, with fewer real OOMs (2.5% against 4.2%).

Setup

How the benchmark works

Workloads
12 families of task code (pandas, polars, DuckDB, CSV, JSON lines, NumPy, scikit-learn, TF-IDF, PyTorch, image arrays, plain Python). A generator varies the code choices that decide memory, such as streaming versus eager reads, chunk sizes, .toarray(), dtypes and model size. Each task runs 3 times on inputs scaled 0.25× to 4×, so later runs have a history.
Labels
Each run's peak memory is read from the kernel (ru_maxrss) in a fresh process on cluster pods, with library versions pinned. Required memory is (peak + 180 MiB for the Flyte runtime) × 1.05. The label is the smallest of 17 sizes from 256Mi to 64Gi, about 1.4× apart, that covers it.
Splits
Split by task, so no approach is tested on code it trained on: 8,457 train, 1,138 validation and 2,316 test runs from 10 families, plus 2,323 runs from 2 families held out entirely. Settings are tuned on validation; test and unseen are scored once.
Approaches
Rules: one static request; history maximum times a margin; a per-format power law of input size. Trees: gradient-boosted quantile regression on ~110 numeric features (input bytes, visible schema, 64 code tokens, history). Autoregressive LLMs: a zero-shot 27B model, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision models: the same LoRA setup with the language-model output replaced by a head that scores each of the 17 sizes. All LLMs trained on one T4 GPU.

Key terms

Oracle
Knows each run's peak in advance and always picks the smallest size that fits. No approach can do better.
Memory regret
Total GiB-hours an approach reserves to get every run to finish, divided by the oracle's total, minus 1. A killed attempt reserves memory until the point of the peak, the retry doubles the request, and each kill adds one oracle-sized run as a delay penalty. 0% equals the oracle; 100% is twice its memory.
First-attempt OOM
The share of runs whose first request was too small and were killed for running out of memory.
Unseen families
The two workload families no approach trained on. They measure whether an approach generalizes to a new kind of code.
Calibration, ECE
A model is calibrated when its stated probabilities match outcomes. Expected calibration error is the average gap between predicted and observed OOM rates over 10 probability bins. 0 is perfect.
Expected-cost decoding
Given a probability for each size, choose the size with the lowest expected cost, counting the cost of an OOM and retry. The alternative, argmax, picks the most likely size.
