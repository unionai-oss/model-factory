RightSizeGPU Bench: predicting GPU memory from PyTorch code, at scale

Big release (big-1) · 10,000 measured runs
Abstract

A GPU task's GPU is chosen before it runs. Too little GPU memory and the run dies with a CUDA out-of-memory error and is retried on a bigger GPU; too much and it pays for memory it never uses. RightSizeGPU Bench measures how well different approaches predict a PyTorch task's peak GPU memory and mean GPU utilization, as Union's GPU monitoring reads them, from the task's code, its input metadata and its earlier runs. The big release has 10,000 runs of generated Flyte task code from 8 families, measured with NVML every 0.5 seconds on T4 GPUs, with runs that ran out of memory re-measured on an L40S; 9,566 are usable. The headline is the share of runs whose predicted peak is within ±20% of the measured one; dollars on the cluster's T4 / L4 / L40S ladder are reported alongside.

With 5,021 training runs, gradient-boosted quantile trees read as a distribution predict the peak within ±20% on 71.3% of 1,413 test runs, and a Qwen3-4B decision model, which scores each option written in its prompt, on 64.9%; rules and a zero-shot 27B model stay at 35–38%. On 2,411 runs from two families held out of training the order flips: the 4B decision model leads at 50.5%, while the trees fall to 25.7%, below a rule on input size. 95% of runs fit the cheapest GPU, and decoding for accuracy almost never asks for more, so the remaining 5% fail once; read by argmax, the same models cost 13–16% over the oracle, and the trees' point prediction 8.4%.

Four findings

  1. 71.3%GPU memory becomes predictable from code once there is data. On the 640-run release no approach was much above 50% on test. With 5,021 training runs, every trained approach gained 15–23 points; the rules and the zero-shot 27B, which do not train, did not move.
  2. 50.5%On new code, models that read the source transfer and trees do not. The 4B decision model loses 14 points on the unseen families; the trees lose 45, falling to 24% on nearest-neighbour search.
  3. 6.4%Accuracy decoding never leaves the T4. The 22 and 44 GiB cells are wide, so the cell most likely within ±20% is almost never above 15 GiB. The trees as a distribution, SFT with 8 samples and a static request all OOM on the same 6.4% of test runs. The argmax read-outs pick bigger GPUs and cut that to 1.7–2.9%.
  4. 78%Utilization by NVML's measure is mostly saturated. 78% of runs average 90% or more, because the metric counts any time a kernel is running. Trained approaches are 94–97% within 10 points; the zero-shot 27B, which expects small models to leave the GPU idle, 56%.
Setup

How the benchmark works

Workloads
8 families of PyTorch task code: a tabular MLP, a CNN, a GPT-style language model, a transformer encoder for embeddings, a CNN fed by a CPU data loader, a blocked all-pairs similarity, a two-tower recommender and nearest-neighbour search. A generator varies width, depth, batch, sequence length, precision, what stays on the GPU and block sizes. 625 tasks per family, each run twice on inputs 0.5× to 2× its base size, for 60 to 120 seconds.
Labels
Peak GPU memory from NVML (what DCGM's FB_USED reports), as the smallest of 12 cells from 1 to 44 GiB that covers it, and mean utilization in 10-point buckets. 1,667 T4 shards took 7.6 hours, and 184 L40S shards for runs that ran out of memory on the T4 another 4.1. Runs whose peak filled the device, 165 whose L40S shard timed out and 50 that exceeded 44 GiB are excluded.
Splits
By task: 5,021 train, 721 validation and 1,413 test runs from 6 families, plus 2,411 runs from 2 families held out entirely (recsys_train, knn_search).
Approaches
Rules: a static request; the task's largest past peak times a margin; a power law in input size. Trees: gradient-boosted quantile regression on about 70 features, and the same at 19 quantiles read as a distribution. Autoregressive LLMs: a zero-shot 27B, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision models: the same LoRA setup on Qwen3-1.7B and 4B with a head that scores each option in the prompt in one forward pass (180 and 391 ms on a T4).

Key terms

Peak GPU memory
The most GPU memory in use at any moment of the run, including the CUDA context and the allocator's reserve.
Within ±20%
The headline: the predicted peak is within 20% of the measured peak, or 0.5 GiB for small peaks.
Device ladder
A prediction runs on the cheapest GPU that holds it: T4 (15 GiB, $0.526/h), L4 (22 GiB, $0.978/h) or L40S (44 GiB, $2.242/h).
Decoded, argmax
Two read-outs of a probability per cell: the cell most likely within ±20% of the peak, or the single most likely cell.
Unseen families
The two families no approach trained on; they test generalization to new code.
