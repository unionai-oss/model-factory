RightSize Bench

A task's resource request is three guesses made before it runs: how much memory, how many CPU cores, and whether it needs a GPU and which one. This benchmark scores approaches on the whole request at once, in dollars, against the cheapest request that would have worked. It joins the three single-axis benches (RightSizeMem, RightSizeCPU, RightSizeGPU) into one corpus and one cost model, and adds a decision model trained with reinforcement learning on that cost.

Summary

  • RL against the cost model gives the lowest regret on familiar code, by a small margin. The RL-tuned 1.7B decision model, read by argmax, costs 8.0% more than the oracle on test runs. The supervised model it started from costs 9.7% more when decoded cost-aware, and trees cost 14.1% more.
  • The RL gain shrank with more data. On the smaller shakedown corpus (4,325 training runs), RL cut regret from 23.6% to 12.6%. With 10,500 training runs, the supervised model caught up and RL's lead is 1.7 points, all of it on the CPU and GPU rows.
  • On unseen task families, RL does worse than the model it started from (37.3% against 34.1%), and a hand-written rule is the best approach for the first time (32.5%). Reading the code's declared pool sizes transfers to new code; the learned CPU heads do not.
  • After RL, argmax is the right read-out. The RL policy already leans toward over-asking where under-asking is expensive, so the cost-aware decoder on top of it over-provisions (19.2%).
  • Every approach except the static request and the zero-shot 27B gets the GPU question right on every run: each GPU task gets a GPU, and no CPU task gets one.
Part 1 · Definitions

Terms used on this page

request
One choice on each of three axes: a memory cell, a CPU cell, and a GPU cell or "none". Each axis uses its own bench's grid.
oracle
The request each run's measurements say is right: the smallest memory cell that holds the measured peak, the CPU cell that covers the busiest 15 seconds, and the GPU cell that holds the peak device memory (or no GPU for a CPU task).
regret
A run's cost under the approach's request, divided by its cost under the oracle's, minus 1, averaged over runs. 0% is the oracle; 100% is twice its cost. Each run counts once, however much it costs. Lower is better.
first attempt ok
Share of runs whose first attempt succeeds: no host OOM, no CUDA OOM, and a GPU when the task needs one. Throttling does not count as a failure.
all axes right
Memory fits and is at most one cell above the oracle, CPU is within ±25% of the busiest 15 seconds, and the GPU choice lands on the oracle's device. A GPU task is scored on the GPU choice only.
source
Which bench a run came from: mem (RightSizeMem), cpu (RightSizeCPU) or gpu (RightSizeGPU). No approach is told the source.
test / unseen
Test runs are new tasks from task families the approaches trained on. Unseen runs (OOD) come from families held out of training on each bench.
argmax / decoded
Two ways to turn a model's probabilities into one request. Argmax takes the most likely cell on each axis. Decoded uses each bench's cost-aware decoder (see Decoding).

The dataset: three measured corpora, one schema

Every run is real task code executed in a pod and measured, collected by the three single-axis benches. The combined bench reads their published corpora as factory sources and rewrites them to one schema. A run keeps the labels its bench measured, and the axes its bench did not measure are left unscored.

Usable runs only. The GPU corpus is the one published by rsg-big-1. Runs in its 42 timed-out L40S re-measure shards, and runs whose outputs filled the device, are not in it. A GPU task's host memory and cores come with its GPU instance, so those two axes are not scored on GPU runs.

The decision models train on a balanced sample of 3,500 runs per source (10,500 in all), so that the memory corpus, the largest of the three, does not dominate. The trees and rules use all 19,106 training runs.

One cost model for all three axes

Each axis fails the way it fails on its own bench, all in one simulation. The cost is the dollars it takes to get the run to SUCCEEDED, including retries and lateness.

  1. Memory below the peak: the pod is OOM-killed when the run reaches its peak, then retried with double the memory.
  2. CPU below the busiest window: the run is throttled. Its measured per-second CPU series is replayed under the limit, and each second at u cores takes max(1, u ÷ limit) seconds. Memory-bench runs have no series, so their mean cores are used instead.
  3. GPU too small: a CUDA OOM at the peak, then a retry on the next device up. No GPU for a GPU task: it fails at start (no CUDA device), and the platform retries it on a T4. A GPU for a CPU task: it runs, at the GPU instance's price for the whole run.
  4. Delay costs something: each retry adds one oracle cost, and each hour late adds one oracle hourly price. Every attempt also pays 0.02 h of start-up.
Worked example

A one-hour CPU task needs 4Gi of memory and a steady 2 cores. The oracle asks for 4Gi and 2 cores: a dominant share of 0.5, so $0.096/h, or about $0.098 with start-up.

  • Asking for 8Gi and 2 cores costs the same. Memory is still not the dominant share, so the extra memory is free here (0% regret).
  • Asking for 4 cores doubles the share: about 100% regret.
  • Asking for 1 core halves the price, but the run takes 2 hours, and the hour late costs one oracle hour: about 99% regret.
  • Asking for 2Gi kills the run at its peak (here half-way through), and the retry runs at 4Gi. Together with the retry penalty that is about 151% regret.
  • Asking for a T4 runs it on a $0.526/h GPU instance: about 450% regret. This is the most expensive mistake a request for a CPU task can make.

What every approach is allowed to see

The same information as each single-axis bench: the task's source code, the metadata of this run's inputs (file sizes, formats, row counts, shapes, dtypes), and what earlier runs of the same task measured. That last part is peak memory, peak and mean cores, peak GPU memory and GPU utilization, whichever that task's bench recorded. Nothing tells an approach which bench a run came from, or its task family. Whether a task needs a GPU has to be read from the code. A test pins this boundary: none of the features or prompt fields can see the run's own measurements.

Rules

static
One request for every run: a training quantile of memory need and of CPU need (each 0.5, 0.75, 0.9 or 0.95, tuned on validation), and no GPU. big-1 chose the 0.9 quantile for memory and the median for CPU. It never asks for a GPU, so every GPU task fails at start and is retried on a T4.
rules
What a platform team would write. GPU: if the code mentions CUDA ("cuda", torch.cuda, .to(device), device =), ask for a GPU sized from the task's largest past GPU peak × a margin, or a training quantile of GPU peaks on a first run. Memory: the largest past peak × a margin, or the static cell. CPU: the largest past peak × a margin; with no history, the largest pool size the code declares (RightSizeCPU's code rule), else 1 core. big-1 chose margins of 1.5× for memory and 1.0× for CPU and GPU.

Gradient-boosted trees (gbt-dist)

Features
The union of the three benches' features: input metadata, each bench's code tokens and code numbers (declared pool sizes, work items, model sizes, batch sizes), four CUDA flags, and history over the unified schema.
Model
For each axis, 19 HistGradientBoostingRegressor quantile models (q = 0.05 to 0.95, pinball loss, 300 rounds, learning rate 0.06, 31 leaves) on log₂ of the need. The memory and CPU models train on the CPU-task rows and the GPU models on the GPU-task rows. A HistGradientBoostingClassifier predicts whether the task needs a GPU.
Inference
Each axis's 19 quantiles become a piecewise-linear CDF and then a probability for each cell. The GPU distribution is P(no GPU) = 1 − P(needs GPU), with the rest spread over the GPU cells. The request is then decoded per axis (see Decoding).

zero-shot 27B

Prompt
One system message for all three decisions: memory is a hard limit, CPU below the busiest 15 seconds throttles, unsized pools get one thread, GPU memory lands on the cheapest device that holds it (with its price), a GPU task with no GPU fails at start, and a GPU on a CPU task is paid for the whole run. Then the code, the inputs, the history, the three option lists, and {"memory": …, "cpu": …, "gpu": …} as the answer format.
Inference
qwen38-27b on the cluster's shared vLLM, at temperature 0 with up to 1,024 tokens. The last JSON object with a usable memory answer is parsed, and each value is rounded up onto its grid. Unparseable answers fall back to 4Gi, 1 core and no GPU, and are counted: 206 of about 900 on big-1. It is scored on a 300-run sample of each split.

Decision 1.7B: one forward pass, three pointer heads

The same pointer decision model as the single-axis benches, with a third decision. It reads the same prompt as the 27B and generates nothing. It scores every option of every axis in one forward pass.

Architecture
Qwen3-1.7B with LoRA adapters (rank 16, α 32, dropout 0.05) on all seven projections of every layer, loaded without its language-model head. Each option's token sits at a fixed distance from the end of the prompt, because prompts are cut from the left to 2,048 tokens and the options come last. The head is a shared LayerNorm plus one query projection and one key projection per axis. An option's score is the scaled dot product of the answer slot's projected state with that option token's.
Training
The sum of three cross-entropies against the oracle's cells, with an axis left out where it was not measured (memory and CPU on GPU runs). 2 epochs over the 10,500 balanced training runs: micro-batches of 8 with 2 accumulation steps, AdamW at 2×10⁻⁴ for the adapters and 10⁻³ for the head, 5% warm-up then cosine decay, fp16 with a loss scaler and gradient checkpointing on one T4. It took 4.9 h, with the loss going from 2.63 in epoch 1 to 1.32 in epoch 2.
Calibration
One temperature per axis, fitted on validation by the negative log-likelihood of the oracle's cell: 1.09 for memory, 1.04 for CPU and 0.94 for GPU.

Decoding: from probabilities to one request

gbt-dist and both decision models end with a probability for every cell of every axis. The decoded rows turn those into a request with each bench's own decoder:

  • GPU first: no GPU when P(none) is at least a threshold tuned on validation (0.3 for every arm on big-1). Otherwise, the GPU cell is chosen from the remaining probability by RightSizeGPU's decoder.
  • Memory: RightSizeMem's Bayes decoder, the cell with the lowest expected cost once an OOM's retry is priced in. It leans toward over-asking.
  • CPU: RightSizeCPU's decoder, the cell most likely to land within ±25% of the busiest window.

The argmax rows take the most likely cell on each axis. For a supervised model, that is the cell most likely to be the label. It ignores that asking one cell too low can cost far more than asking one cell too high.

RL 1.7B: training on the cost itself

The supervised model learns to imitate the oracle's cells. Imitation cannot see two things the cost model cares about. First, the axes interact: on a GPU node, memory and CPU are free, while on a CPU node a GPU is the most expensive mistake there is. Second, asking low costs more than asking high, by an amount the label does not carry. The RL arm starts from the supervised model and maximizes the bench's own reward directly: minus the run's cost ratio under the same simulator that scores the leaderboard, capped at 20.

for each batch of 8 prompts:                                   (6,000 training prompts, 1 epoch, 375 steps)
    one forward pass  →  P(memory), P(cpu), P(gpu)  per prompt
    sample K = 16 joint requests per prompt from the three heads     (no text is generated)
    reward_k  = − min(cost(request_k) ÷ oracle cost, 20)          the leaderboard's simulator
    advantage = (reward_k − mean over the 16) ÷ std over the 16      group-normalized, as in GRPO
    loss      = − mean( advantage × Σ_axis log P(chosen cell) )
                + 0.05 × KL( current policy ‖ supervised policy )
    a GPU task's memory and CPU terms are left out (they do not change its reward)
Method
GRPO (group-relative policy optimization) without generation. Each prompt's 16 sampled requests are a group, and each request's advantage is its reward relative to the rest of its group, so no value network is needed. Sampling 16 requests costs nothing beyond the one forward pass, because the policy is three categorical distributions, not a sequence of tokens.
Prompts
6,000 training runs, balanced across the three sources: half of them runs the supervised model did not train on, and half that it did.
Settings
AdamW at 3×10⁻⁵ for the adapters and 10⁻⁴ for the head, micro-batches of 8 with 2 accumulation steps, 5% warm-up then cosine decay, KL coefficient 0.05 against the supervised policy's distributions (computed once, before any update). 1.8 h of RL on one T4.
Read-out
The same calibration and decoding as the supervised model. The calibrated temperatures hit the calibrator's cap of 5.0 for memory and CPU (3.1 for GPU). The RL heads are sharp, and they are no longer trying to predict the label.

Where the regret comes from

Splitting each split by the bench a run came from shows which axis each approach gets wrong.

Mean regret by source. Test: 2,316 mem, 1,634 cpu, 1,413 gpu runs. Unseen: 2,323 mem, 1,800 cpu, 2,411 gpu runs. Shading grows with regret, capped at 100%.

How to read this
  • Memory rows are the hardest in-distribution slice for every approach (16–25% for the learned ones). After RL, the supervised model decoded is slightly better there (16.3% vs 17.1%).
  • RL's gain is on the CPU and GPU rows. CPU goes from −0.3% to −4.6%, and GPU goes from 10.4% to 7.6%. RL is the only approach that moved the GPU slice; the others all score 10.4–10.6% there.
  • Negative regret is possible on CPU rows. The oracle asks for the cell that covers the busiest 15 seconds. Asking one cell lower throttles that window briefly, and that can cost less than the core-hours it saves. RL found this.
  • Unseen CPU rows are where learning fails. The rules score 16.7% and the zero-shot 27B 14.7%, while every learned approach scores 52–96%. The rules read the declared pool size, which transfers to new code.

The RL curve

Each point averages the last 20 micro-batches (160 prompts × 16 sampled requests) at every 10th optimizer step. Top: the mean regret of the sampled requests, which is minus the reward minus 1. Bottom: KL divergence from the supervised policy, in nats, summed over the axes.

How to read this
  • The sampled requests start at about 13% regret (the first 50 steps) and end at about 6% (the last 50). The curve is noisy because each point covers only 160 prompts.
  • KL rises to about 2 nats in the first 250 steps and then holds. With a KL coefficient of 0.05, the policy is free to move a long way from the supervised model. That is consistent with the sharp heads and the loss on unseen families.

What 2.4× more supervised data changed

The same factory, code and settings ran on the full-1 corpora (rsa-full-3) and on the big-1 corpora (rsa-big-1). The CPU and GPU benches grew from about 900 to about 10,000 runs each, while the memory corpus stayed the same.

Mean regret. The source mix changed between the two runs: CPU and GPU rows were 9% of full-3's test runs and are 57% of big-1's. So compare orderings rather than single values.

How to read this
  • The supervised decision model gained the most: 23.6% → 9.7% on test.
  • RL's lead over it shrank from 11.0 points to 1.7.
  • On unseen families, nobody improved by more than a point or two, except the rules, which went from 59.4% to 32.5% because the unseen CPU rows grew from 160 to 1,800.

What this release supports

  • One decision model can size the whole request, at 189 ms and no generated tokens per decision, for 9.7% regret supervised and 8.0% RL-tuned on familiar code.
  • RL on the bench's own cost model helps most when supervised data is scarce. At 4,325 training runs it halved the regret; at 10,500 it is worth 1.7 points.
  • RL overfits to the families it trains on. It is worse than its starting point on unseen families, and its probabilities are no longer calibrated. A tighter KL penalty, or RL prompts from more families, are the obvious next tries; neither was run.
  • For new code, the declared parallelism is the signal that transfers. A learned approach that kept the rule's CPU answer where it has no history might combine the two; that was not tried.

Assumptions and limits

  • The oracle is the label, not the cost minimum. It asks for the cell that covers the busiest 15 seconds, and a slightly smaller CPU request can cost less, which is how CPU-row regret goes negative.
  • Prices are list prices: an m6i.xlarge dominant share for CPU pods and on-demand GPU instance prices. Spot discounts and bin-packing are not modelled.
  • A GPU task's host memory and cores are not scored. They come with the instance, so the request for them costs nothing either way.
  • Memory-bench runs have no per-second CPU series. Their throttling is modelled from mean cores, which understates bursts.
  • The GPU corpus is missing the runs of 42 timed-out L40S shards from rsg-big-1, which removes some of the largest GPU workloads.
  • The zero-shot 27B is scored on 300 runs per split (about ±5 points), and 23% of its answers were unparseable.
  • One training seed per arm. The 1.7-point test gap between RL and the supervised model has not been checked against seed-to-seed variation.
