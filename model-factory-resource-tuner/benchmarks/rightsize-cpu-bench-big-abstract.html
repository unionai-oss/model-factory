RightSizeCPU Bench: predicting peak CPU from code, at scale

Big release (big-1) · 9,900 measured runs
Abstract

A task's CPU request is set before it runs. Below the task's real peak, the kernel throttles it and it finishes late; above it, cores sit idle. RightSizeCPU Bench measures how well different approaches predict a task's peak CPU: the busiest 15-second average, which is what Union's task monitoring can show. The big release has 9,900 runs of generated Flyte task code from 11 workload families, 45× the small release. Each run was measured in its own pinned 7-core slot, two per 15-CPU spot pod, a method checked against one-run-per-pod cgroup labels before use (44 of 44 within ±25%). Every approach sees only the source code, the input files' metadata and the task's earlier runs, and is scored on the share of runs whose predicted peak lands within ±25% of the measured one.

With 5,628 training runs, a Qwen3-1.7B decision model, which scores each option written in its prompt, predicts the peak within ±25% on 97.9% of 1,634 test runs, ahead of gradient-boosted trees (94.6%) and the same model fine-tuned to write its answer (94.9%). On 1,800 runs from two families held out of training, the 4B decision model leads at 86.1%, level with a zero-shot 27B model (83.7%) and well ahead of the trees (68.4%). The 27B, the strongest approach on the small release, scores only 68.4% on test, because it predicts the average rather than the peak for code with a serial phase followed by a parallel one. Training data lifted every trained approach on familiar code; none improved on the unseen families beyond the 880-run release.

Four findings

  1. 97.9%Given data, a small decision model is the best CPU predictor on familiar code. The 1.7B decision model scores 96–100% on every kind of parallelism: explicit pools, Python's GIL, process pools capped by their work, I/O waits and phased code. It has the lowest error of any approach (0.24 cores). On the 220-run release it scored 71%.
  2. 86.1%On new code, reading the source transfers and trees do not. On the two unseen families, the 4B decision model (86.1%), the 1.7B (83.9%) and the zero-shot 27B (83.7%) are within a few points of each other. The trees fall from 94.6% to 68.4%, and to 48% on pyarrow's CSV reader, whose pool-size API looks like nothing in training.
  3. 6%The zero-shot 27B fails one pattern. It handles serial code and explicit pools, but gets code with a serial phase followed by a parallel one right only 6% of the time: it predicts the average, not the peak. That alone puts it at 68.4% on test.
  4. 0% / 63%The declared pool size is a strong one-line rule with fixed blind spots. Reading the largest pool size in the code scores 73.6% on test and 79.4% on unseen families, but 0% on I/O-bound code and 63% on Python thread pools held back by the GIL. Its 95% on the small release's unseen families came from 40 runs.
Setup

How the benchmark works

Workloads
11 families of task code: NumPy BLAS, polars, DuckDB SQL, scikit-learn ensembles, pandas, Python thread pools, process pools, PyTorch on CPU, pyarrow CSV, I/O-bound fetch loops, and a serial phase followed by a parallel one. A generator varies the choices that decide parallelism (pool sizes up to 6, GIL-bound or GIL-releasing work, chunk counts, batch sizes). 450 tasks per family; each runs twice, on inputs 0.5× to 2× its base size, for 30 to 60 seconds.
Labels
Each run gets 7 cores of its own: a 15-CPU spot pod runs two runs, each pinned to disjoint cores, and samples its own process tree every second. The label is the smallest of 16 core counts (0.25 to 8) that covers the busiest sliding 15-second window. A task's two runs agree to within 0.5% at the median: peak CPU is a property of the code. 1,238 shards took 17.6 hours, with no run lost.
Splits
Split by task: 5,628 train, 838 validation and 1,634 test runs from 9 families, plus 1,800 runs from 2 families held out entirely (DuckDB SQL and pyarrow CSV). Settings are tuned on validation; test and unseen are scored once.
Approaches
Rules: one static request; the task's largest past peak times a margin; the largest pool size the code declares, times a factor. Trees: gradient-boosted quantile regression on 71 numeric features, and the same trees read as a distribution over cells. Autoregressive LLMs: a zero-shot 27B model, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision models: the same LoRA setup on Qwen3-1.7B and Qwen3-4B, with a head that scores each core count written in the prompt. All fine-tuning on T4 GPUs.

Key terms

Peak CPU
The highest average core usage in any 15-second window of the run: the busiest value Union's monitoring can show.
Within ±25%
The predicted peak is within 25% of the measured peak, or within 0.25 core for small peaks. The headline metric. No two of the 16 options are more than 25% apart, so the oracle always scores 100%.
Throttling
A task asking for more cores than its limit is paused by the scheduler, so its work takes longer. It is never killed.
CPU regret
Core-seconds reserved (limit × stretched duration) plus one oracle core-second per oracle core for each second late, summed over runs, divided by the oracle's total, minus 1.
GIL
Python's global interpreter lock. Threads running pure Python share one core; libraries such as zlib, hashlib and NumPy release it and run in parallel.
Unseen families
The two families no approach trained on. They test whether an approach generalizes to new code and new pool-size APIs.
