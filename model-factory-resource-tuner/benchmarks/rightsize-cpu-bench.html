RightSizeCPU Bench

A task's CPU request is a guess made before it runs. Ask for fewer cores than the code uses and the kernel throttles it, so it runs slower; ask for more and the extra cores sit idle. This benchmark measures how well different approaches predict a task's peak CPU, as Union's own monitoring would see it, from the task's code and its input metadata.

Summary

  • Peak CPU is set by the code, not by the input size. Two runs of the same task, on inputs up to 4× apart in size, agree to within 0.7% at the median. What decides the peak is a pool size written in the code, and whether that pool can actually run in parallel.
  • A zero-shot 27B model is the strongest approach on balance. It predicts the peak within ±25% on 78.8% of test runs and 92.5% of runs from unseen families, with the lowest error (0.43 cores) and the lowest cost of throttling plus idle cores (15.4% over the oracle).
  • A one-line rule that reads the declared pool size scores well and fails in a predictable way. It reaches 80.8% on test and 95.0% on unseen families, but only 25% on Python thread pools held back by the GIL and 0% on I/O-bound code.
  • A 1.7B decision model learns this from 116 training runs. It reaches 71.2% on test and 82.5% on unseen families, ahead of the tree models on unseen code (47.5%).
  • These are small-sample results. The test split has 52 runs, so a share near 75% has a 95% interval of about ±12 points. Read the ordering of approaches, not the decimals.
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of code, such as a scikit-learn job that fits a random forest. A run is that task executed once on a particular set of input files. Each task in this release runs twice, on inputs of different sizes.
Cores, CPU request
CPU is measured in cores: 1 core is one CPU busy for the whole time, 2.5 cores is the work of two and a half CPUs. A task's CPU request, such as cpu="2", is what it asks the cluster for. Here it also acts as the limit.
Throttling
When a task tries to use more cores than its limit, the Linux scheduler (CFS) pauses it until the next period. Nothing is killed. The work just takes longer: a second that wanted 4 cores under a 2-core limit takes 2 seconds.
Peak CPU (the label)
The highest average core usage in any 15-second window of the run. This is the busiest value Union's task monitoring can show. See Why 15 seconds.
Mean CPU
Total CPU seconds divided by wall-clock seconds. A second, easier label. Peak and mean differ only for code with phases, such as a serial step followed by a parallel one.
Grid, cell
Predictions are chosen from a fixed list of 16 core counts, the way requests are written: 0.25, 0.5, 0.75, 1, 1.25, 1.5, 1.75, 2, 2.5, 3, 3.5, 4, 5, 6, 7, 8. One entry is a cell. The largest gap between neighbours is 25% (4 to 5).
Oracle
An imaginary approach that knows each run's measured peak in advance and asks for the smallest cell that covers it. Nothing can do better.
Within ±25% (headline metric)
The share of runs whose predicted peak is within 25% of the measured peak, or within 0.25 core for small peaks (a task that peaks at 0.3 cores is not wrong at 0.5). Higher is better. Because no two grid cells are more than 25% apart, the oracle always scores 100%.
Under-predicted
The share of runs whose predicted peak is below the measured peak. These are the runs that would be throttled.
MAE
Mean absolute error between the predicted and measured peak, in cores. Lower is better.
CPU regret
What the prediction costs, compared with the oracle, when it is used as the CPU limit: core-seconds reserved, plus a penalty for each second the run finishes late because it was throttled. 0% equals the oracle. Full definition under Scoring.
Test split
Runs of tasks whose code no approach saw during training, from the same 9 families used in training.
Unseen families
Runs from two whole families left out of training: DuckDB SQL and pyarrow's CSV reader. Each uses a pool-size API (SET threads, pa.set_cpu_count) that no training family uses.
Driver
What an approach has to understand to get a run right. threads: an explicit pool size the library honours. gil: a Python thread pool whose parallelism depends on whether the work holds the GIL. processes: a process pool, possibly capped by how many chunks of work there are. serial: single-threaded code. io: waiting dominates. phases: a serial phase, then a parallel one.
GIL
CPython's global interpreter lock. Only one thread runs Python bytecode at a time, so 8 threads looping in pure Python use about 1 core. Libraries such as zlib, hashlib and NumPy release the lock while they work, so their threads do run in parallel.
Cold start, history
A run's history is the earlier runs of the same task, with their input sizes and measured CPU. The first run of each task has none (a cold start); the second sees the first.
Arm, decoding
An arm is one approach being compared. Arms that output a probability for each cell need a rule, called decoding, to turn it into one prediction. Here they pick the cell most likely to be within ±25% of the peak. Argmax, the alternative, picks the single most likely cell.
Part 2 · Methodology

Why the label is a 15-second window

A benchmark for right-sizing should predict what the platform will measure, so the label copies Union's own metrics pipeline (read from the unionai/cloud repository):

  • The operator's Prometheus scrapes cAdvisor, the container metrics exporter, every 15 seconds. The kubernetes-cadvisor job inherits the global scrape_interval: 15s.
  • The console's task CPU chart is irate(container_cpu_usage_seconds_total[5m]): the rate between the last two scrapes, which is a 15-second average.

The benchmark therefore reads the same counter cAdvisor exports (the container cgroup's cpu.stat), once per second, and takes the busiest sliding 15-second average. Sliding, because the platform's scrapes land at an arbitrary moment in the run; the label is the worst any of those moments could see. Each workload loops for a time budget of 60, 75 or 90 seconds, so every run spans at least 4 windows (median 5.0) and its peak is a sustained window, not a start-up spike.

The dataset: real code, real parallelism

Every workload is generated from one of 11 families of task code. Within a family, a random generator picks the code-level choices that decide how many cores the task can use, and the size of its input files. Each generated task is a complete Flyte task: imports, a TaskEnvironment, and an @env.task function.

From tasks to runs

This release has 10 tasks per family and 2 runs per task: 220 runs. Each run scales the task's input files by a factor between 0.5× and 2× of the family's base size, so a task's two runs are up to 4× apart. The range is narrower than RightSizeMem's (16×) because peak CPU barely moves with input size; preparation time and pod memory do. The first run of each task has no history; the second sees the first.

Splits

Tasks, not runs, are split, so both runs of a task land in the same split and no approach trains on code it is tested on. A hash of the task id sends 70% of tasks in the 9 training families to train, 10% to validation and 20% to test. The 2 held-out families go entirely to unseen. Validation is used only to tune each approach's settings; test and unseen are scored once.

How each run was measured

Each run executes alone in its own pod, so nothing else competes for its cores:

  1. Prepare. A child process writes the run's input files to local disk.
  2. Run. The task's module is imported into a fresh Python interpreter and its function is called on those files. Importing the module, rather than executing it as a script, lets process pools pickle the task's helper functions.
  3. Observe. A sampler reads the container's cumulative CPU time from the cgroup's cpu.stat while the workload runs (with psutil as a fallback). The cumulative series is interpolated onto a 1-second grid before taking differences. Without that, a short final sampling interval produced spurious spikes of 20 cores in the pilot.

Pods. Each measurement pod has 9 CPUs and 14 GiB on spot capacity. Workloads size their own pools to at most 8 threads (16 for I/O waits), and the ninth core covers the harness and the Flyte runtime. BLAS and OpenMP are pinned to one thread unless the code sets them, and every prompt says so. The 220 runs were split into 37 shards of 6 runs. Four shards were reclaimed by spot twice each and finished on their third attempt. Measurement took 4.7 pod-hours.

From series to label. The peak label is the smallest grid cell that covers the busiest 15-second window. The mean label is the smallest cell that covers CPU seconds ÷ wall-clock seconds.

What every approach is allowed to see

Every approach gets the information a scheduler has when a run is submitted, and nothing more: the task's source code, each input file's metadata (only what its format exposes), and the task's earlier runs. No approach sees the generator's hidden choices, the family name or the driver. Here is a real prompt from this release, for a task that runs pure-Python work on a pool of 2 threads:

### Task code
```python
import flyte
from flyte.io import File
import hashlib
import os
import time
import zlib
from concurrent.futures import ThreadPoolExecutor
import numpy as np

env = flyte.TaskEnvironment(name="python-threadpool", image=...with_pip_packages("numpy"))

@env.task
async def digest_blobs(blob: File) -> dict:
    blob_path = await blob.download()
    TIME_BUDGET_S = float(os.environ.get("TIME_BUDGET_S", "60"))
    blob = np.load(blob_path)
    def work(chunk):
        total = 0
        for b in chunk[:20_000].tolist():
            total += (b * b) % 7
        return total
    with ThreadPoolExecutor(max_workers=2) as pool:
        ...
            results = list(pool.map(work, blob))
```

This run's measured peak was 1.00 cores: the code declares 2 threads, but the GIL lets only one run at a time. The system prompt explains the window, that unsized pools get one thread, and that a limit below the peak throttles. The non-LLM approaches receive the same information as numbers: 71 features, including input bytes and visible shapes, the presence of 44 CPU-relevant code tokens (such as n_jobs=, ThreadPoolExecutor, use_threads=False), the largest declared pool size, the smallest number of work items, and summaries of the history.

Training the LLM-based approaches

The SFT and decision models share the base model (Qwen3-1.7B), the LoRA adapters, the prompt, the 116 training runs, and the training schedule (3 epochs, effective batch 16), the same recipe as RightSizeMem. Their target is the oracle's peak cell and mean cell. The decision model minimizes cross-entropy on the peak cell plus 0.3 × cross-entropy on the mean cell, and its softmax temperature is fitted on validation afterwards. Each model trained on one NVIDIA T4 GPU. The same code serves all three RightSize benches: a small spec per bench names its two decisions, their options, prompt, parser and decoder.

Scoring: accuracy first, cost alongside

The headline is accuracy, because the task is to predict the peak. Cost is reported next to it, because it shows which mistakes matter. Each approach's predicted peak is used as the run's CPU limit and replayed against that run's own measured per-second series:

  1. Each second that wanted u cores under a limit L takes max(1, u ÷ L) seconds. Throttling stretches the work and never kills it.
  2. The run pays L × its stretched duration, in core-seconds.
  3. A late result costs something. Each second of delay adds one oracle core-second per oracle core (the oracle's limit × seconds late).
  4. CPU regret = total core-seconds across all runs ÷ the oracle's total − 1.
Worked example

A run uses a steady 4 cores for 60 seconds. The oracle asks for 4 and pays 4 × 60 = 240 core-seconds.

  • Asking for 5 cores: 5 × 60 = 300 core-seconds, 25% over the oracle. The fifth core sits idle.
  • Asking for 3 cores: each second takes 1.33 s, so the run takes 80 s. 3 × 80 = 240, plus 20 s late × 4 = 80. Total 320, or 33% over.
  • Asking for 2 cores: 120 s. 2 × 120 = 240, plus 60 s late × 4 = 240. Total 480, or 100% over.

Why cost is not the headline. Throttling only stretches time, so for a run that sits at its peak only part of the time, asking for less than the peak is often cheaper in core-seconds than asking for the peak. A decoder that minimizes expected cost therefore predicts low on purpose, which is the opposite of the task. The results show this directly. Approaches that output probabilities are decoded for accuracy: the cell most likely to land within ±25% of the peak, with ties going to the larger cell, because an under-prediction throttles while an over-prediction only idles.

The declared pool size is a strong hint, and sometimes wrong

Each dot is one run: the largest pool size its code declares, against its measured peak. If every pool ran fully in parallel, the dots would sit on the diagonal.

All 220 runs of small-1. "none" means the code declares no pool size (one thread here). Dots are spread sideways slightly so overlapping runs stay visible.

How to read this
  • The dashed diagonal is "peak = declared pool". Blue dots (explicit pools) mostly sit on or just under it, which is why the code-rule works on them.
  • Orange dots (thread pools under the GIL) split in two: pure-Python work stays at 1 core whatever the pool size, while zlib and hashlib work reaches the pool size.
  • Red dots (I/O-bound) sit near zero even with 16 threads, because the threads spend their time waiting. Purple dots (phases) peak at the pool size but average less.
  • Green dots (process pools) fall below the diagonal when there are fewer chunks of work than processes.

Where each approach goes wrong

Splitting the test runs by driver shows what each approach does and does not understand. Counts per driver are small (2 to 24 runs), so single cells move a lot; look for consistent patterns.

Share of test runs predicted within ±25%, by driver. Cell shading is proportional to the value.

How to read this
  • code-rule is perfect on serial, process-pool and phased code and near perfect on explicit pools, but scores 25% under the GIL (it reads max_workers=8 on pure-Python threads as 8 cores) and 0% on I/O.
  • zero-shot 27B gets the GIL right (88%) but the phased code wrong (12%): it predicts the average of a serial and a parallel phase, not the parallel peak.
  • gbt-dist and the decision model learned the GIL from training data (100% and 75%).
  • The I/O row has only 2 test runs.

Optimizing cost predicts low on purpose

The decision model outputs a probability for each cell, so it can be decoded two ways from the same predictions. The chart decodes it by lowest expected cost, as the penalty for each second of delay grows from 0 to 8 oracle core-seconds, and compares that with decoding for accuracy.

Decision 1.7B, pointer head, test split. Lines: cost-optimal decoding at each delay penalty. Dashed horizontal lines: accuracy decoding, the setting used on the leaderboard.

How to read this
  • At the default penalty (1 oracle core-second per second late), cost-optimal decoding under-predicts 60% of runs. A throttled second costs less than an idle core, so the cheapest policy is to throttle.
  • Only at a penalty of 4 does it under-predict as rarely as accuracy decoding, and by then its accuracy has already started falling again (65%) because it over-predicts.
  • Accuracy decoding gets 71% within ±25% with 17% under-predicted, from the same probabilities. The trees show the same pattern.

What the small release supports

  • The benchmark works end to end. 220 runs were measured from the cgroup in one factory materialization, every run spans at least 4 platform windows, and labels match what the code should do (pilot checks above).
  • Reading code is what separates approaches. Input-size features alone cannot predict a peak that does not depend on input size; approaches that read the pool size lead on unseen families.
  • The zero-shot 27B is strongest on balance, with the lowest error and cost and no training. The code-rule's 95% on unseen families says more about those two families (both honour their declared pool) than about the rule.
  • The decision model is competitive at a fiftieth of RightSizeMem's training data. Decoding for accuracy beats its own argmax by 8 points on test and 15 on unseen families, the same pattern as RightSizeMem.
  • Not yet shown: whether the 4B decision model, or pooling the trees with a decision model (RightSizeMem's best policy), beats the 27B. Both are in the full release.

Assumptions and limits

  • Sample size. 52 test runs and 40 unseen runs. A 95% interval on a share near 75% is about ±12 points.
  • Workloads are short kernels of real tasks: 60–90 seconds, long enough for 4–6 platform windows. Peak CPU does not depend on run length, but cost totals would.
  • The throttling model stretches each second by u ÷ L. Real CFS throttling works in 100 ms periods and can add latency spikes the model does not capture.
  • Pools are at most 8 threads (16 for I/O waits) on a 9-CPU pod, and BLAS is pinned to one thread unless the code sets it. On a larger node, an unsized BLAS pool would use every core.
  • The code-rule and the trees' 44 code tokens were written by the person who wrote the generator, which makes both baselines generous.
  • Unseen families are only two, and both honour their declared pool size, which favours any approach that reads it.
