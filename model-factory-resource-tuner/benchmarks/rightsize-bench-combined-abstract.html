RightSize Bench: sizing memory, CPU and GPU in one request

big-1 · 33,700 measured runs from three benches
Abstract

A Flyte task's resource request is three guesses made before it runs: memory, CPU cores, and a GPU or none. RightSize Bench joins the three single-axis benches (RightSizeMem, RightSizeCPU and RightSizeGPU) into one corpus of 33,700 measured runs of real task code, and scores every approach on the whole request, in dollars. One simulation prices every mistake: an OOM kill and retry for memory, a throttled replay of the measured CPU series, a CUDA OOM and retry on a larger device, a failed start for a GPU task given no GPU, and a GPU instance's price for a CPU task given one. The headline is mean regret: how much more than the oracle's request a run costs. Approaches see only the code, the input metadata and the task's earlier runs, and are never told which bench a run came from.

A Qwen3-1.7B decision model with three pointer heads, which scores every option of every axis in one forward pass, reaches 9.7% regret on 5,363 test runs when trained on the oracle's labels, against 14.1% for gradient-boosted trees. Tuned further with group-relative policy gradients (GRPO) against the bench's own cost model, it reaches 8.0%. On the smaller shakedown corpus, RL halved the regret (23.6% to 12.6%); with 2.4× the training data its lead is 1.7 points. On 6,534 runs from task families held out of training, RL is worse than its starting point (37.3% vs 34.1%), and a hand-written rule that reads the code's declared pool sizes is the best approach (32.5%).

Four findings

  1. 8.0%RL on the cost model gives the lowest regret on familiar code. Read by argmax, the RL-tuned decision model costs 8.0% over the oracle. Its gain over the supervised model is on the CPU rows (−0.3% to −4.6%) and the GPU rows (10.4% to 7.6%); the supervised model stays slightly better on the memory rows.
  2. 11 → 1.7RL's lead shrinks as supervised data grows. With 4,325 training runs, RL cut regret by 11 points. With 10,500, the supervised model caught up to 9.7% and RL's lead is 1.7 points.
  3. 32.5%On new code, a rule wins. On unseen families the rules (32.5%), trees (33.2%) and decision models (34.0–37.3%) are close, and RL is the worst of the learned ones. On unseen CPU tasks the rules score 16.7% by reading the declared pool size, while every learned approach scores 52–96%.
  4. 5.0After RL, read the policy by argmax. The RL heads are sharp: calibration pushes their memory and CPU temperatures to the cap of 5.0. Decoding them cost-aware on top adds a second safety margin and over-provisions (19.2%). Before RL it was the reverse: the supervised model needs the cost-aware decoder (9.7% vs 24.3% by argmax).
Setup

How the benchmark works

Corpus
RightSizeMem v2 (14,234 runs, peak memory and mean cores), RightSizeCPU big-1 (9,900 runs, peak memory and the busiest 15 seconds of CPU) and RightSizeGPU big-1 (9,566 usable runs, peak GPU memory), each split by task on its own bench: 19,106 train, 2,697 validation, 5,363 test and 6,534 unseen-family runs.
Request
Memory from 17 cells (256Mi to 64Gi), CPU from 16 (0.25 to 8 cores), and GPU from 13 (none, or 1 to 44 GiB, landing on a T4, L4 or L40S). CPU pods are priced by their dominant share of an m6i.xlarge, and GPU pods at the instance's on-demand price.
Approaches
Rules: a static request; a GPU if the code mentions CUDA, history × margin, else the declared pool size. Trees: 19-quantile gradient-boosted trees per axis plus a needs-a-GPU classifier. Zero-shot: a 27B model asked for JSON. Decision model: Qwen3-1.7B with LoRA and three pointer heads, trained by cross-entropy on 10,500 balanced runs (4.9 h on a T4). RL: that model, tuned by GRPO: 16 requests sampled per prompt from the three heads, rewarded by the simulator, with group-normalized advantages and a KL penalty to the supervised policy (6,000 prompts, 1.8 h on a T4).

Key terms

Oracle
The request the measurements say is right on each axis: the smallest memory cell that holds the peak, the CPU cell that covers the busiest 15 seconds, and the GPU cell that holds the device peak, or no GPU for a CPU task.
Regret
A run's cost to SUCCEEDED, including retries and lateness, divided by the oracle's cost, minus 1, averaged over runs. It can go slightly negative on CPU tasks, where a brief throttle can cost less than the oracle's extra cores.
Decision model
An LLM whose language-model head is replaced by a head that scores each option written in the prompt. One forward pass gives a probability for every option; no text is generated (189 ms per request on a T4).
GRPO
Group-relative policy optimization. Each sampled request's reward is compared with the others sampled for the same prompt, so no value network is needed.
Unseen families
Task families each bench held out of training, which test whether an approach generalizes to new code.
