RightSize Bench: learning Kubernetes resource requests from code

Abstract

Before a batch pod runs on Kubernetes, someone has to decide how much memory and CPU it gets and whether it gets a GPU. Too little makes it fail or run slowly, and too much wastes the cluster. We present RightSize Bench, a benchmark that scores this decision in dollars: each request is replayed against a measured run, failed attempts and throttling included, and compared with the cheapest request that would have run it. The benchmark has 32,082 measured runs of 33 families of generated Python tasks that use real libraries, from dataframes and SQL to PyTorch training and sharded language models. Every run appears twice, as a raw Kubernetes Job whose inputs are staged in one of four ways, and as a task submitted through Flyte, an orchestrator whose runtime we measure at about 70 MiB per pod. We checked the Job labels in about 480 real pods, which found two errors in our first release.

We release the benchmark with a set of baseline models: gradient-boosted quantile trees, and a 1.7B decision model whose pointer heads score the request options written in its prompt, trained with cross-entropy and then with reinforcement learning against the cost. On new tasks from familiar families, the trees pooled with the decision model come within 11.7% of the cheapest request on Job pods, against 44.5% for a rule that scales earlier runs by input size and reads the pod spec, and 58.5% for a zero-shot 27B model. On seven held-out families every approach does much worse, and the rule (42.7%) is as good as anything we trained. Models trained on Jobs move their memory request with the volume medium in the manifest about three times in four. 81% of the test tasks share their exact code with a training task, so the held-out families are the benchmark’s test of new code.

1  Introduction

Every container that runs on Kubernetes asks for resources before it starts [13], and each number fails differently. Memory is a hard limit: a container that uses more than it asked for is killed and has to run again. CPU is a soft limit: a container that wants more cores than it was given is throttled and finishes late. A GPU is a choice of machine. If the GPU is too small the task runs out of device memory, if a GPU task gets none it fails at start, and if a CPU task gets one it pays for hardware it never uses. Engineers usually pick these numbers by hand, once and generously, and large clusters run well below what their jobs reserve [22, 21].

Autoscalers that learn from usage history [18, 15] work well for long-running services. Batch work is harder, because the first run of a batch task has no history and later runs often see inputs of a different size. Much of what decides the right request is still known before the pod starts. A scheduler can read the code the pod will run, the size and format of its inputs, the way the pod spec stages those inputs, and what earlier runs of the same task used. This paper asks how well different approaches turn that information into a request, and measures the answer in dollars.

We treat the Kubernetes pod as the unit of work. Teams submit pods in different ways. The most direct is a batch/v1 Job, a container image paired with a manifest. Another is to write a typed Python function and let an orchestrator build the pod. We use Flyte [5] as the example of the second route: it turns a function into a pod and adds typed inputs and outputs, caching, retries and durable execution. In both cases the same user code runs in the same kind of pod. What differs is how inputs arrive, what else shares the container, and what the monitoring history reports.

The contributions are a benchmark and a first set of models trained on it (Figure 1).

  1. RightSize Bench. 32,082 measured runs of 33 families of generated Python tasks covering dataframes, SQL, linear algebra, classical ML, PyTorch training and inference, and sharded language models, with measured peak memory, CPU use at the 15-second resolution of cluster monitoring, and peak GPU memory across seven machine shapes (Section 5). Every run is presented as a raw Kubernetes Job, with one of four ways of staging its inputs, and as a Flyte task: 64,164 pods in all (Section 6).

  2. Labels checked in real pods. We checked the derived Job labels in about 480 pods, reading each container’s own cgroup counters (Section 7). The check found two errors in our first release: the Flyte runtime constant was 2.6 times too large, and some init containers were too small to hold the inputs they staged.

  3. A cost-based evaluation. One cost model covers memory, CPU and GPU together, and regret is measured against the cheapest request under that model (Section 8). Results carry intervals clustered by task and, for held-out families, by family; each approach’s read-out is chosen on validation; and every trained approach is trained three times.

  4. Baseline models. Gradient-boosted quantile trees over 209 scheduler-visible features, and a decision model that puts three pointer heads on Qwen3-1.7B so that one forward pass scores every option written in the prompt, trained with cross-entropy and then with reinforcement learning against the cost (Section 9). We compare them with static requests, two rules, a zero-shot 27B model, opinion pools and a novelty gate (Section 11).

  5. An open release. The dataset, with prompts, features and every approach’s requests, and the trained models, with standalone inference code, are on the Hugging Face Hub, and the benchmark itself is a Flyte factory that rebuilds only what changed (Section 12).

The models trained on Jobs read the pod spec: on first runs where only the volume medium changes, they move their memory request the right way about three times in four. On familiar code the best of them come within 12–14% of the cheapest request. On held-out families, a hand-written rule that scales earlier runs by input size and reads the manifest does as well as any of them.

2  Background: one pod, two ways to submit it

Requests, limits and cgroups. Each Kubernetes container declares a memory and CPU request, which the scheduler reserves on a node, and a limit, which the kubelet enforces through the container’s cgroup [13, 9]. Under cgroup v2, a container whose charged memory reaches its limit is OOM-killed. Anonymous memory and shared memory (shmem) both count toward the limit. Clean page cache does not, because the kernel can reclaim it first. A CPU limit is enforced as a CFS quota, so a container that exceeds it is slowed down instead of killed. Accelerators are requested as whole devices on node pools that carry them. In this paper a request also sets the limit, the usual choice for batch pods because it makes scheduling and failures predictable.

How the pod spec changes a task’s memory. Three details of a pod spec change how much memory a batch task needs without any change to its code. The first is the medium of the volume that holds its inputs. An emptyDir on node disk keeps files as page cache, which the kernel reclaims under pressure. An emptyDir with medium: Memory is a tmpfs, and every byte written to it is charged as shmem [14], so staging a 2 GiB input on tmpfs adds 2 GiB to the pod’s need. The second is who fetches the inputs. An init container runs to completion before the main container starts and has its own limit, while a download inside the job runs in the job’s container, so the client library’s memory counts against the job. The third is anything else that shares the container, such as an orchestration runtime.

A tmpfs page is charged to the cgroup of the container that writes it, so pages an init container writes are not charged to the main container. When the init container exits, its pages move to the pod’s cgroup and still count against the pod’s limit. We confirm this in real pods in Section 7.

Raw Jobs. A batch/v1 Job runs a pod template until it succeeds. Its backoffLimit says how many failed pods it replaces before giving up; batch teams often set it to zero and resubmit failures by hand or from an outer scheduler. A Job stages its own inputs, with an init container or in the job’s code.

Flyte. Flyte [5] turns a typed Python function into a Kubernetes pod. A user writes @env.task async def f(x: File) -> dict, and Flyte builds the image, renders the pod spec, moves typed inputs and outputs through object storage, caches results by their inputs, retries failed attempts, and records each execution so that a long pipeline can resume after a node is lost. None of this changes what the function does inside the container. It changes the pod’s edges: inputs arrive through Flyte’s download, the container also runs Flyte’s runtime, and the execution history reports the container’s peak with that runtime included. We measure the runtime at 55 MiB at rest and a median 70 MiB above the same workload run as a plain Job (Section 7). An approach that can size a Kubernetes pod should therefore be able to size a Flyte task with the same knowledge plus the runtime.

3  Related work

Sizing from history. Autopilot [18] sets Google’s container limits from the usage history of a job’s tasks, using moving-window and ML recommenders. Kubernetes’ Vertical Pod Autoscaler [15] recommends requests from a decaying histogram of observed usage. Borg traces show that most jobs over-request [22, 21]. Resource Central [1] predicts VM utilization from a subscription’s history. All of these size workloads that have run before, and run long enough to observe. RightSize Bench reports first runs (no history) and runs with history separately. Quasar [2] classifies new workloads from short profiling runs; RightSize Bench allows no profiling, only what a scheduler can read before the pod starts.

Learned predictors. Quantile regression [12] with gradient-boosted trees [6, 11] is a standard way to predict a distribution of resource need; it is the strongest classical approach here. Our decision model replaces a language model’s output layer with a pointer head [23] that scores option tokens written in the prompt. It is adapted with LoRA [10] on Qwen3 [17].

Training on the objective. Group-relative policy optimization (GRPO) [19] drops PPO’s value network by normalizing rewards within a group of samples for the same prompt. We use that group-normalized advantage with a single on-policy step per batch. Our policy is three categorical distributions, so a group is sampled from one forward pass, and the reward is the benchmark’s own cost simulator.

Combining and routing models. Logarithmic opinion pools [7] combine calibrated distributions by a weighted geometric mean. Temperature scaling [8] calibrates each model before pooling. Distance to the kk nearest training points is a common out-of-distribution signal [20]; our gate uses it to choose between two models.

4  Problem

A run is one execution of a task on one set of inputs, in one pod. Before the pod starts, an approach may look at three things. The first is the task’s code as it was submitted: job.py and the Job manifest for a raw Job, and the task module for a Flyte task (Section 6). The second is the metadata a scheduler can read about this run’s inputs: their sizes and formats and whatever the format’s header exposes, such as the row count and schema of a Parquet file or the shape and dtype of a .npy array. The third is what earlier runs of the same task used: their peak memory, peak and mean cores, peak GPU memory and utilization, wall time and input sizes. These are reported the way the platform’s monitoring would show them, which means the container’s own peak for a Job and the peak including the runtime for a Flyte task.

An approach is never given the task’s family, the hidden settings it was generated with, the corpus it came from, or anything measured on the run itself. A unit test checks that changing those fields leaves the features and the prompt unchanged. The code does identify the family in practice: each task is named after its family, and each family’s generator has a fixed function name and input schema. Section 11.4 re-scores with neutral names.

From what it can see, the approach chooses a request on three axes (Table 1). A GPU request lands on the cheapest machine that can hold it (Table 2). On a GPU node the host memory and cores come with the instance, so they are not scored.

5.1  Families, tasks and runs

A family is a Python generator. Given a seed, it writes a task function and the specification of its inputs, and it draws a few hidden settings, which we call knobs, that decide how input bytes turn into resource use. A pandas family decides whether to project columns, which dtype backend to use and whether to downcast floats. A training family picks width, depth, batch size, mixed precision and checkpointing, and a CPU family picks a thread-pool size or leaves it unset. The knobs show up only in the code an approach reads; we keep them to slice results.

Several families have small knob spaces, so their tasks repeat. In RightSizeMem, python_grouping has 3 distinct programs across its 400 tasks and jsonl_records has 4, while torch_train has 327. Of the 5,095 test Job pods, 4,135 (81%) run code identical to some training task’s, and differ from it only in input sizes and history. The remaining 960 test pods are new programs from familiar families, and the seven held-out families are new kinds of code. Section 11.2 reports all three.

Each run scales the leading dimension of the task’s inputs by a factor drawn log-uniformly from [0.25,4][0.25, 4] for RightSizeMem and from [0.5,2][0.5, 2] for the CPU and GPU corpora. Runs are shuffled, so a task’s history can be larger or smaller than the current run. The inputs are synthetic (normal floats, uniform integers, dictionary-encoded categories, random strings, Zipf-distributed word ids, and random bytes for images), written as Parquet, CSV, JSONL or .npy. CPU and GPU workloads loop until a per-task time budget runs out (30–60 s for CPU and 45–90 s for GPU), while RightSizeMem workloads run to completion.

5.2  RightSizeMem v2: peak memory

RightSizeMem has twelve families, chosen because they turn input bytes into memory in different ways: pandas group-bys and joins, polars pipelines in eager, lazy and streaming modes, DuckDB queries with and without a memory limit, chunked CSV and JSONL readers, NumPy linear algebra with optional memory mapping, scikit-learn estimators, TF-IDF, a small PyTorch model on CPU, image batches and pure-Python grouping.

Each run uses three processes. A child process writes the inputs to a temporary directory, a fresh interpreter runs the task body on those files, and the parent reads the child’s ru_maxrss and CPU time from wait4. BLAS and OpenMP are limited to one thread, and workloads set their own threads in code. The workload’s peak memory ww is its ru_maxrss. On Linux this value includes the measuring parent’s own peak at the time of exec, about 158 MiB here, which raises about a third of the smaller workloads’ labels by one cell (Section 7).

5.3  RightSizeCPU big-1: the busiest 15 seconds

RightSizeCPU has eleven families, chosen for how they use cores, since CPU need depends on parallelism more than on input size. They cover NumPy BLAS with and without a thread cap, polars and DuckDB with explicit thread settings, scikit-learn ensembles, serial pandas, Python thread pools that hold or release the GIL, process pools, a CPU PyTorch model, pyarrow CSV parsing, an I/O-bound pool and a task with two phases.

CPU time for the whole process tree is sampled every second. Each pod runs two measurements side by side on disjoint sets of seven cores; a check of 44 runs against single-run pods put all 44 within 25% of each other. The CPU label is the busiest 15-second average, because Prometheus scraping cAdvisor every 15 s sees a container at that resolution. Peak memory is measured as in RightSizeMem.

5.4  RightSizeGPU big-2: peak GPU memory across a machine ladder

RightSizeGPU has ten PyTorch families: a tabular MLP, a CNN, a CNN limited by its data loader, a GPT language model, a transformer encoder, a recommender with sharded embeddings, blocked matrix multiplication, nearest-neighbour search, fine-tuning of decoders from 0.6B to 7B parameters split across GPUs, and generation with a KV cache. NVML reports memory and utilization on every visible GPU every half second. Each run starts on a T4 and moves up the machine ladder (Table 2) whenever it runs out of device memory, and a run that runs out of memory on the largest machine it reached is censored. The label is the cheapest machine the run fits on. For machines a run was not measured on, we model the fit from its per-GPU peak and, for sharded code, its imbalance across GPUs. Single-GPU runs that outgrew a T4 were measured on an L40S, because L4 capacity was not available, and their L4 labels come from that peak.

5.5  Splits and history

Runs are split by task, never by run. A hash of the task id sends 70% of each family’s tasks to training, 10% to validation and 20% to test. Seven held-out families go entirely to a separate unseen split: DuckDB SQL (in both RightSizeMem and RightSizeCPU), image batches, pyarrow CSV parsing, nearest-neighbour search, generation with a KV cache, and the sharded recommender. Only DuckDB is a library no training family imports; the other five use libraries the training families also use, in code the training families do not contain. Every setting an approach tunes is chosen on validation, which has familiar families only.

The kk-th run of a task carries the task’s earlier runs as its history. A task’s first run has no history, and these cold starts make up 33–50% of each split (Table 4).

6  Every run as a Job and as a Flyte task

The workload code was generated as Flyte tasks, and nothing in the body of a task depends on Flyte. We use that to put every measured run into the benchmark twice, once as a raw Kubernetes Job and once as a Flyte task, with the task body unchanged in both. To make the Job version, job.py, we turn File parameters into paths, drop the flyte import, and add a __main__ block that stages the inputs, calls the function and writes result.json for upload. A batch/v1 manifest goes with it, carrying the image, the input locations, the thread settings the measurement used, the staging volume and an empty resources block, which is the request still to be decided. Figure 3 shows one task written both ways.

6.1  Stagings

How a Job’s inputs reach its container is the biggest thing that changes its memory need. Each task is assigned one of four stagings by a hash of its id, and all of its runs share it (Table 5). Inputs are fetched either by an init container running aws-cli or by the job itself with boto3, and they land either on node disk or on a memory-backed volume.

6.2  Label accounting

Let ww be the workload’s measured peak memory (Section 5) and let BB be the size of the staged inputs plus the result file, with each file rounded up to whole pages. The two kinds of pod need Job:1.05(w+48MiB⋅[boto3]+B⋅[tmpfs]),Flyte:1.05(w+R),R=70MiB,\begin{align*} \text{Job:}\quad & 1.05\,\bigl(w + 48\,\text{MiB}\cdot[\text{boto3}] + B\cdot[\text{tmpfs}]\bigr),\\ \text{Flyte:}\quad & 1.05\,\bigl(w + R\bigr), \qquad R = 70\,\text{MiB}, \end{align*} where the factor 1.05 is headroom and the memory label is the smallest grid cell at or above the need. Files on a memory-backed volume are charged to memory byte for byte, while the same files on node disk are reclaimable page cache and add nothing, since the measured workloads already read local files. The boto3 client adds 48 MiB to a workload’s peak. Its download also runs inside the job, taking d=bytes/440MB/s+0.4s per object+0.7sd = \text{bytes}/440\,\text{MB/s} + 0.4\,\text{s per object} + 0.7\,\text{s} at about 1.8 cores, so we prepend that window to the run’s CPU series. For a light job with a large input, the download can be the busiest 15 seconds of the run. The Flyte runtime RR is 70 MiB, measured in real task pods (Section 7). Our first release used 180 MiB, a value no probe had measured. Staging does not change GPU need.

The manifest sizes the init container at 256MiB+B256\,\text{MiB} + B for tmpfs stagings, so that it can hold what it writes. Our first release used a flat 256 Mi, which real pods showed cannot work for larger inputs (Section 7). Histories are reported in each interface’s own units: a Job’s earlier runs report the container’s peak as cAdvisor would, and a Flyte task’s report the peak including the runtime, as Flyte’s UI would. A Job’s history is computed with the same accounting as its label, so an earlier run’s reported peak is exactly its need without the headroom. Real cAdvisor peaks are noisier, and max_usage also counts page cache. The init container’s own download time is not priced, while the boto3 stagings pay for theirs inside the job, which makes the init stagings slightly cheaper than they are.

The staging constants come from an in-cluster probe using boto3 1.43 under cgroup v2. A bare interpreter holds 11 MiB. With boto3 imported, a client built and a file downloaded, the process holds 74–80 MiB, and it never peaks above that final level. Inside a real workload boto3 adds only 48 MiB at the median, because it shares modules the workload has already loaded. Download throughput rises from 122 MB/s for a 64 MiB object to 417–431 MB/s for a 4 GiB one.

7  Checking the labels in real pods

The Job labels in Section 6.2 are derived from the workload’s measurement, so we checked them twice. The first check (rt-k8sval-2) re-ran 176 corpus runs both as Flyte tasks and as their rendered job.py, as sibling processes inside one pod. It confirmed the arithmetic of the accounting. Measured over predicted memory was 0.999–1.000 at the median for every staging, and tmpfs was charged at exactly the input size. A pod with one container has one memory cgroup, so this check could not show where the kernel charges pages when a pod has several containers.

The second check (rt-k8spod-1) used real pods. We took 100 runs (48 from RightSizeMem, 44 from RightSizeCPU, and 8 init-tmpfs runs with inputs over 300 MiB) and gave each of them pods of its own, about 480 in all (Table 6). Every container sampled its own cgroup’s memory counters every 50 milliseconds.

The Flyte runtime. Before a task’s own module is imported, the Flyte task container already holds 55.0 MiB of anonymous memory, with almost no variation across the 100 runs (p10–p90 54.9–55.0 MiB). Its peak is a median 70 MiB above the same run’s peak as a plain Job (p10 53, p90 242 MiB), so running a workload inside the runtime’s process costs slightly more than the runtime does on its own. With the first release’s 180 MiB, the Flyte label matched the real container’s cell for only 23% of runs and was one cell too high for 70%. With 70 MiB, it matches for 58%, is one cell high for 33% and one cell low for 9%. The low ones are process pools, where the container counts every worker process, and some DuckDB and polars runs. The k8s-2 release uses 70 MiB, which lowers 61% of the Flyte labels on CPU nodes by one cell.

Where tmpfs pages are charged. A tmpfs page is charged to the container that writes it. When the job downloads its own inputs (boto3-tmpfs), the job container’s shared memory grows by the staged size times 1.0001 at the median (n=23n=23). When an init container stages them (init-tmpfs), the init container’s shared memory equals the staged size and the job container’s stays at zero (n=31n=31). The pages outlive the init container, however, and still count against the pod. With its limit set to the label minus the staged bytes, the job was OOM-killed in 9 of 31 init-tmpfs pods, and with the full label 30 of 31 ran. Adding the staged bytes to the label is therefore correct; the pages are enforced through the pod’s limit, not the container’s.

The first release’s init containers. With the flat 256 Mi init container of the first release, every staging up to 162 MiB ran and none of 254 MiB or more did. Ten of those were confirmed OOM-killed while staging, and six more failed. In that release, 982 of the 2,756 evaluated init-tmpfs Jobs staged more than 200 MiB, which means 7% of all Job rows described pods that could never have started. The k8s-2 release sizes the init container at 256 MiB plus the staged bytes.

Labels as limits. When we set the job container’s limit to its label, 98 of 100 runs succeeded (Table 7). Both failures were process pools, where the label records the largest single process but the cgroup counts all of them together. One cell below the label, 25 of the 97 runs that started were OOM-killed.

Labels are sometimes a cell too generous. We also compared each corpus label with the job container’s measured peak of anonymous plus shared memory, plus the same 5% headroom (Table 8). Depending on the staging, the label falls in the same cell for 52–68% of runs and within one cell for 91–100%. It is higher for 26–48% of runs and lower for at most 6%. Two things push labels up. The first is a quirk of ru_maxrss: on Linux, the value a parent reads for its child through wait4 includes the parent’s own high-water mark at the moment the child calls exec, because the kernel carries the old address space’s peak into the new one. The measuring parent in our corpora held about 158 MiB, so even the smallest workloads report at least that much. The second is memory-mapped input files, which RSS counts but the kernel can reclaim; numpy_linalg and image_batch both map their inputs. Neither effect makes a run fail at its label, and together they make about a third of labels one cell larger than necessary. The same comparison explains why 72 of the 97 Job pods that started one cell below their label still ran: for many of them the label is one cell high. The simulator of Section 8 replays the measured need, so the cheapest request it finds inherits the same bias, and regret is measured against a slightly generous floor.

8  Cost model and metrics

We score a request by what it costs to get the pod to finish, counting failed attempts, retries and lateness, all simulated from the run’s measurements. Each axis fails the way it fails on Kubernetes. If memory is too low, the container is OOM-killed when the run reaches its peak (at the measured fraction of its runtime) and is retried with double the memory, for up to eight attempts. If CPU is too low, the run is throttled: each second that wanted uu cores takes max⁡(1,u/limit)\max(1, u/\text{limit}) seconds, replayed against the measured per-second series. If the GPU is too small, the run hits a CUDA out-of-memory error and is retried on the next machine up, for up to four attempts. A GPU task given no GPU fails at start and is retried on a T4. A CPU task given a GPU runs normally and pays the GPU node’s price.

A CPU pod is priced by its dominant share of an m6i.xlarge (4 vCPU, 16 GiB, $0.192 per hour), that is p(m,c)=0.192⋅max⁡(c/4,GiB(m)/16)p(m,c) = 0.192\cdot\max(c/4,\ \text{GiB}(m)/16), and a GPU pod pays the on-demand price of its machine. Every attempt pays a start-up overhead: 0.02 hours on a CPU node and 0.05 hours on a GPU node, for image pull, device initialization and reading inputs. We normalize every run to one nominal hour of work, so that short measured runs stand in for longer production tasks. A run that exhausts its attempts pays for the attempts it made; this happens for fewer than 0.4% of evaluated pods for any approach.

Two penalties price time. Each retry adds the cost of running the label request once, which stands for the delay of running again, and each hour of lateness from throttling adds the same amount per hour. The label request’s cost is a fixed quantity for each run, so the penalties do not depend on the request being scored. These defaults match an orchestrator that retries automatically. A raw Job with backoffLimit: 0 fails and waits for someone to resubmit it, so Section 11.7 also scores every approach with retry penalties of 0, 5 and 20. Because costs include these penalties, the “dollars” in this paper are priced dollars, not a cloud bill.

The cheapest request. For each pod, the benchmark searches the grid for the request with the lowest cost under this model: every memory and CPU cell with no GPU for a CPU task (272 requests), and every GPU cell for a GPU task. This is the denominator of regret, and no request can beat it. It is often cheaper than the label, the smallest cell that fits: asking for one CPU cell below the busiest 15 seconds only throttles that window, and the cores saved over the rest of the run can cost less than the throttling. Against the label, our first release reported negative regret for some approaches on RightSizeCPU; against the cheapest request, regret is never negative.

Metrics. The headline metric is regret, the mean over pods of an approach’s cost divided by the cheapest request’s cost, minus one. Every pod counts equally however much it costs, and this is the quantity every approach tunes on validation. Dollar regret is total cost over total cheapest cost, minus one, so large jobs count for more. We also report the share of runs whose first attempt succeeds. For pairs of pods that come from the same run but differ in one detail of the pod spec, we check whether an approach’s memory request moves in the same direction as the label (Section 11.4), separately for pairs whose label moved and pairs whose label did not.

Uncertainty. Runs of the same task share code, and a run’s Job and Flyte pods share a workload, so pods are not independent. Intervals are 95% percentile intervals from a clustered Poisson bootstrap [3, 4] with 2,000 replicates. By default each task, with all of its runs and both pods of each run, gets one Poisson(1) weight; this measures uncertainty about new tasks from the same families. A claim about new kinds of code has only seven held-out families behind it, so for the unseen split we also cluster by family, which gives much wider intervals. Differences between approaches and between pod types are bootstrapped as paired differences on the same pods. Variation between trainings is reported separately, across three seeds (Section 11.8).

9  Approaches

Every approach produces a full request for every pod. Settings that an approach tunes, including which of its read-outs to report, are chosen on the validation split by mean regret; the reinforcement-learning settings are fixed and listed with the rest in Appendix C.

9.1  Static requests and rules

Static gives every pod the same request: a training quantile of memory need and of CPU need, and no GPU, so every GPU task fails at start and is retried on a T4.

Rules are what a platform team might write by hand. If the code mentions CUDA, the task gets a GPU sized from its largest past GPU peak times a margin. Memory is the largest past peak, converted to this pod’s units and multiplied by a margin, or the static request if there is no history. CPU is the largest past peak in cores times a margin; on a first run it falls back to the largest pool size the code declares (max_workers=, n_jobs= and so on), or one core.

Rules-sized also reads input sizes and the pod spec. With history, it takes the earlier run closest in input size and scales its peak by the ratio of input sizes. On a first run it estimates the workload’s peak as a+k⋅input MiBa + k\cdot\text{input MiB}, with aa and kk tuned on validation first runs, and adds the staging’s cost as read from the pod spec: 48 MiB if job.py imports boto3, and the staged bytes if the manifest says medium: Memory. It then converts that peak into the pod’s need with the accounting of Section 6.2. Rules-sized therefore uses the benchmark’s own accounting constants (the runtime, the boto3 footprint, the headroom), which a learned model has to infer from data.

9.2  Gradient-boosted quantile trees

The trees use 209 features a scheduler can compute. Twenty-seven describe the inputs and history: total bytes, bytes by format, visible rows, column counts, array shapes, the number of earlier runs, their peaks, and the size ratio to the closest earlier run. Another 173 mark API tokens in the code, such as groupby, TfidfVectorizer or ProcessPoolExecutor, and numeric literals such as pool sizes, layer widths and batch sizes. Four flag CUDA use, and five flag details of a Job’s pod spec (kind: Job, initContainers, medium: Memory, import boto3 and download_file).

For each axis we fit 19 quantile regressors [12] with scikit-learn’s HistGradientBoostingRegressor (quantiles 0.05 to 0.95, 300 rounds, learning rate 0.06, 31 leaves) on the base-2 log of the need, plus a classifier that predicts whether the task needs a GPU. The predicted quantiles define a piecewise-linear CDF, and each cell’s probability is the CDF mass between its edges. The fit is deterministic. Two ablations train on Job pods only or on Flyte pods only.

9.3  Zero-shot 27B

A 27B-parameter Qwen instruction model, served with vLLM [16], reads the prompt shown in Appendix B and answers in JSON at temperature zero. We read units as Kubernetes would (so 2 GiB, 2GB and 500m all parse) and round each value up onto the grid; an answer we cannot parse falls back to 4 Gi, one core and no GPU. The model writes plain-text reasoning before its answer even with thinking turned off, so we give it up to 8,192 tokens, and we also score a variant whose decoding is constrained to the answer’s JSON schema with 256 tokens. Both are scored on a family-stratified sample of 150 runs per split, each run’s Job and Flyte pods, which leaves 130 test and 150 unseen Job pods. Section 11.9 compares every approach on that same sample.

9.4  Decision model: three pointer heads on one forward pass

The decision model reads the prompt and scores every option on every axis in one forward pass (Figure 4). The options are written out at the end of the prompt. For each axis, a small head compares the hidden state at the prompt’s last token with the hidden state at each option’s last token: saxis(j)=⟨Wq,axisLN(a),Wk,axisLN(kj)⟩256,P(axis=j)=softmaxj(saxis(j)/Taxis).\begin{equation} s_{\text{axis}}(j) = \frac{\langle W_{q,\text{axis}}\,\mathrm{LN}(a),\ W_{k,\text{axis}}\,\mathrm{LN}(k_j)\rangle}{\sqrt{256}},\qquad P(\text{axis}=j) = \mathrm{softmax}_j\!\big(s_{\text{axis}}(j)/T_{\text{axis}}\big). \end{equation} Here aa is the last prompt token’s hidden state, kjk_j is option jj’s, each axis has its own affine maps Wq,WkW_q, W_k from 2,048 to 256 dimensions, LN\mathrm{LN} is one shared LayerNorm, and the temperature TaxisT_{\text{axis}} minimizes validation negative log-likelihood. This is a pointer mechanism [23] over option tokens: the model reads the candidates in its context, so the same heads work for any option list written in the same format.

The torso is Qwen3-1.7B [17] without its language-model head, adapted with LoRA [10] (rank 16, α\alpha 32) on every projection of every layer. Prompts are cut from the left at 3,072 tokens, a length no evaluated prompt reaches. The loss is the sum of the three axes’ cross-entropies, leaving out memory and CPU for GPU tasks. Training uses at most 5,000 rows per corpus and pod type, 27,936 rows in all, for one epoch with micro-batches of 8, two accumulation steps, and AdamW at 2×10−42\times10^{-4} for the adapters and 10−310^{-3} for the heads, on one NVIDIA L4. Two ablations train on one pod type only, on half the rows for two epochs, so that all three variants take the same number of steps; each is calibrated on its own pod type’s validation rows. The two pod types are drawn independently, so the model trained on both sees about 40% more distinct workloads than either ablation.

9.5  Turning a distribution into a request

The trees, the decision models and the pools all give a distribution on each axis, and we read each one out in two ways. The argmax read-out takes the most likely cell on each axis. The decoded read-out first decides whether to give a GPU, choosing none when P(none)P(\text{none}) is at least a threshold θ\theta tuned on validation, and otherwise the most likely GPU cell. For memory it picks the cell with the lowest expected cost, arg⁡min⁡m∑jC[m,j]P(j)\arg\min_m \sum_j C[m,j]\,P(j), where C[m,j]C[m,j] is RightSizeMem’s memory cost of requesting cell mm for a run that needs cell jj, retries included (a fixed matrix, not the per-run simulator). For CPU it picks the cell most likely to fall within 25% of the busiest window. An OOM costs a retry, so decoding leans toward asking for more memory. For each model, validation decides which read-out the leaderboard reports (Table 22).

9.6  Reinforcement learning against the cost model

Matching the label misses two things the cost model cares about. The axes interact: memory and CPU are free on a GPU node, while a GPU is the most expensive mistake on a CPU node. And asking for too little costs more than asking for too much. The RL approach starts from the decision model and maximizes the cost model’s reward (Figure 5). Because the policy is three categorical distributions, a group of 16 joint requests comes from one forward pass and no text is generated. Advantages are normalized within each group as in GRPO [19], and each batch takes one on-policy step, so the update is REINFORCE with a group baseline and an exact KL penalty to the supervised model; there is no clipped ratio. It trains on 6,000 training prompts, about half of them unseen by the supervised model, for one epoch with a KL coefficient of 0.05 and the reward capped at 20.

The fitted temperatures of every RL model sit at or near the top of the search range (5.0), so its decoded read-out is set by that bound. The RL policy moves probability away from the label cell on purpose, so calibrating it against the label is the wrong target, and validation prefers its argmax read-out.

9.7  Opinion pools

The trees and the language models make different mistakes. The trees read numbers exactly and have nothing to go on for code they have never seen; the language models read code well and treat numbers as tokens. A logarithmic opinion pool [7] combines their calibrated distributions on each axis: ppool(j)∝ptrees(j)wpLM(j)1−w.\begin{equation} p_{\text{pool}}(j) \propto p_{\text{trees}}(j)^{w}\,p_{\text{LM}}(j)^{1-w}. \end{equation} One weight ww is shared across the three axes and tuned on validation together with θ\theta, for the decoded read-out; nothing is retrained. A model trained on one pod type is pooled with trees trained on the same pod type.

9.8  A novelty gate

In our first release, the pooled RL model read by argmax was the best approach on familiar code and one of the worst on new code, while the RL model read out by decoding was the reverse. The gate sends each pod to one or the other by its distance from the training data: s(x)=110∑i=110‖z(x)−z(x(i))‖2,request={pool×RL, argmaxif s(x)≤τ,RL, decodedotherwise.\begin{equation} s(x) = \tfrac{1}{10}\textstyle\sum_{i=1}^{10}\lVert z(x) - z(x_{(i)})\rVert_2,\qquad \text{request} = \begin{cases}\text{pool}\times\text{RL, argmax} & \text{if } s(x)\le\tau,\\ \text{RL, decoded} & \text{otherwise.}\end{cases} \end{equation} Here zz standardizes the trees’ 209 features by their training mean and standard deviation, x(i)x_{(i)} are the ten nearest training pods, and τ\tau is the 95th percentile of ss on validation. Validation has familiar families only, so it cannot tune the gate: the threshold sends 5% of familiar pods to the RL model by construction, and validation regret falls steadily as fewer pods are routed. We chose the members, the signal and the threshold after seeing the first release’s unseen results, and fixed them before training k8s-2 at new seeds. k8s-2 has the same seven held-out families, so it tests whether the choice holds up after relabelling and retraining, not whether it generalizes to new families.

Our first release divided a feature that never varied in training by 10−910^{-9}, so any pod with an unseen import landed effectively infinitely far away. Such features now keep their raw units; the old scaling remains as a comparison. We also compare two other signals: kNN on the 27 numeric features alone, and the Jensen–Shannon divergence between the trees’ and the RL model’s predictions.

9.9  A Flyte-to-Job adapter

A team whose history is all Flyte tasks has no Job pods to train on. The adapter shifts a Flyte-trained model’s memory distribution with the accounting of Section 6.2: each cell’s representative need njn_j (its geometric middle) becomes (nj/1.05−R+48[boto3]+B[tmpfs])×1.05(n_j/1.05 - R + 48[\text{boto3}] + B[\text{tmpfs}])\times1.05, using the manifest’s volume medium, whether job.py imports boto3, and the input sizes. CPU and GPU come from the model’s own reading of the Job’s prompt. Its memory distribution can come from the model’s reading of the Job’s prompt (the variant a scheduler can deploy) or of the same run’s Flyte task, which a scheduler holding only a raw Job does not have. We report both.

10  Experimental setup

The benchmark runs as one Flyte factory on an EKS cluster: a graph of cached tasks, each of which publishes a versioned artifact (Figure 6). The trees and rules fit on a CPU pod, each decision model and the RL model train on one NVIDIA L4, and the zero-shot model runs as a shared vLLM service in the same cluster. Each of these is itself a batch pod that someone had to size.

We trained k8s-2 three times on the same data (rsk-k8s-2, -s2 and -s3). The seed controls data order, LoRA initialization and RL sampling; GPU kernels are not bit-for-bit deterministic, so even the same seed would not reproduce a model exactly. The zero-shot model is scored once. Tables show seed 1 with its bootstrap interval unless they say otherwise, and the leaderboard adds the mean and range over the three seeds. Seed 1 is the best or tied-best test seed for most trained approaches, so its numbers are slightly optimistic; Section 11.8 reports all three. Appendix D lists every cluster run.

11.4  Does a model read the manifest?

A model could do well on Jobs by learning only that a Job’s numbers run lower than a Flyte task’s, because a Job does not carry the runtime. We test this two ways.

Run and Job pairs. Of the 3,950 test pairs of a run’s Flyte pod and its Job pod on CPU nodes, the memory label differs in 29.9%. In 638 pairs the Job needs more, because it stages its inputs on tmpfs, and in 543 it needs less, because it has no runtime. A model that ignores the pod type keeps the same request for both pods, which scores 100% on the pairs whose label stays the same and 0% on those whose label moves. Models trained on both pod types move the right way on 56–67% of the pairs that move, and on 75–83% of upward moves (Table 19). The rules move the right way on 25%.

A controlled counterfactual. The pairs above mix the effect of the manifest with the effect of the runtime. To isolate the manifest, we took 1,189 first runs from the test and unseen splits and rendered each one as a Job under all four stagings, holding the task, code and inputs fixed (4,756 pods). Only the manifest and the way the job fetches its inputs change, and with no history, the manifest is the only evidence of the staging. Switching the volume from disk to tmpfs moves the label in 48.6% of test pairs and 74.2% of unseen pairs, and switching the fetcher from an init container to boto3 moves it in about a fifth.

The models trained on Jobs read the manifest (Figure 8 and Table 25). When the label moves, the decision model, the trees, RL and the pools move their request the right way on 72–78% of familiar-code pairs and 64–78% of unseen pairs. The Flyte-only model, which has never seen a manifest, does so on 21%. Static requests and rules never move, because on a first run they have only fixed defaults. On new code the models overreact: when the label does not move, which mostly means the staged inputs were small, they still change their request on 57–80% of unseen pairs. They pick up the fetcher less reliably (31–47% on test), which fits boto3’s 48 MiB only sometimes crossing a cell.

The task’s name. Generated tasks are named after their family (for example pandas-join), and the name appears in the code and the manifest. We re-scored the counterfactual’s first runs with each name replaced by a hash, without retraining (Table 20). On familiar code, regret changes by less than a point for every trained approach except the Flyte-only model (+1.8); on new code it rises by 0.5–3.6 points. Each family also has a fixed function name and input schema, which this test leaves in place, so it bounds the name’s effect without removing the family’s identity from the code.

11.7  Dollars and the price of a retry

Mean regret counts every pod equally, while dollar regret is dominated by large jobs. On familiar code the two mostly agree: the pooled RL model read by argmax costs 18.1% more than the cheapest requests in total, and the gate 21.9%. On new code, dollars rank the trees first (86.9%), because they size the largest jobs better even though their mean regret is among the worst. The trees cost $959 per 1,000 unseen Job runs, against $1,126 for rules-sized, $1,177 for the gate, and $513 for the cheapest requests.

A raw Job with backoffLimit: 0 does not retry: it fails, and someone resubmits it. That makes an OOM much more expensive than our default penalty. Figure 9 and Table 14 re-score every approach with penalties of 0, 5 and 20 times the label request’s cost per retry. Every approach was tuned at the default penalty of 1, so this measures how fixed requests hold up when failures get dearer, not how well each approach could adapt. On familiar code the pooled decision model has the lowest regret at every penalty from 1 to 20 (95.3% at 20), though at 20 the pooled RL model is within -13.4 points [-27.2, +0.7]. On new code, rules-sized has the lowest regret at penalties of 5 and 20 (116.1% and 391.4%), ahead of RL and the gate (140.1% and 505.1%). Clustered by task, that lead is clear (-113.7 points [-129.8, -97.4] at 20); clustered by the seven families, it is not ([-263.7, +15.9]). For teams that run raw Jobs without retries, the evidence favours a rule that scales by input size and reads the manifest on code nobody has seen before, and does not rule out the trained models.

12  Release

The benchmark and the models are on the Hugging Face Hub, in the unionai organization’s “RightSize Bench” collection, and the code that builds and scores them is at https://github.com/unionai-oss/model-factory.

The dataset (unionai/rightsize-bench, CC-BY-4.0) has one row per pod, 64,164 in all, split into train, validation, test and unseen. Each row holds what an approach may read (the task code, the Job manifest, the input metadata, the history, and the rendered prompt), the labels as grid cells and as option text, the cheapest request and its cost, and the columns the cost simulator replays. Configurations give the Job and Flyte pods separately, the 209 tree features, the counterfactual renditions, and every reported approach’s request and cost for each pod and seed, so a new approach can be compared with ours pod by pod. The simulator is resource_tuner/bench_all/scoring.py; it runs on the published rows unchanged.

The models (Apache-2.0) are the trees, in scikit-learn’s skops format; the decision model and the RL model; and the two training-data ablations:

  • unionai/rightsize-trees

  • unionai/rightsize-decision-qwen3-1.7b and unionai/rightsize-rl-qwen3-1.7b

  • unionai/rightsize-decision-qwen3-1.7b-job-only and -flyte-only

Each decision-model repository holds the LoRA adapter, the pointer heads in safetensors, the calibration, and a standalone inference file that needs only transformers and peft; seeds 2 and 3 are branches. A unit test checks that the inference file reproduces the training code’s scores exactly in fp32.

Intended use. The benchmark is for comparing ways of choosing a pod’s resource request before it runs. It is not a model of any production cluster: the workloads are generated and short, prices are list prices, and the labels have the biases of Section 7. The models are baselines for that comparison and have not been tested on production workloads.

Contamination. The test and unseen labels are public. A model trained on them, or on this paper’s predictions, is no longer evaluated on new tasks; this release has no private held-out set.

Maintenance. Every release is a tagged revision of each repository (this one is k8s-2), and its factory run is recorded in the project’s research log. The earlier releases (RightSizeMem v2, RightSizeCPU big-1, RightSizeGPU big-2, and k8s-1) are described in Appendix D.

Environment. Runs were measured on Amazon EKS under cgroup v2, on spot c5.4xlarge nodes for the CPU corpora and on the GPU shapes of Table 2, with pandas 3.0.5, polars 2.0.0, DuckDB 1.5.6, PyTorch 2.14.0 and scikit-learn 1.9.0. The inputs are synthetic and contain no personal data.

13  Discussion

One measurement, two kinds of pod. The user code is the same whichever way a pod is submitted, so one measurement of the workload can label both a raw Job and a Flyte task, as long as the accounting for the pod’s edges is right. Getting it right took real pods. Sibling processes in one pod confirmed the arithmetic. Only per-container cgroups showed where tmpfs pages are charged, that the first release’s init containers could not hold their inputs, and that the Flyte runtime was less than half the size we had assumed. Labels derived this way should be checked against the cgroup, since a second RSS measurement repeats the first one’s biases.

What a model learns from Jobs. A model trained on Jobs reads the manifest. It changes its memory request when the volume medium changes, on first runs where nothing else gives the staging away. Flyte tasks add little to that model’s accuracy on Jobs, and a Flyte-only model transfers poorly; an adapter that applies the accounting helps only when it can also see the run’s Flyte task. For a team that submits pods both ways, the practical advice is to train on the pods it actually runs.

Familiar code, new programs and new families. The benchmark separates three levels of novelty, and the models handle them differently. Most familiar-family test tasks repeat a training program at a new input size, which every trained approach handles well. New programs from familiar families cost the decision model the most and the pooled RL model almost nothing. New families cost every approach, and there a rule that reads input sizes and the pod spec is as good as anything we trained. Pooling the trees with a language model helps on familiar code and hurts on new families, because the pool’s weight is tuned on familiar families. A gate can recover the better approach on each split when its detector works, and on this benchmark the detector’s job is easy. A benchmark with held-out families built only from familiar code tokens would test it properly.

Cost, not accuracy. The read-out that matches labels best is not the one that costs least. Cost-aware decoding over-asks memory on purpose. The label itself is not the cheapest request: one CPU cell below the busiest window is often cheaper, which is why our first release, scored against the label, reported negative regret. And the ranking on new code flips when retries get expensive. A benchmark for this decision has to score money, and it has to say what a failure costs.

14  Limitations

The tasks. The workloads are synthetic. They use real libraries and real code paths, but the tasks are generated, the data is random, and runs take seconds to minutes. Several families have only a handful of distinct programs, so most of the familiar-family test split repeats training code. The seven held-out families were chosen by hand, two of them are DuckDB families from different corpora, and only DuckDB is a library the training families never import. The code names the family through task names, function names and input schemas; the neutral-name test removes only the first. The people who wrote the generators also wrote the tree features and the rules.

The labels. The ru_maxrss floor and memory-mapped inputs make about a third of memory labels one cell larger than needed; on tmpfs stagings a mapped input may be counted twice. Process pools are labelled by their largest process, which is why two of 100 real pods failed at their label. RightSizeMem has no per-second CPU series, so its throttling is modelled from mean cores. The Job labels and the Job history are derived from the workload measurement with the same accounting, and were checked on 100 runs in real pods and 176 in one pod; no Flyte pod was run with its limit at its label, and GPU runs were not re-measured as Jobs. Most multi-GPU runs were censored because the cluster had no capacity for them, single-GPU runs that outgrew a T4 were measured on an L40S, and fits on unmeasured machines are modelled, so the GPU labels above a T4 rest partly on the fit model.

The evaluation. The cost model uses list prices with no spot discounts or bin-packing, and every approach was tuned at a retry penalty of 1; we re-priced fixed requests at other penalties without re-tuning. Generalization to new kinds of code rests on seven families, so family-clustered intervals on the unseen split are wide, and the gate’s members were chosen with those families in view. The RL model’s calibration temperature sits at its search bound. We trained three times, enough to show that rankings on new code within about ten points are not stable and not enough to bound that variation. The zero-shot model was scored once, on 130 test and 150 unseen Job pods.

15  Conclusion

RightSize Bench scores the request a scheduler makes before a Kubernetes pod runs, in dollars against the cheapest request, across 33 families of task code submitted both as raw Jobs and through Flyte. Checking its labels in real pods fixed two errors and measured Flyte’s runtime at about 70 MiB. Gradient-boosted trees pooled with a small decision model trained on Jobs come within 12% of the cheapest request on familiar code, and the decision model reads the manifest. On held-out families a careful rule does as well as any model we trained, and it holds up best when failures are expensive. The open problems are new programs and new families, and a benchmark whose held-out code does not announce itself through new tokens. The dataset, the models and the factory that builds them are public.

B  A complete prompt

The prompt every language-model approach reads, here for the init-tmpfs Job of a k8s-2 test task. The init container’s memory limit is 281 Mi: 256 Mi plus the 25 MiB it stages onto the memory-backed volume. A Flyte pod’s prompt shows the task module in place of job.py and the manifest, and reports history peaks with the runtime included.

System

You size batch jobs before they run: Flyte tasks, or Kubernetes Jobs given as a Python module and its manifest. Given the code, the metadata of this run's inputs, and what earlier runs of the same job used, choose the cheapest request that runs it: memory, CPU cores, and a GPU or none. Memory is a hard limit: below the peak the container is OOM-killed and retried with double. A Flyte task's memory includes the Flyte runtime; a Kubernetes container's includes whatever the job loads to fetch its inputs, and files written to a memory-backed emptyDir (medium: Memory) are charged to it. CPU below the busiest 15 seconds' use throttles the task and it finishes late. Thread pools the code does not size get one thread. gpu is the peak GPU memory to provision, or none for a task that does not use CUDA; it lands on the cheapest machine that holds it -- T4 (15 GiB, $0.53/h), L4 (22 GiB, $0.98/h), A10G (22 GiB, $1.21/h), L40S (44 GiB, $2.24/h), 4xL4 (88 GiB, $4.60/h), 8xT4 (120 GiB, $7.82/h), 4xL40S (176 GiB, $10.49/h) -- and a GPU pod comes with its host memory and cores. A multi-GPU machine only helps code that spreads its model over every visible GPU. A GPU task given no GPU fails at start; a GPU given to a CPU task is paid for the whole run.
