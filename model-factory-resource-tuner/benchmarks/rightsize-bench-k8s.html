Abstract

Before a batch task runs, a scheduler must request its memory, its CPU cores, and whether it needs a GPU and which machine. Requests that are too small fail or slow the task; requests that are too large waste the cluster. We present RightSize Bench, which scores approaches to this decision by the dollars it takes to get each run to completion, against the cheapest request that would have worked. The bench measures 32,082 runs of 33 families of real Python task code (dataframes, SQL, linear algebra, classical ML, PyTorch training and inference, sharded language models) in Kubernetes pods, across a CPU grid and a ladder of seven GPU machine shapes. This release gives every run a Kubernetes twin: the same code as a plain module in a Job manifest, with its inputs staged one of four ways. The twin's labels are derived from the Flyte measurement by an accounting of what differs between the containers; on 176 runs re-measured as Jobs, 100% fall within one memory cell. The re-measurement also shows that the standard ru_maxrss instrument inherits the measuring parent's peak, a floor in every label of this kind.

We compare a static request, hand-written rules, quantile gradient-boosted trees, a zero-shot 27B language model, a Qwen3-1.7B model with pointer decision heads trained by cross-entropy and then by group-relative policy optimization against the bench's own cost, logarithmic opinion pools of the trees with each language model, and a label-free novelty gate that routes each run to the pooled or the RL model by its distance to the training runs. Trained on both platforms, every decoded approach's regret on Jobs is within 3 points of its regret on Flyte tasks, and the decision model moves its memory request with the single manifest line that charges staged bytes to memory. A model trained on Flyte alone does not transfer. The gate scores 6.9% regret on 10,190 test rows and 36.8% on 12,832 rows from held-out task families, matching the best single approach on each split, on two independent trainings. Its detector separates held-out families almost perfectly only because they import libraries the training families do not; on numeric features alone its AUROC is 0.67.

1 Introduction

Every task submitted to a Kubernetes cluster carries a resource request. Memory is a hard limit: a container that exceeds it is OOM-killed and must be retried. CPU is a soft limit: a container that exceeds it is throttled and finishes late. A GPU is a discrete choice of machine: too small and the task fails with a CUDA out-of-memory error, absent and a GPU task fails at start, present and a CPU task pays for an accelerator it never uses. Engineers set these numbers by hand, usually once, usually generously. Autoscalers that learn from history help with long-running services, but a batch task's first run has no history, and its later runs differ in input size.

The information that decides the right request is mostly available before the task runs: the code, the sizes and formats of its inputs, and what earlier runs of the same task used. This paper asks how well different approaches turn that information into a request, measured in money.

2 Related work

Autoscaling from history. Google's Autopilot sets container limits from the usage history of a job's tasks, with ML recommenders over moving windows [1]. Kubernetes' Vertical Pod Autoscaler recommends requests from a decaying histogram of observed usage [2]. Borg reports that most jobs over-request [3]. These systems size services that run long enough to observe; a batch task's first run has no history, and RightSize Bench reports first runs and runs with history separately. Quasar [4] classifies new workloads from short profiling runs; RightSize Bench allows no profiling, only what a scheduler can read before the run.

Learned predictors. Quantile regression [5] with gradient-boosted trees [6] is a standard way to predict a distribution of resource need, and is the strongest classical approach here. Language models have been applied to reading code; we compare a zero-shot model with fine-tuned ones whose language-model head is replaced by a pointer head that scores option tokens in the prompt [7], adapted with LoRA [8] on Qwen3 [9].

Training on the objective. Group-relative policy optimization [10] removes the value network from PPO by normalizing rewards within a group of samples for the same prompt. Because the decision model's policy is three categorical distributions, groups are sampled from one forward pass, and the reward is the benchmark's own cost simulator.

Combining models. Logarithmic opinion pools [11] combine calibrated distributions by a weighted geometric mean. Temperature scaling [12] calibrates each model before pooling and decoding. Distance to the k nearest training points in a feature space is a standard out-of-distribution signal [13]; the gate uses it to choose between two models.

3 Problem

A run is one execution of a task on one set of inputs. Before it starts, an approach sees three things and nothing else:

  • the task's code: a Flyte task module, or a Kubernetes Job's job.py and manifest (§5);
  • the metadata a scheduler could read about this run's inputs: bytes on disk, format, and whatever the format's header exposes (rows and schema for parquet, shape and dtype for npy, header for CSV, first record's keys for JSONL);
  • the measurements of earlier runs of the same task: peak memory, peak and mean cores, peak GPU memory and utilization, wall time, and their inputs' metadata.

It never sees the task's family, the knobs it was generated with, which corpus it came from, or anything measured on the run itself. A unit test pins this boundary for every feature and prompt field. From this, the approach outputs a request on three axes:

4.1 Families, tasks and runs

A family is a Python generator that, given a random seed, writes a task function and its input specifications, and draws hidden knobs: code-level choices that decide how input bytes become resource use. A pandas family chooses whether to project columns, which dtype backend to use, and whether to downcast; a training family chooses width, depth, batch size, mixed precision and checkpointing; a CPU family chooses a thread-pool size, or whether to set one at all. The knobs appear only in the code the approach reads. They are never given to an approach, and are kept only for slicing results.

  • Task. One sampled instance, with id family-sha1(seed)[:10]. Its code is rendered as a Flyte task with no resources declared: the request is exactly what is missing.
  • Runs. Each run rescales the leading dimension of the task's inputs (rows, or the first axis of an array) by a size factor drawn log-uniform: [0.25, 4] for RightSizeMem, [0.5, 2] for the CPU and GPU corpora. Run order is shuffled, so history can be larger or smaller than the current run. A task's runs share code, knobs and time budget, and differ only in size and data seed.
  • Inputs. Synthetic data written by a separate process: standard-normal floats, uniform integers, dictionary-encoded categories, random lowercase strings, Zipf(1.3) word ids over a 30k vocabulary for text, uniform uint8 for images; as parquet, CSV, JSONL or npy, as the family declares.
  • Time budgets. CPU and GPU workloads loop until a per-task TIME_BUDGET_S is spent: 30, 45 or 60 s for RightSizeCPU big-1, and 45, 60 or 90 s for RightSizeGPU big-2. A training loop reaches its peak memory in its first steps. RightSizeMem workloads run to completion.

4.2 RightSizeMem v2: peak memory

Twelve families that turn input bytes into memory in different ways: pandas group-bys and joins (with a join fan-out knob), polars eager/lazy/streaming pipelines, DuckDB queries with an optional memory_limit, chunked CSV and JSONL readers, NumPy linear algebra (optionally memory-mapped), scikit-learn estimators, TF-IDF (sparse, densified or reduced), a CPU PyTorch MLP with an embedding table, image batches, and pure-Python grouping. Each family is labelled by its memory driver: code (the code decides; input size barely matters) for polars, DuckDB and chunked CSV, both for the rest. Held out: duckdb_sql, image_batch.

Process model
Three processes per run: a child writes the inputs to a temporary directory; a fresh python interpreter executes the task body on local paths; the parent reads the child's ru_maxrss and CPU time from os.wait4. A sampler thread reads VmRSS every 20 ms to time the peak (t_peak_frac, the fraction of the run before 90% of the peak) and to enforce the guard. BLAS and OpenMP threads are set to 1; workloads set their own threads, up to 3, in code.
Pods
Pass 1: 240 shards of 60 runs on spot c5.4xlarge nodes (12 CPU / 24 Gi pods, 4 workloads at once, a 5,376 MiB per-process guard, 900 s timeout). Pass 2: runs that hit the guard re-run one at a time on on-demand 3 CPU / 24 Gi pods with a 20,480 MiB guard. 71.6 pod-hours in all; 166 runs exceeded 20 GiB or timed out and are censored.
Label
need = (peak + 180 MiB) × 1.05. The 180 MiB is the Flyte runtime's footprint, measured by a probe; 1.05 is headroom. The memory label is the smallest cell ≥ need. The CPU label for these rows is the cell covering mean cores (CPU time ÷ wall time): this corpus has no per-second series.

4.3 RightSizeCPU big-1: the busiest 15 seconds

Eleven families chosen for how they use cores, because CPU need is decided by parallelism, not input size: NumPy BLAS with or without a thread cap, polars and DuckDB with explicit thread settings, scikit-learn ensembles whose n_jobs can be capped by the tree count, serial pandas, a Python thread pool that either holds the GIL (pure Python) or releases it (zlib, hashlib, NumPy), a process pool whose chunk count can cap it, a CPU PyTorch MLP, pyarrow CSV with set_cpu_count, an I/O-bound thread pool that mostly sleeps, and a two-phase task (pure-Python cleanup for 20–80% of the budget, then a BLAS Gram matrix). Pool sizes are drawn from 1–6 (I/O pools 1–16), or left unset. Held out: duckdb_sql, pyarrow_csv.

Measurement
Each run in a fresh interpreter; process-tree CPU time (psutil, keeping exited children) read every second and interpolated onto a 1 s grid, cross-checked against wait4's CPU time. Pods of 15 CPU / 24 Gi on spot c5.4xlarge nodes run two slots of 7 disjoint cores pinned with sched_setaffinity, 8 runs per shard. A paired check on 44 runs (pinned pairs vs one run per pod, read from the cgroup) put all 44 within ±25% and 43 in the same cell, median ratio 1.000.
Label
The busiest 15-second sliding mean of the per-second series, the resolution at which the platform's monitoring (Prometheus scraping cAdvisor every 15 s) sees a container. The CPU label is the smallest cell ≥ that peak. Peak memory is measured as in RightSizeMem. All 9,900 runs were usable; median 2.08 peak cores (p10–p90 1.0–5.0), median run 45.6 s, a task's two runs agree to a median 0.46%. Measured in 17.6 h on 4–9 pods.

4.4 RightSizeGPU big-2: peak GPU memory across the machine ladder

Ten PyTorch families: a tabular MLP, a CNN classifier, a GPT language model, a transformer encoder for embeddings (optionally keeping outputs on the device), a two-tower recommender whose embedding tables shard by row over every GPU, a DataLoader-bound CNN, blocked GEMM, k-nearest-neighbour search, fine-tuning of 0.6–7B-parameter decoders sharded by layer across GPUs, and KV-cached generation from 16–48-layer fp16 decoders. Three families shard over every visible GPU (lm_finetune, llm_generate, recsys_train). Held out: recsys_train, knn_search, llm_generate.

Measurement
NVML memory.used and utilization.gpu on every visible GPU every 0.5 s (the counters behind DCGM's framebuffer and utilization metrics). Peak is the single-GPU equivalent: per-GPU peaks summed, minus a 0.5 GiB CUDA context for each extra GPU used. Imbalance = (busiest GPU − context) × k ÷ total, floored at 1.
The ladder climb
Every run starts on a T4 (6 runs per shard). Single-GPU code that runs out of memory moves to one GPU of a 4×L4 node, then of a 4×L40S node, falling back to single-L40S pods after an hour in the queue. Sharded code moves to an 8×T4 node spread over all 8, then a 4×L40S node over all 4. A run that is out of memory on the largest shape it reached is censored. Multi-GPU capacity mostly did not come: all 118 4×L4 shards and 229 of 459 8×T4 shards timed out in the queue, and 4×L40S scheduled 6 of 497 shards. 1,569 runs are censored, 1,001 of them sharded.
Label and fit model
The oracle machine is the cheapest shape the run fits. On a shape it was not measured on, fit is modelled: single-GPU code fits if its whole peak fits one GPU; sharded code on n GPUs fits if (peak − 0.5) × max(imbalance, 1) ÷ n + 0.5 GiB fits each GPU, with imbalance 1.25 when it was measured on one GPU. The GPU label is the smallest cell that lands on the oracle's shape, which for sharded code can be larger than the raw peak. Of the usable runs, 74.7% fit a T4, 6.5% an L4, 14.9% an L40S, 2.6% a 4×L4, 0.9% an 8×T4.

4.5 Splits

Splits are by task, never by run: a hash of the task id sends 70% of a family's tasks to train, 10% to validation and 20% to test. Held-out families go entirely to the unseen split; no task of theirs is in train or validation. Test therefore measures generalization to new tasks of familiar families (new knobs, new sizes), and unseen measures generalization to new code. 5 Kubernetes twins

The workload code was written for Flyte, but nothing in its body depends on Flyte. The twin keeps the body line for line and changes only its edges: File parameters become paths, the flyte import goes, and a __main__ stages the inputs, calls the function, writes result.json and uploads it. A batch/v1 Job manifest carries the image, the input URIs, the single-thread floor the measurement used, the staging volume, and an empty resources block.

Flyte task (as measured)
import flyte
from flyte.io import File
import pandas as pd

env = flyte.TaskEnvironment(name="pandas-join", image=flyte.Image.from_debian_base().with_pip_packages("pandas", "pyarrow"))


@env.task
async def join_orders_catalog(orders: File, catalog: File) -> dict:
    orders_path = await orders.download()
    catalog_path = await catalog.download()
    orders = pd.read_parquet(orders_path)
    catalog = pd.read_parquet(catalog_path)
    joined = orders.merge(catalog, on="sku", how="inner")
    joined["revenue"] = joined["qty"] * joined["price"]
    by_brand = joined.groupby("brand", observed=True)["revenue"].sum()
    return {"rows": int(len(joined)), "brands": int(len(by_brand))}

  • No Flyte runtime. A Flyte task's container also holds the Flyte runtime; a plain python job.py does not.
  • tmpfs is memory. A file on a memory-backed emptyDir is charged to the container's memory cgroup as shmem, byte for byte, and counts toward its OOM limit. On node disk the same file is page cache, which the kernel reclaims before it OOM-kills; the measured workloads already read local files, so disk staging adds nothing.
  • boto3. The client adds 48 MiB to a workload's peak, and its download runs inside the job, where on a light job it can be the busiest 15 seconds.
  • History in container units. A twin's earlier runs report the container's own peaks, as cAdvisor would; a Flyte run's history reports the peak plus the runtime, as Flyte's UI would.

5.3 Validation

Finding: ru_maxrss includes the parent's peak

The RightSize corpora measure a child's peak with ru_maxrss from os.wait4. On Linux this value includes the parent's high-water mark at the moment the child calls exec: exec_mmap folds the old memory map's hiwater into the child's signal->maxrss, and under fork or vfork the old map is the parent's. In the probe every child reported 228–490 MiB, the probe's own peak at the time, against its own VmHWM of 74–80 MiB. Of the 176 re-measured corpus runs, 27% read more than 5% high (RightSizeCPU 39%, RightSizeMem 17%), almost all at 157–161 MiB, the measuring parent's peak, against own peaks of 12–160 MiB. With the Flyte label's 180 MiB runtime added, this moves 13 of the 176 labels up one cell (and one down). It moves no K8s label: floor and own peak both fall in the bottom cell. The published labels are left unchanged, and the smallest Flyte workloads' memory labels are conservative by up to one cell. The validation measures each child's own VmHWM (an atexit hook) and the container cgroup's anon + shmem peak instead.

6 Cost model and metrics

The cost of a request is the dollars it takes to get the run to SUCCEEDED, including failed attempts, retries and lateness, simulated from the run's measurements. Each axis fails the way it fails in production:

CPU pod price      p(m, c) = $0.192/h × max(c ÷ 4, GiB(m) ÷ 16)        dominant share of an m6i.xlarge (4 vCPU, 16 GiB)
GPU pod price      p(g)    = on-demand price of the cheapest shape holding cell g   (host memory and cores included)
attempt overhead   0.02 h per attempt                                    image pull, start, input read

memory m < need    OOM-kill at t_peak of the run; pay p · (t_peak · T + 0.02); retry with 2 × memory      (≤ 8 attempts)
cpu c < series     throttle: each second at u cores takes max(1, u ÷ c) seconds; T' = Σ max(1, u_s ÷ c)
                   (RightSizeMem rows: T' = T · max(1, mean ÷ c))
gpu g too small    CUDA OOM at t_peak; retry on the next shape up that fits (fit model, §4.4)
gpu none, GPU task fails at CUDA init after 0.05 h; the platform retries on a T4
gpu, CPU task      runs, at the GPU shape's price for the whole run

cost   = Σ attempts + 1.0 × oracle cost × (attempts − 1) + 1.0 × oracle hourly price × (hours late)
oracle = (label_mem, label_cpu, no GPU) for a CPU task; (label_gpu) for a GPU task

Part II · Methods

7 Approaches

Every approach makes the whole request for every run. Every tunable setting is chosen on the validation split by mean regret.

7.1 Static request and rules

static
One request for every run: a training quantile (0.5, 0.75, 0.9 or 0.95) of memory need and of CPU need, and no GPU. Tuned: the 0.9 quantile for memory, the median for CPU. Every GPU task fails at start and is retried on a T4.
rules
What a platform team would write. GPU if the code contains "cuda", torch.cuda, .to(device) or device =, sized from the task's largest past GPU peak × a margin, or a training quantile of GPU peaks on a first run. Memory: the largest past peak, in the platform's units, × a margin, or the static cell. CPU: the largest past peak cores × a margin; on a first run, the largest pool size the code declares (max_workers=, n_jobs=, set_num_threads, …), else 1. Tuned: margins 1.5 / 1.0 / 1.0 for memory / CPU / GPU, the median GPU peak for first runs.

7.2 Gradient-boosted trees (gbt-dist)

Features
209 scheduler-visible features: 27 from the inputs and history (log total bytes, bytes by format, visible rows, column counts by dtype, array shape; number of earlier runs, their largest peak memory, cores, GPU peak and utilization, and the peak of the earlier run closest in size, scaled by the size ratio), 173 code features written for the three single-axis benches (presence of API tokens such as groupby, TfidfVectorizer, ProcessPoolExecutor, checkpoint; numeric literals such as declared pool sizes, layer widths and batch sizes), 4 CUDA flags, and 5 Job flags (kind: Job, initContainers, medium: Memory, import boto3, download_file).
Model
Per axis, 19 HistGradientBoostingRegressor quantile models (τ = 0.05, 0.10, …, 0.95; pinball loss; 300 rounds; learning rate 0.06; 31 leaves) on log₂ of the need. Memory and CPU models train on CPU-task rows, GPU models on GPU-task rows. A HistGradientBoostingClassifier (300 rounds, learning rate 0.06) predicts whether the task needs a GPU.
Distribution
The 19 predicted quantiles, made monotone, define a piecewise-linear CDF of log₂ need through (q̂_τ, τ), closed with tails 1.5 doublings beyond the outermost quantiles. Each cell's probability is the CDF mass between its edges. GPU: P(none) = 1 − P(needs GPU), the rest spread over the GPU cells.

7.3 Zero-shot 27B

Qwen 27B served by vLLM, given the prompt of Appendix B and asked for JSON, at temperature 0 with up to 1,024 tokens. The last JSON object with a usable memory value is parsed and each value is rounded up onto its grid; a missing CPU is 1 core and a missing GPU none. Unparseable answers fall back to 4Gi, 1 core and no GPU. Scored on a family-stratified sample of 150 Flyte runs per split and their twins (260 test and 300 unseen rows). On this release, 444 of its 560 answers were unparseable, against 82 of 586 in the previous release with a Flyte-only prompt; its row mostly measures the fallback, and the cause has not been investigated.

7.5 Decoding a distribution into a request

The trees, every decision model and every pool end with a distribution over each axis. Two read-outs are reported for each:

  • argmax: the most likely cell on each axis.
  • decoded (cost-aware): GPU first: no GPU if P(none) ≥ θ, with θ tuned on validation over {0.3, 0.5, 0.7, 0.8, 0.9, 0.95, 0.98}; otherwise the GPU cell most likely to be within margin of the peak under P(gpu | some GPU). Memory: the Bayes cell argmin_m Σ_j C[m, j] · P(j), where C[m, j] is the memory GiB-hours, OOM retries and an OOM penalty included, of requesting cell m for a run that needs cell j. CPU: the cell with the highest probability of landing within ±25% of the busiest window, argmax_m Σ_j H[m, j] · P(j), ties to the larger cell.

Bayes decoding leans toward over-asking memory, because an OOM costs a retry; argmax ignores that asymmetry.

7.6 RL: training on the cost itself

Imitating the label cannot see two things the cost model cares about: the axes interact (on a GPU node memory and CPU are free; on a CPU node a GPU is the most expensive mistake there is), and asking low costs more than asking high by an amount the label does not carry. 7.7 Pooling the trees with a language model

The trees and the language models fail differently: the trees read numbers exactly but have no feature for code they have not seen; the language models read code but read numbers as tokens. A logarithmic opinion pool combines their calibrated distributions on each axis:

p_pool(j) ∝ p_trees(j)^w · p_LM(j)^(1−w)            on each axis, renormalized; one w shared by the three axes
(w, θ) = argmin over w ∈ {0, 0.1, …, 1} × θ ∈ {0.3, …, 0.98} of validation regret (decoded)
then read out decoded (with θ) and by argmax

Where both models put mass, the pool does too; where either gives a cell almost none, the pool does not pick it. Nothing is retrained. Tuned weights on the trees: w = 0.5 for the decision model, 0.6 for the RL model, 0.6 for the Flyte-only model, all with θ = 0.3.

7.8 The novelty gate

The pooled RL model, read by argmax, is the best approach on familiar code and among the worst on new code; the RL model alone is the reverse (§9). The gate routes each run to one of them by how far it lies from the training runs.

7.9 The Flyte → Kubernetes adapter

A customer whose history is all Flyte has no Job runs to train on. The adapter moves a Flyte-trained model's memory distribution through the twin's accounting, reading only what a scheduler sees: the manifest's volume medium, import boto3 in the job, and the input sizes.

for each memory cell j with probability p_j:
    n_j   = geometric middle of cell j's interval              a representative need
    n'_j  = (n_j ÷ 1.05 − 180 + 48·[boto3] + B·[tmpfs]) × 1.05

CPU and GPU: the model's own distributions on the Job's prompt

Two earlier versions also moved the CPU distribution (by the boto3 download window) and took CPU and GPU from the rendition; both did worse than the model's own reading (rt-k8sgate-1, -2), so the adapter moves memory only.

Why the detector is perfect here

Six of the seven unseen families import a library no training family imports. Each such import is a code-token feature that is constant on train, so after standardization any run that has it sits far outside the training cloud. 10 Discussion

  • Kubernetes Jobs can be benchmarked from Flyte measurements. The accounting is exact where it can be checked (tmpfs, init containers) and calibrated where it cannot (boto3), and every derived label lands within one cell of a re-measurement.
  • One model, trained on both platforms, sizes both, and reads the one manifest line that changes the memory need. Hand-written rules cannot until the task has run.
  • Accuracy on the label and cost diverge. The adapter raises memory accuracy and raises cost; RL lowers accuracy and lowers test cost; Bayes decoding over-asks on purpose. A benchmark of this decision has to score money, not cells.
  • Familiar and new code want different models. Pooling with the trees helps most on familiar code and hurts most on new code, because the pool's weight is tuned on familiar families. Routing by novelty recovers the best of both on this bench. How far that carries depends on the detector, which here has an easy job.
  • Next: a family-held-out validation split, so that the pool weight, the gate threshold and the detector are tuned on families the approaches have not seen; unseen families built from familiar libraries; and a seed sweep.

11 Limitations

  • Synthetic workloads. Real libraries and real code paths, but generated tasks, random data and short runs (seconds to minutes). RightSizeCPU runs are 30–60 s, two to four monitoring windows.
  • Few unseen families. Seven across three corpora, chosen by hand, and six of them introduce a library no training family uses.
  • Feature and generator authorship. The tree features and the code rules were written by the people who wrote the generators.
  • Truncated memory range. RightSizeMem runs above 20 GiB are censored, so memory labels stop at the 24Gi cell.
  • GPU top end. 1,569 GPU runs are censored, concentrated where multi-GPU nodes never scheduled; fit on unmeasured shapes is modelled with a default imbalance of 1.25; single-GPU runs past a T4 were measured on an L40S, not an L4.
  • Measurement. Flyte memory labels carry the ru_maxrss floor (§5.3). RightSizeCPU big-1 used process-tree CPU time in shared pods, validated against the cgroup on 44 runs. Process-pool peaks are the largest single process's, not the sum. RightSizeMem rows have no CPU series; their throttling uses mean cores.
  • The twin is derived, not measured. Validated on 176 RightSizeMem and RightSizeCPU runs; GPU twins were not re-measured. Four stagings by hash; CSI drivers, sidecars and other init work are not modelled. boto3's cost is one version on one node type.
  • Cost model. List prices; no spot discounts or bin-packing; OOM priced as one retry at double; delay at one oracle cost per retry and one oracle hourly price per hour late. The oracle is the label, not the cost minimum.
  • Two trainings, not a seed sweep. Unseen-family regret moves by up to 25 points between them for some approaches.
  • Zero-shot 27B is scored on about 280 rows per split, and 79% of its answers were unparseable on this release.

12 Conclusion

RightSize Bench measures the request a scheduler makes before a task runs, in dollars, over 33 families of real task code and, with this release, over each task's Kubernetes twin. A 1.7B decision model trained on both platforms sizes both and reads the staging from the manifest; a model trained on one platform does not transfer, and a label-level adapter does not fix that. Pooling with gradient-boosted trees wins on familiar code and loses on new code, RL against the cost wins on new code, and a label-free novelty gate gets the best of each on this bench. The open question is the gate's detector on new code that looks familiar.

        def __init__(self, d, **kw):
            super().__init__()
            self.ln1, self.ln2 = torch.nn.LayerNorm(d, **kw), torch.nn.LayerNorm(d, **kw)
            self.qkv, self.proj = torch.nn.Linear(d, 3 * d, **kw), torch.nn.Linear(d, d, **kw)

            self.h = d // 128

            q, k, v = self.qkv(self.ln1(x)).view(b, s, 3, self.h, d // self.h).permute(2, 0, 3, 1, 4)

        """An embedding table split by row over every GPU: row r lives on GPUS[r % n]."""
        def __init__(self, rows, dim, sparse):
            super().__init__()
            n = len(GPUS)
            self.parts = torch.nn.ModuleList(
                [torch.nn.Embedding(-(-rows // n), dim, sparse=sparse, device=g) for g in GPUS])
        def forward(self, idx):
            n, out = len(GPUS), None
            for j, (g, part) in enumerate(zip(GPUS, self.parts)):
                mask = idx % n == j
                rows = part((idx[mask] // n).to(g)).to(GPUS[0])

The prompt every language-model approach reads, here for an init-tmpfs twin of the pandas join in Figure 1. The history values are illustrative; the structure is exact. A Flyte row shows the task module instead of job.py and the manifest, and reports history peaks with the Flyte runtime included.

system
You size batch jobs before they run: Flyte tasks, or Kubernetes Jobs given as a Python module and its manifest. Given the code, the metadata of this run's inputs, and what earlier runs of the same job used, choose the cheapest request that runs it: memory, CPU cores, and a GPU or none. Memory is a hard limit: below the peak the container is OOM-killed and retried with double. A Flyte task's memory includes the Flyte runtime; a Kubernetes container's includes whatever the job loads to fetch its inputs, and files written to a memory-backed emptyDir (medium: Memory) are charged to it. CPU below the busiest 15 seconds' use throttles the task and it finishes late. Thread pools the code does not size get one thread. gpu is the peak GPU memory to provision, or none for a task that does not use CUDA; it lands on the cheapest machine that holds it -- T4 (15 GiB, $0.53/h), L4 (22 GiB, $0.98/h), A10G (22 GiB, $1.21/h), L40S (44 GiB, $2.24/h), 4xL4 (88 GiB, $4.60/h), 8xT4 (120 GiB, $7.82/h), 4xL40S (176 GiB, $10.49/h) -- and a GPU pod comes with its host memory and cores. A multi-GPU machine only helps code that spreads its model over every visible GPU. A GPU task given no GPU fails at start; a GPU given to a CPU task is paid for the whole run.

import pandas as pd
import json
import os
import sys


def join_orders_catalog(orders_path: str, catalog_path: str) -> dict:
    orders = pd.read_parquet(orders_path)
    catalog = pd.read_parquet(catalog_path)
    joined = orders.merge(catalog, on="sku", how="inner")
    joined["revenue"] = joined["qty"] * joined["price"]
    by_brand = joined.groupby("brand", observed=True)["revenue"].sum()
    return {"rows": int(len(joined)), "brands": int(len(by_brand))}


if __name__ == "__main__":
    result = join_orders_catalog(sys.argv[1], sys.argv[2])
    os.makedirs("/data/out", exist_ok=True)
    with open("/data/out/result.json", "w") as f:
        json.dump(result, f)
