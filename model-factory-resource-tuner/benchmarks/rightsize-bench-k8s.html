Abstract

Before a batch pod runs on Kubernetes, someone has to decide how much memory and CPU it gets, and whether it gets a GPU. Too little makes it fail or run slowly, and too much wastes the cluster. We present RightSize Bench, which scores approaches to this decision by the dollars it takes to get each run to finish, compared with the cheapest request that would have worked. The benchmark contains 32,082 measured runs of 33 families of generated Python tasks that use real libraries, from dataframes and SQL to PyTorch training and sharded language models. Each run appears twice, once as a raw Kubernetes Job, with its inputs staged in one of four ways, and once as a task submitted through Flyte, an AI-native interface to Kubernetes that adds typed I/O, caching, retries and durable execution at a measured cost of about 70 MiB per pod. We validated the labels in about 480 real pods, which exposed and fixed two errors in our first release.

We compare static requests, two kinds of rules, gradient-boosted trees, a zero-shot 27B model, a fine-tuned 1.7B decision model further trained with reinforcement learning against the cost, opinion pools that combine the trees with each language model, and a pre-registered novelty gate, over three independent trainings. On new tasks from familiar families, the pool of trees and the decision model has 6.6% mean regret on Job pods [5.6, 7.6] (dollar regret 27.6%). On held-out families, the RL model and a rule that scales by input size and reads the manifest tie at 39%. When an out-of-memory failure costs as much as resubmitting a Job by hand, that rule is the best approach on new code. Models trained on Jobs read the manifest: when only the volume medium changes, they move their request the right way about three times in four. Adding Flyte data does not improve them on Jobs, and a model trained only on Flyte tasks transfers poorly to Jobs.

1  Introduction

Every container that runs on Kubernetes asks for resources before it starts [13]. The numbers matter in different ways. Memory is a hard limit, so a container that uses more than it asked for is killed and has to be run again. CPU is a soft limit, so a container that wants more cores than it was given is throttled and finishes late. A GPU is a choice of machine: if it is too small the task runs out of device memory, if it is missing a GPU task fails at start, and if a CPU task gets one it pays for hardware it never uses. In practice engineers pick these numbers by hand, usually once and usually generously, and large clusters run well below what their jobs reserve [22, 21].

Autoscalers that learn from usage history [18, 15] work well for long-running services. Batch work is harder. The first run of a batch task has no history, and later runs often see inputs of a different size. Still, much of what decides the right request is known before the pod starts. A scheduler can read the code the pod will run, the size and format of its inputs, the way the pod spec stages those inputs, and what earlier runs of the same task used. This paper asks how well different approaches turn that information into a request, and measures the answer in dollars.

We treat the Kubernetes pod as the unit of work throughout. Teams submit pods in different ways. The most direct is a batch/v1 Job, which pairs a container image with a manifest. Another is to write a typed Python function and let an orchestrator build the pod. We use Flyte [5] as the example of the second route. Flyte acts as an AI-native interface to Kubernetes: it turns a function into a pod, and adds typed inputs and outputs, caching, retries and durable execution along the way. In both cases the same user code runs in the same kind of pod. The differences are at the edges of the pod, in how inputs arrive, what else shares the container, and what the monitoring history reports. For Flyte, those conveniences cost 55–70 MiB of runtime memory in the task’s container, which we measure directly (Section 7).

This paper makes five contributions.

  1. We build a benchmark of the whole pod request from 32,082 measured runs of 33 families of generated Python tasks, covering dataframes, SQL, linear algebra, classical ML, PyTorch training and inference, and sharded language models. Each run has measured peak memory, CPU use at the 15-second resolution of cluster monitoring, and peak GPU memory across seven machine shapes (Section 5).

  2. We present every run both as a raw Kubernetes Job and as a Flyte task. The Job stages its inputs in one of four ways, and its labels follow from an explicit accounting of what differs between the two pods (Section 6).

  3. We check that accounting in about 480 real pods, reading each container’s own cgroup counters (Section 7). The check found two defects in our first release, both now fixed. The Flyte runtime constant was 2.6 times too large, and some init containers were too small to hold the inputs they staged. It also showed that the standard ru_maxrss measurement leaves about a third of labels one cell higher than necessary.

  4. We score requests with a single cost model that covers memory, CPU and GPU together, and report both mean and dollar-weighted regret with task-clustered confidence intervals (Section 8).

  5. We compare eleven kinds of approach over three independent trainings, from static requests and hand-written rules to gradient-boosted trees, a zero-shot 27B model, a fine-tuned 1.7B decision model trained further with reinforcement learning, opinion pools, and a pre-registered novelty gate (Sections 9 and 11). Two controlled tests ask what the models actually read. One changes only the manifest, and the other removes the task’s name from its code.

2  Background: one pod, two ways to submit it

Requests, limits and cgroups. Each Kubernetes container declares a memory and CPU request, which the scheduler reserves on a node, and a limit, which the kubelet enforces through the container’s cgroup [13, 9]. Under cgroup v2, a container whose charged memory reaches its limit is OOM-killed. Both anonymous memory and shared memory (shmem) count toward that limit, while clean page cache does not, because the kernel can reclaim it first. A CPU limit works differently. It is enforced as a CFS quota, so a container that exceeds it is slowed down rather than killed. Accelerators are requested as whole devices on node pools that carry them. In this paper a request also sets the limit, which is the usual choice for batch pods because it makes scheduling and failures predictable.

How the pod spec changes a task’s memory. Three details of a pod spec can change how much memory a batch task needs without any change to its code. The first is the medium of the volume that holds its inputs. An emptyDir on node disk keeps files as page cache, which the kernel reclaims under pressure. An emptyDir with medium: Memory is a tmpfs, and every byte written to it is charged to memory as shmem [14]. Staging a 2 GiB input on tmpfs therefore adds 2 GiB to the pod’s need. The second detail is who fetches the inputs. An init container runs to completion before the main container starts and has its own limit, whereas a download inside the job runs in the job’s container, so the client library’s memory and threads count against the job. The third is anything else that shares the container, such as an orchestration runtime or a client library.

There is one subtlety with tmpfs. A page is charged to the cgroup of the container that writes it, so pages written by an init container are not charged to the main container. When the init container exits, though, its pages move to the pod’s cgroup and still count against the pod’s overall limit. We confirm this in real pods in Section 7.

Raw Jobs. A batch/v1 Job runs a pod template until it succeeds. Its backoffLimit says how many failed pods it will replace before giving up. Batch teams often set it to zero and resubmit failures by hand or from an outer scheduler. A Job has to stage its own inputs, either with an init container or in the job’s code.

Flyte as an interface to Kubernetes. Flyte [5] turns a typed Python function into a Kubernetes pod. A user writes @env.task async def f(x: File) -> dict, and Flyte builds the image, renders the pod spec, moves typed inputs and outputs through object storage, caches results by their inputs, retries failed attempts, and records each execution so that a long pipeline can resume after a node is lost. None of this changes what the function does inside the container. It changes the pod’s edges instead. Inputs arrive through Flyte’s own download, the container also runs Flyte’s runtime, and the execution history reports the container’s peak with that runtime included. We measure the runtime at 55 MiB at rest, and a median 70 MiB above the same workload run as a plain Job (Section 7).

For resource sizing, then, Flyte is a convenience layer over the same pod. It costs a little memory in exchange for typed I/O, caching, retries and durable execution. An approach that can size a Kubernetes pod should be able to size a Flyte task using the same knowledge plus the runtime.

3  Related work

Sizing from history. Autopilot [18] sets Google’s container limits from the usage history of a job’s tasks, using moving-window and ML recommenders. Kubernetes’ Vertical Pod Autoscaler [15] recommends requests from a decaying histogram of observed usage. Borg traces show that most jobs over-request [22, 21]. Resource Central [1] predicts VM utilization from a subscription’s history. All of these size workloads that have run before, and run long enough to observe. RightSize Bench reports first runs (no history) and runs with history separately. Quasar [2] classifies new workloads from short profiling runs; RightSize Bench allows no profiling, only what a scheduler can read before the pod starts.

Learned predictors. Quantile regression [12] with gradient-boosted trees [6, 11] is a standard way to predict a distribution of resource need, and is the strongest classical approach here. Our decision model replaces a language model’s output layer with a pointer head [23] that scores option tokens written in the prompt. It is adapted with LoRA [10] on Qwen3 [17].

Training on the objective. Group-relative policy optimization (GRPO) [19] drops PPO’s value network by normalizing rewards within a group of samples for the same prompt. Our policy is three categorical distributions, so a group is sampled from one forward pass, and the reward is the benchmark’s own cost simulator.

Combining and routing models. Logarithmic opinion pools [7] combine calibrated distributions by a weighted geometric mean. Temperature scaling [8] calibrates each model before pooling. Distance to the kk nearest training points is a standard out-of-distribution signal [20]; our gate uses it to choose between two models.

4  Problem

A run is one execution of a task on one set of inputs, in one pod. Before the pod starts, an approach may look at three things. The first is the task’s code as it was submitted: for a raw Job that means job.py and the Job manifest, and for a Flyte task it means the task module (Section 6). The second is the metadata a scheduler can read about this run’s inputs, namely their sizes and formats and whatever the format’s header exposes, such as the row count and schema of a Parquet file or the shape and dtype of a .npy array. The third is what earlier runs of the same task used: their peak memory, peak and mean cores, peak GPU memory and utilization, wall time and input sizes. These are reported the way the platform’s monitoring would show them, which means the container’s own peak for a Job and the peak including the runtime for a Flyte task.

An approach never sees the task’s family, the hidden settings it was generated with, which corpus it came from, or anything measured on the run itself. A unit test enforces this for every feature and every field of the prompt. From what it can see, the approach chooses a request on three axes (Table 1). A GPU request lands on the cheapest machine that can hold it (Table 2). On a GPU node the host memory and cores come with the instance, so they are not scored.

5.1  Families, tasks and runs

A family is a Python generator. Given a seed, it writes a task function and the specification of its inputs, and it draws a few hidden settings, which we call knobs, that decide how input bytes turn into resource use. A pandas family, for example, decides whether to project columns, which dtype backend to use and whether to downcast floats. A training family picks width, depth, batch size, mixed precision and checkpointing, and a CPU family picks a thread-pool size or leaves it unset. The knobs show up only in the code an approach reads. They are never given to an approach directly, and we keep them only to slice the results.

Each run scales the leading dimension of the task’s inputs by a factor drawn log-uniformly from [0.25,4][0.25, 4] for RightSizeMem and from [0.5,2][0.5, 2] for the CPU and GPU corpora. Runs are shuffled, so a task’s history can be larger or smaller than the current run. The inputs are synthetic: normal floats, uniform integers, dictionary-encoded categories, random strings, Zipf-distributed word ids for text, and random bytes for images, written as Parquet, CSV, JSONL or .npy. CPU and GPU workloads loop until a per-task time budget runs out (30–60 s for CPU and 45–90 s for GPU), while RightSizeMem workloads run to completion.

5.2  RightSizeMem v2: peak memory

RightSizeMem has twelve families, chosen because they turn input bytes into memory in different ways. They include pandas group-bys and joins, polars pipelines in eager, lazy and streaming modes, DuckDB queries with and without a memory limit, chunked CSV and JSONL readers, NumPy linear algebra with optional memory mapping, scikit-learn estimators, TF-IDF, a small PyTorch model on CPU, image batches and pure-Python grouping.

Each run uses three processes. A child process writes the inputs to a temporary directory, a fresh interpreter runs the task body on those files, and the parent reads the child’s ru_maxrss and CPU time from wait4. BLAS and OpenMP are limited to one thread, and workloads set their own threads in code. The workload’s peak memory ww is its ru_maxrss. As we show in Section 7, on Linux this value includes the measuring parent’s own peak at the time of exec, about 158 MiB here, which makes about a third of the smaller workloads’ labels one cell higher than needed.

5.3  RightSizeCPU big-1: the busiest 15 seconds

RightSizeCPU has eleven families, chosen for how they use cores, since CPU need depends on parallelism much more than on input size. They cover NumPy BLAS with and without a thread cap, polars and DuckDB with explicit thread settings, scikit-learn ensembles, serial pandas, Python thread pools that hold or release the GIL, process pools, a CPU PyTorch model, pyarrow CSV parsing, an I/O-bound pool and a task with two phases.

CPU time for the whole process tree is sampled every second. Each pod runs two measurements side by side on disjoint sets of seven cores, and a check of 44 runs against single-run pods put all 44 within 25% of each other. The CPU label is the busiest 15-second average, because that is the resolution at which cluster monitoring (Prometheus scraping cAdvisor every 15 s) sees a container. Peak memory is measured as in RightSizeMem.

5.4  RightSizeGPU big-2: peak GPU memory across a machine ladder

RightSizeGPU has ten PyTorch families: a tabular MLP, a CNN, a CNN limited by its data loader, a GPT language model, a transformer encoder, a recommender with sharded embeddings, blocked matrix multiplication, nearest-neighbour search, fine-tuning of decoders from 0.6B to 7B parameters split across GPUs, and generation with a KV cache. NVML reports memory and utilization on every visible GPU every half second. Each run starts on a T4 and moves up the machine ladder (Table 2) whenever it runs out of device memory, and a run that runs out of memory on the largest machine it reached is censored. The oracle machine for a run is the cheapest one it fits on. For machines a run was not measured on, we model the fit from its per-GPU peak and, for sharded code, its imbalance across GPUs.

5.5  Splits and history

Runs are split by task, never by run. A hash of the task id sends 70% of each family’s tasks to training, 10% to validation and 20% to test. The seven held-out families go entirely to a separate unseen split. The test split therefore measures how well an approach handles new tasks from familiar families, and the unseen split measures how well it handles new kinds of code. Every setting that an approach tunes is chosen on validation, which contains familiar families only.

The kk-th run of a task carries the task’s earlier runs as its history. A task’s first run has no history at all, and these cold starts make up 33–50% of each split.

6  Every run as a Job and as a Flyte task

The workload code was generated as Flyte tasks, but nothing in the body of a task depends on Flyte. We use that to put every measured run into the benchmark twice, once as a raw Kubernetes Job and once as a Flyte task, with the task body unchanged in both. To make the Job version, job.py, we turn File parameters into paths, drop the flyte import, and add a __main__ block that stages the inputs, calls the function and writes result.json for upload. A batch/v1 manifest goes with it, carrying the image, the input locations, the thread settings the measurement used, the staging volume and an empty resources block, which is the request still to be decided. Figure 1 shows one task written both ways.

6.1  Stagings

How a Job’s inputs reach its container is the biggest thing that changes its memory need. Each task is assigned one of four stagings by a hash of its id, and all of its runs share it (Table 5). Inputs are fetched either by an init container running aws-cli or by the job itself with boto3, and they land either on node disk or on a memory-backed volume.

6.2  Label accounting

Let ww be the workload’s measured peak memory (Section 5) and let BB be the size of the staged inputs plus the result file, with each file rounded up to whole pages. The two kinds of pod need Job:1.05(w+48MiB⋅[boto3]+B⋅[tmpfs]),Flyte:1.05(w+R),R=70MiB,\begin{align*} \text{Job:}\quad & 1.05\,\bigl(w + 48\,\text{MiB}\cdot[\text{boto3}] + B\cdot[\text{tmpfs}]\bigr),\\ \text{Flyte:}\quad & 1.05\,\bigl(w + R\bigr), \qquad R = 70\,\text{MiB}, \end{align*} where the factor 1.05 is headroom and the memory label is the smallest grid cell at or above the need. Each term has a simple reason. Files on a memory-backed volume are charged to memory byte for byte, while the same files on node disk are reclaimable page cache and add nothing, since the measured workloads already read local files. The boto3 client adds 48 MiB to a workload’s peak. Its download also runs inside the job, taking d=bytes/440MB/s+0.4s per object+0.7sd = \text{bytes}/440\,\text{MB/s} + 0.4\,\text{s per object} + 0.7\,\text{s} at about 1.8 cores, so we prepend that window to the run’s CPU series. For a light job with a large input, the download can be the busiest 15 seconds of the run. The Flyte runtime RR is 70 MiB, measured in real task pods (Section 7). Earlier releases used a value of 180 MiB that had never been measured. Staging does not change GPU need.

The manifest sizes the init container at 256MiB+B256\,\text{MiB} + B for tmpfs stagings, so that it can hold what it writes. Our first release used a flat 256 Mi, which real pods showed cannot work for larger inputs (Section 7). Histories are reported in each interface’s own units: a Job’s earlier runs report the container’s peak as cAdvisor would, and a Flyte task’s report the peak including the runtime, as Flyte’s UI would.

The staging constants come from an in-cluster probe using boto3 1.43 under cgroup v2. A bare interpreter holds 11 MiB. With boto3 imported, a client built and a file downloaded, the process holds 74–80 MiB, and it never peaks above that final level. Inside a real workload boto3 adds only 48 MiB at the median, because it shares modules the workload has already loaded. Download throughput rises from 122 MB/s for a 64 MiB object to 417–431 MB/s for a 4 GiB one.

7  Checking the labels in real pods

Because the labels in Section 6.2 are derived rather than measured directly, we checked them twice. The first check (rt-k8sval-2) re-ran 176 corpus runs both as Flyte tasks and as their rendered job.py, as sibling processes inside one pod. It confirmed the arithmetic of the accounting. Measured over predicted memory was 0.999–1.000 at the median for every staging, and tmpfs was charged at exactly the input size. A single pod has a single memory cgroup, though, so this check could not show where the kernel charges pages when a pod has several containers.

The second check (rt-k8spod-1) used real pods. We took 100 runs (48 from RightSizeMem, 44 from RightSizeCPU, and 8 init-tmpfs runs with inputs over 300 MiB) and gave each of them pods of its own, about 480 in all (Table 6). Every container sampled its own cgroup’s memory counters every 50 milliseconds.

The Flyte runtime. Before a task’s own module is imported, the Flyte task container already holds 55.0 MiB of anonymous memory, with almost no variation across the 100 runs (p10–p90 54.9–55.0 MiB). Its peak is a median 70 MiB above the same run’s peak as a plain Job (p10 53, p90 242 MiB), so running a workload inside the runtime’s process costs slightly more than the runtime does on its own. The 180 MiB used in earlier releases had no measurement behind it. With that value, the Flyte label matched the real container’s cell for only 23% of runs and was one cell too high for 70%. With 70 MiB, it matches for 58%, is one cell high for 33% and one cell low for 9%. The low ones are process pools, where the container counts every worker process, and some DuckDB and polars runs. The k8s-2 release uses 70 MiB, which lowers 61% of the Flyte labels on CPU nodes by one cell.

Where tmpfs pages are charged. A tmpfs page is charged to the container that writes it. When the job downloads its own inputs (boto3-tmpfs), the job container’s shared memory grows by the staged size times 1.0001 at the median (n=23n=23). When an init container stages them (init-tmpfs), the init container’s shared memory equals the staged size and the job container’s stays at zero (n=31n=31). The pages outlive the init container, however, and still count against the pod. With its limit set to the label minus the staged bytes, the job was OOM-killed in 9 of 31 init-tmpfs pods, and with the full label 30 of 31 ran. So adding the staged bytes to the label is correct, even though the pages are enforced through the pod’s limit rather than the container’s.

The first release’s init containers. With the flat 256 Mi init container of the first release, every staging up to 162 MiB ran and none of 254 MiB or more did. Ten of those were confirmed OOM-killed while staging, and six more failed. In that release, 982 of the 2,756 evaluated init-tmpfs Jobs staged more than 200 MiB, which means 7% of all Job rows described pods that could never have started. The k8s-2 release sizes the init container at 256 MiB plus the staged bytes.

Labels as limits. When we set the job container’s limit to its label, 98 of 100 runs succeeded (Table 7). Both failures were process pools, where the label records the largest single process but the cgroup counts all of them together. One cell below the label, 25 of the 97 runs that started were OOM-killed.

Labels are sometimes a cell too generous. We also compared each corpus label with the job container’s measured peak of anonymous plus shared memory, plus the same 5% headroom (Table 8). Depending on the staging, the label falls in the same cell for 52–68% of runs and within one cell for 91–100%. It is higher for 26–48% of runs and lower for at most 6%. Two things push labels up. The first is a quirk of ru_maxrss: on Linux, the value a parent reads for its child through wait4 includes the parent’s own high-water mark at the moment the child calls exec, because the kernel carries the old address space’s peak into the new one. The measuring parent in our corpora held about 158 MiB, so even the smallest workloads report at least that much. The second is memory-mapped input files, which RSS counts but the kernel can reclaim; numpy_linalg and image_batch both map their inputs. Neither effect causes a run to fail at its label, but together they make about a third of labels one cell larger than strictly necessary. The oracle in Section 8 inherits this, so all regrets in this paper are measured against a slightly generous oracle.

8  Cost model and metrics

We score a request by the dollars it takes to get the pod to finish successfully, counting failed attempts, retries and lateness, all simulated from the run’s measurements. Each axis fails the way it fails on Kubernetes. If memory is too low, the container is OOM-killed partway through (at the point where the run reached 90% of its peak) and retried with double the memory, for up to eight attempts. If CPU is too low, the run is throttled: each second that wanted uu cores takes max⁡(1,u/limit)\max(1, u/\text{limit}) seconds, replayed against the measured per-second series. If the GPU is too small, the run hits a CUDA out-of-memory error and is retried on the next machine up. A GPU task given no GPU fails at start and is retried on a T4, and a CPU task given a GPU runs normally but pays the GPU node’s price.

A CPU pod is priced by its dominant share of an m6i.xlarge (4 vCPU, 16 GiB, $0.192 per hour), that is p(m,c)=0.192⋅max⁡(c/4,GiB(m)/16)p(m,c) = 0.192\cdot\max(c/4,\ \text{GiB}(m)/16). A GPU pod pays the on-demand price of its machine. Every attempt also pays 0.02 hours for image pull and start-up. We normalize every run to one nominal hour of work, so that short measured runs stand in for longer production tasks.

On top of dollars, two penalties account for time. Each retry adds one oracle cost, which stands for the delay of running again, and each hour of lateness adds one oracle hourly price. These defaults match an orchestrator that retries automatically. A raw Job with backoffLimit: 0 simply fails and waits for someone to resubmit it, so in Section 11.6 we also score everything with retry penalties of 5 and 20 oracle costs.

The oracle requests the label cell on each axis, and no GPU for a CPU task. It is the label rather than the cheapest possible request. Asking for one CPU cell below the busiest window only throttles that window, which can cost less than the cores it saves, so CPU regret can occasionally be slightly negative.

Metrics. Our headline metric is regret, the mean over runs of an approach’s cost divided by the oracle’s cost, minus one. Every run counts equally however much it costs, and this is also the quantity that every approach tunes on validation. Dollar regret is total cost over total oracle cost, minus one, so large jobs count for more. We also report the share of runs whose first attempt succeeds, and how often the memory request fits and is at most one cell above the label. For pairs of pods that come from the same run but differ in one detail of the pod spec, we check whether an approach’s memory request moves in the same direction as the label (Section 11.3). We report this separately for pairs whose label moved and pairs whose label did not.

Uncertainty. Runs of the same task share code, and a run’s Job and Flyte pods share a workload, so the rows are not independent. Every interval in this paper is therefore a 95% percentile interval from a task-clustered Poisson bootstrap [3, 4] with 2,000 replicates. Each task, including all of its runs and both pods of each run, gets a single Poisson(1) weight. Differences between approaches and between pod types are bootstrapped as paired differences on the same rows. We report variation between trainings separately, across three seeds (Section 11.7).

9  Approaches

Every approach produces a full request for every pod, and every setting an approach tunes is chosen on the validation split by mean regret. Appendix C lists the settings.

9.1  Static requests and rules

The simplest approach, static, gives every pod the same request: a training quantile of memory need and of CPU need, and no GPU. Every GPU task therefore fails at start and is retried on a T4.

Rules are what a platform team might write by hand. If the code mentions CUDA, the task gets a GPU sized from its largest past GPU peak times a margin. Memory is the largest past peak, converted to this pod’s units and multiplied by a margin, or the static request if there is no history. CPU is the largest past peak in cores times a margin. On a first run it falls back to the largest pool size the code declares (max_workers=, n_jobs= and so on), or one core.

We added a stronger baseline, rules-sized, which also reads the pod spec. When a task has history, it takes the earlier run closest in input size and scales its peak by the ratio of input sizes. On a first run it estimates the workload’s peak as a+k⋅input MiBa + k\cdot\text{input MiB}, with aa and kk tuned on validation cold starts, and adds the staging’s cost as read from the pod spec: 48 MiB if job.py imports boto3, and the staged bytes if the manifest says medium: Memory. The result is converted into the pod’s need with the accounting of Section 6.2.

9.2  Gradient-boosted quantile trees

The trees use 209 features that a scheduler can compute. Twenty-seven describe the inputs and history, such as total bytes, bytes by format, visible rows, column counts, array shapes, the number of earlier runs, their peaks, and the size ratio to the closest earlier run. Another 173 describe the code, marking API tokens such as groupby, TfidfVectorizer or ProcessPoolExecutor and numeric literals such as pool sizes, layer widths and batch sizes. Four flag CUDA use, and five flag details of a Job’s pod spec (kind: Job, initContainers, medium: Memory, import boto3 and download_file).

For each axis we fit 19 quantile regressors [12] with scikit-learn’s HistGradientBoostingRegressor (quantiles 0.05 to 0.95, 300 rounds, learning rate 0.06, 31 leaves) on the base-2 log of the need, plus a classifier that predicts whether the task needs a GPU. The predicted quantiles define a piecewise-linear CDF, and each cell’s probability is the CDF mass between its edges. Two ablations, gbt-dist-k8s and gbt-dist-flyte, train on Job pods only or on Flyte pods only.

9.3  Zero-shot 27B

A 27B-parameter Qwen instruction model, served with vLLM [16], reads the prompt shown in Appendix B and answers in JSON at temperature zero. We parse its answer, read units as Kubernetes would (so 2 GiB, 2GB and 500m all work), and round each value up onto the grid. An answer we cannot parse falls back to 4 Gi, one core and no GPU. The model reasons in plain text before answering even with thinking turned off, and our first release cut it off at 1,024 tokens, which left 444 of 560 answers unparseable. Here we score it two ways: with up to 8,192 tokens of free text, and with decoding constrained to the answer’s JSON schema and 256 tokens. Both are scored on a family-stratified sample of 300 runs per split, with each run’s Job and Flyte pods.

9.4  Decision model: three pointer heads on one forward pass

Instead of generating an answer, the decision model reads the prompt and scores every option on every axis in one forward pass (Figure 2). The options are written out in the prompt itself. For each axis, a small head compares the hidden state at each option’s last token with the hidden state at the end of the prompt, so the model reads the candidates in its context rather than memorizing a fixed output layer: saxis(j)=⟨Wq,axisLN(a),Wk,axisLN(kj)⟩256,P(axis=j)=softmaxj(saxis(j)/Taxis).\begin{equation} s_{\text{axis}}(j) = \frac{\langle W_{q,\text{axis}}\,\mathrm{LN}(a),\ W_{k,\text{axis}}\,\mathrm{LN}(k_j)\rangle}{\sqrt{256}},\qquad P(\text{axis}=j) = \mathrm{softmax}_j\!\big(s_{\text{axis}}(j)/T_{\text{axis}}\big). \end{equation} Here aa is the last prompt token’s hidden state, kjk_j is option jj’s, each axis has its own Wq,Wk∈ℝ256×2048W_q, W_k\in\mathbb{R}^{256\times2048}, and the temperature TaxisT_{\text{axis}} is fitted on validation. This is a pointer mechanism [23] applied to option tokens.

The torso is Qwen3-1.7B [17] without its language-model head, adapted with LoRA [10] (rank 16, α\alpha 32) on every projection of every layer. Prompts are cut from the left at 3,072 tokens, a length no evaluated prompt reaches. We train with cross-entropy on the three labels, weighting the CPU term by 0.3 and leaving out memory and CPU for GPU tasks. Training uses at most 5,000 rows per corpus and pod type, 27,936 rows in all, for one epoch with micro-batches of 8, two accumulation steps, and AdamW at 2×10−42\times10^{-4} for the adapters and 10−310^{-3} for the heads, on one NVIDIA L4. Each axis’s temperature minimizes validation negative log-likelihood.

Two ablations train on one pod type only: jev-pointer-k8s on Jobs and jev-pointer-flyte on Flyte tasks. Each has half the rows and trains for two epochs, so that all three variants take the same number of steps, and each is calibrated on its own pod type’s validation rows.

9.5  Turning a distribution into a request

The trees, the decision models and the pools all produce a probability distribution on each axis, and we read each one out in two ways. The argmax read-out takes the most likely cell on each axis. The decoded read-out takes cost into account. It first decides whether to give a GPU, choosing none when P(none)P(\text{none}) is at least a threshold θ\theta tuned on validation, and otherwise the GPU cell most likely to hold the peak. For memory it picks the cell with the lowest expected cost, arg⁡min⁡m∑jC[m,j]P(j)\arg\min_m \sum_j C[m,j]\,P(j), where C[m,j]C[m,j] is the cost, retries included, of requesting cell mm for a pod that needs cell jj. For CPU it picks the cell most likely to fall within 25% of the busiest window. Because an OOM costs a retry, decoding leans toward asking for a little more memory, while argmax ignores that asymmetry.

9.6  Reinforcement learning against the cost model

Training to match the label misses two things the cost model cares about. The axes interact, since memory and CPU are free on a GPU node, while a GPU is the most expensive mistake on a CPU node. And asking for too little costs more than asking for too much. The RL approach (rl-pointer) starts from the decision model and directly maximizes the cost model’s reward using GRPO [19], as shown in Figure 3. Because the policy is three categorical distributions, a group of 16 samples comes from a single forward pass and no text is generated. It trains on 6,000 prompts for one epoch with a KL coefficient of 0.05 and the reward capped at 20.

9.7  Opinion pools

The trees and the language models make different mistakes. The trees read numbers exactly but have nothing to go on for code they have never seen, while the language models read code well but treat numbers as tokens. A logarithmic opinion pool [7] combines their calibrated distributions on each axis: ppool(j)∝ptrees(j)wpLM(j)1−w.\begin{equation} p_{\text{pool}}(j) \propto p_{\text{trees}}(j)^{w}\,p_{\text{LM}}(j)^{1-w}. \end{equation} A single weight ww is shared across the three axes and tuned on validation together with θ\theta, and nothing is retrained. A model trained on one pod type is pooled with trees trained on the same pod type and tuned on that pod type’s validation rows.

9.8  A pre-registered novelty gate

In our first release, the pooled RL model read by argmax was the best approach on familiar code and one of the worst on new code, while the RL model on its own was the reverse. The gate sends each pod to one or the other according to how far it is from the training data: s(x)=110∑i=110‖z(x)−z(x(i))‖2,request={pool×RL, argmaxif s(x)≤τ,RL, decodedotherwise.\begin{equation} s(x) = \tfrac{1}{10}\textstyle\sum_{i=1}^{10}\lVert z(x) - z(x_{(i)})\rVert_2,\qquad \text{request} = \begin{cases}\text{pool}\times\text{RL, argmax} & \text{if } s(x)\le\tau,\\ \text{RL, decoded} & \text{otherwise.}\end{cases} \end{equation} Here zz standardizes the trees’ 209 features by their training mean and standard deviation, x(i)x_{(i)} are the ten nearest training pods, and τ\tau is the 95th percentile of ss on validation. No labels are involved. Because validation contains familiar families only, the threshold sends exactly 5% of familiar pods to the RL model by construction. We chose the gate’s members, signal and threshold after seeing the first release’s results, so we fixed all three before training k8s-2 at new seeds, which makes k8s-2 a confirmation of a pre-registered choice.

An internal review found a problem with the first release’s version. A feature that never varied in training was divided by 10−910^{-9}, so any pod with an unseen import landed effectively infinitely far away. We now leave such features in their raw units, and we keep the old scaling as knn-raw for comparison. We also compare two other signals: kNN on the 27 numeric features alone, and the Jensen–Shannon divergence between the trees’ and the RL model’s predictions.

9.9  A Flyte-to-Job adapter

A team whose history is all Flyte tasks has no Job pods to train on. The adapter shifts a Flyte-trained model’s memory distribution using the accounting of Section 6.2, reading only what a scheduler can see: the manifest’s volume medium, whether job.py imports boto3, and the input sizes. Each cell’s representative need njn_j (its geometric middle) becomes (nj/1.05−R+48[boto3]+B[tmpfs])×1.05(n_j/1.05 - R + 48[\text{boto3}] + B[\text{tmpfs}])\times1.05. CPU and GPU come from the model’s own reading of the Job’s prompt.

10  Experimental setup

The whole benchmark runs as one Flyte factory on an EKS cluster: a graph of cached tasks, each of which publishes a versioned artifact (Figure 4). The trees and rules fit on a CPU pod, each decision model and the RL model train on one NVIDIA L4, and the zero-shot model runs as a shared vLLM service in the same cluster. Each of these is itself a batch pod that someone had to size.

We trained k8s-2 three times on the same data (rsk-k8s-2, -s2 and -s3). The seed controls data order, LoRA initialization and RL sampling. GPU kernels are not bit-for-bit deterministic, so even the same seed would not reproduce a model exactly. The zero-shot model is scored once, with seed 1. Unless we say otherwise, tables show seed 1 with its bootstrap interval, and Section 11.7 reports the spread across all three seeds. Appendix D lists every cluster run.

11.3  Does a model read the manifest?

A model could do well on Jobs for the wrong reason, for example by learning only that a Job’s numbers run lower than a Flyte task’s because a Job does not carry the runtime. We test this two ways.

Run and Job pairs. Of the 3,950 test pairs of a run’s Flyte pod and its Job pod on CPU nodes, the memory label differs in only 29.9%. In 638 pairs the Job needs more, because it stages its inputs on tmpfs, and in 543 it needs less, because it has no runtime. With the old 180 MiB constant, 69% of pairs differed and almost all of those moves were downward, so this metric mostly measured whether a model knew about the runtime. A model that ignores the pod type keeps the same request for both pods; it scores 100% on the pairs whose label stays the same and 0% on the pairs whose label moves. Models trained on both pod types move the right way on 56–67% of the pairs that move, and on 75–83% of upward moves (Table 19 in Appendix E). The rules move the right way on 25%.

A controlled counterfactual. The pairs above still mix the effect of the manifest with the effect of the runtime. To isolate the manifest, we took 1,189 first runs from the test and unseen splits and rendered each one as a Job under all four stagings, holding the task, code and inputs fixed (4,756 pods in all). Only the manifest and the way the job fetches its inputs change. Because these are first runs, there is no history to give the staging away, so the manifest is the only evidence. Switching the volume from disk to tmpfs moves the label in 48.6% of test pairs and 74.2% of unseen pairs, and switching the fetcher from an init container to boto3 moves it in about a fifth.

11.5  First runs and runs with history

Cold starts are where the approaches differ most (Table 13). With history, almost everything trained does well on familiar code, from 1.6% for RL read by argmax to 10.1% for RL decoded, and even rules-sized reaches 11.6%. 11.6  Dollars and the price of a retry

Mean regret counts every run equally, while dollar regret is dominated by large jobs. On familiar code the two agree: the pooled RL model read by argmax costs 15.7% more than the oracle in dollars, and the gate 19.5%. On new code, dollars rank the trees first (85.6%), because they size the largest jobs better, even though their mean regret is among the worst. The gate and RL cost $1,177 per 1,000 unseen Job runs, against $959 for the trees, $1,126 for rules-sized and $517 for the oracle.

A raw Job with backoffLimit: 0 does not retry; it fails, and someone resubmits it. That makes an OOM much more expensive than our default penalty of one oracle cost per retry. Table 14 re-scores everything with penalties of 0, 5 and 20 oracle costs. The pooled decision model stays best on familiar code at every penalty from 1 to 20, at 89.4% even when a retry costs twenty times the oracle. (With no retry penalty at all, RL read by argmax is best, at 1.9%.) On new code, a larger penalty favours the approaches that ask for more memory. At a penalty of 5 or 20, rules-sized becomes clearly the best approach on unseen code (112.5% and 387.2%), ahead of RL and the gate (135.7% and 497.1%). For teams that run raw Jobs without retries, this is the most practical result in the paper. On code nobody has seen before, a rule that scales by input size and reads the manifest is safer than any model we trained.

11.8  Zero-shot

With room to finish its reasoning, the 27B model answers almost every prompt, and the results are no longer dominated by fallbacks. It scores 48.8% on familiar-code Job pods and 42.8% on unseen ones, against 42.4% and 49.8% for the rules. Constraining it to the JSON schema makes little difference on Jobs (48.8% and 44.4%) but helps on Flyte tasks (21.8% on familiar code). Its intervals are wide, about 30 points, because it is scored on a sample, so the honest summary is that a large model with no training is roughly as good as hand-written rules and much worse than a small model trained on the benchmark. It is, however, the only approach that does not get worse on new code.

12  Discussion

Benchmarking Kubernetes pods from one set of measurements. Because the user code is the same whichever way a pod is submitted, one measurement of the workload can label both a raw Job and a Flyte task, as long as the accounting for the pod’s edges is right. Getting it right took real pods. Sibling processes in one pod confirmed the arithmetic, but only per-container cgroups showed where tmpfs pages are charged, that the first release’s init containers could not hold their inputs, and that the Flyte runtime was less than half the size we had assumed. Anyone deriving Kubernetes labels this way should check them against the cgroup, not against another RSS measurement.

What a model learns from Jobs. A model trained on Jobs reads the manifest. It changes its memory request when the volume medium changes, and it does so on first runs where nothing else gives the staging away. Flyte tasks add nothing to that model’s accuracy on Jobs, and a Flyte-only model does not transfer well even after an explicit adapter. For a team that submits pods both ways, the practical advice is to train on the pods it actually runs. Flyte history is still useful for sizing Flyte tasks, and the corrected adapter recovers part of the gap when Job history is missing.

Familiar and unfamiliar code. The gap between the two splits is the main open problem. On familiar code the best approaches are within 7–8% of the oracle. On new kinds of code, the best trained model is 39% above it, and a careful rule matches it. Pooling the trees with a language model helps on familiar code and hurts on new code, because the pool’s weight is tuned on familiar families. The gate recovers the better of the two on each split, but on this benchmark its detector has an easy job, since new families usually bring new libraries. A benchmark that separates unfamiliar code from unfamiliar libraries would test it properly.

Cost, not accuracy. Accuracy on the label and cost often disagree. Cost-aware decoding over-asks on purpose, the Flyte-to-Job adapter was judged a failure until its runtime constant was corrected, and the ranking on new code flips when retries become expensive. A benchmark for this decision has to score money, and it has to say what a failure costs.

13  Limitations

The workloads are synthetic. They use real libraries and real code paths, but the tasks are generated, the data is random, and runs take seconds to minutes. Production tasks are longer and messier. The seven unseen families were chosen by hand, and six of them introduce a library that no training family uses, so the benchmark does not test new code built only from familiar libraries. The people who wrote the generators also wrote the tree features and the rules, and the task names give away the family, although removing them changes regret by less than four points.

The labels carry three known biases. The ru_maxrss floor and memory-mapped inputs make about a third of labels one cell larger than strictly needed, so the oracle is slightly generous. Process pools are labelled by their largest process rather than their total, which is why two of 100 real pods failed at their label. And RightSizeMem has no per-second CPU series, so its throttling is modelled from mean cores. The Job labels are derived rather than measured for every run. We validated them on 100 runs in real pods and 176 in a single pod, but we did not re-measure GPU runs as Jobs, and the four stagings leave out sidecars, CSI drivers and other init work.

The cost model uses list prices, with no spot discounts or bin-packing, and prices a retry at one oracle cost by default; Section 11.6 shows how much that choice matters. We trained three times, which shows that rankings on new code within about ten points are not stable, but three seeds are not enough to put tight intervals on that variation. The zero-shot model was scored on a sample of about 300 runs per split, and only once.

14  Conclusion

RightSize Bench scores the request a scheduler makes before a Kubernetes pod runs, in dollars, across 33 families of task code submitted both as raw Jobs and through Flyte. Checking its labels in real pods fixed two errors and measured the cost of Flyte’s runtime at about 70 MiB. A small model trained on Jobs reads the manifest and, pooled with gradient-boosted trees, comes within 7% of the oracle on familiar code. On unfamiliar code, the best trained model and a careful rule are both about 39% above the oracle, and the rule is safer when failures are expensive. Closing that gap, and testing a novelty detector on code that looks familiar but is not, is the work that remains.

B  A complete prompt

The prompt every language-model approach reads, here for the init-tmpfs Job of a k8s-2 test task. The init container’s memory limit is 281 Mi: 256 Mi plus the 25 MiB it stages onto the memory-backed volume. A Flyte pod’s prompt shows the task module in place of job.py and the manifest, and reports history peaks with the runtime included.

System

You size batch jobs before they run: Flyte tasks, or Kubernetes Jobs given as a Python module and its manifest. Given the code, the metadata of this run's inputs, and what earlier runs of the same job used, choose the cheapest request that runs it: memory, CPU cores, and a GPU or none. Memory is a hard limit: below the peak the container is OOM-killed and retried with double. A Flyte task's memory includes the Flyte runtime; a Kubernetes container's includes whatever the job loads to fetch its inputs, and files written to a memory-backed emptyDir (medium: Memory) are charged to it. CPU below the busiest 15 seconds' use throttles the task and it finishes late. Thread pools the code does not size get one thread. gpu is the peak GPU memory to provision, or none for a task that does not use CUDA; it lands on the cheapest machine that holds it -- T4 (15 GiB, $0.53/h), L4 (22 GiB, $0.98/h), A10G (22 GiB, $1.21/h), L40S (44 GiB, $2.24/h), 4xL4 (88 GiB, $4.60/h), 8xT4 (120 GiB, $7.82/h), 4xL40S (176 GiB, $10.49/h) -- and a GPU pod comes with its host memory and cores. A multi-GPU machine only helps code that spreads its model over every visible GPU. A GPU task given no GPU fails at start; a GPU given to a CPU task is paid for the whole run.
