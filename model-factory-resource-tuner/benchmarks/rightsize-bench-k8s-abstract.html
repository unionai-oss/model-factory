RightSize Bench: learning Kubernetes resource requests from code

k8s-2 · 32,082 measured runs, each as a raw Job and as a Flyte task · 3 trainings
Abstract

Before a batch pod runs on Kubernetes, someone has to decide how much memory and CPU it gets and whether it gets a GPU. Too little makes it fail or run slowly, and too much wastes the cluster. RightSize Bench scores that decision in dollars: each request is replayed against a measured run, failed attempts and throttling included, and compared with the cheapest request that would have run it. It has 32,082 measured runs of 33 families of generated Python tasks that use real libraries, from pandas and DuckDB to PyTorch training and sharded language models. Every run appears twice, as a raw Kubernetes Job with its inputs staged in one of four ways, and as a Flyte task, whose runtime we measure at about 70 MiB per pod. We checked the labels in about 480 real pods, which found two errors in our first release.

On new tasks from familiar families, gradient-boosted trees pooled with a fine-tuned 1.7B decision model come within 11.7% of the cheapest request on Job pods [10.8, 12.7]. On seven held-out families every approach does much worse, and a hand-written rule that scales by input size and reads the manifest (42.7%) is as good as anything we trained. Models trained on Jobs read the manifest. The dataset and the models are on the Hugging Face Hub.

What we found

  1. 70 MiBReal pods changed the labels. The Flyte runtime we had assumed was 180 MiB measures about 70, and init containers in our first release were too small to hold what they staged, so 7% of its Job rows described pods that could not start. Both are fixed in this release.
  2. 3 in 4Models trained on Jobs read the manifest. When only the staging volume changes from disk to medium: Memory on a first run, the trained models move their request the right way about three times in four. A model trained only on Flyte tasks does so about one time in five, and rules never do.
  3. 81%Most familiar-family test tasks repeat a training program. On the test pods with new programs, the decision model's regret more than doubles, while the trees pooled with the RL model barely move. The seven held-out families are the benchmark's test of new code.
  4. 42.7%New families are the open problem. On held-out families a careful rule does as well as any trained model, and it has the lowest regret when an out-of-memory failure is expensive. With seven families, intervals clustered by family are wide.
Setup

How the benchmark works

Runs
32,082 usable runs from three corpora (RightSizeMem, RightSizeCPU and RightSizeGPU), each measured in Kubernetes pods for peak memory, CPU over the busiest 15 seconds, and peak GPU memory. Tasks are split 70/10/20 into train, validation and test, and seven whole families are held out as the unseen split.
Two pods per run
The same task body as a job.py with a batch/v1 manifest, or as a Flyte task. A Job stages its inputs with an init container or boto3, onto node disk or a memory-backed volume. Its label is the workload's peak plus what the staging adds; a Flyte task's is the peak plus the 70 MiB runtime.
Approaches
A static request, two kinds of rules, gradient-boosted quantile trees, a zero-shot 27B model, a Qwen3-1.7B decision model with pointer heads (also trained on Jobs only and on Flyte tasks only), that model trained further with reinforcement learning against the cost, pools of the trees with each model, and a novelty gate.
Cost
Out-of-memory kills retry at double the memory, CPU throttling is replayed from the measured series, a too-small GPU retries one machine up, and retries and lateness add penalties. Prices are on-demand list prices.
Cheapest request
For each pod, the request on the grid with the lowest cost under the same model. It is often one CPU cell below the busiest 15 seconds, because throttling that window costs less than the cores.
