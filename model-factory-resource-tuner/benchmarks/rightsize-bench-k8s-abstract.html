RightSize Bench: learning Kubernetes resource requests from code

k8s-2 · 32,082 measured runs, each as a raw Job and as a Flyte task · 3 trainings
Abstract

Before a batch pod runs on Kubernetes, someone has to decide how much memory and CPU it gets, and whether it gets a GPU. Too little makes it fail or run slowly, and too much wastes the cluster. RightSize Bench scores approaches to this decision by what their requests would cost to get each run to finish, compared with the cheapest request that would have worked. It contains 32,082 measured runs of 33 families of generated Python tasks that use real libraries, from pandas and DuckDB to PyTorch training and sharded language models. Every run appears twice: once as a raw Kubernetes Job, with its inputs staged in one of four ways, and once as a task submitted through Flyte, an AI-native interface to Kubernetes that adds typed I/O, caching, retries and durable execution for about 70 MiB of runtime per pod. We checked the labels in about 480 real pods, which found and fixed two errors in our first release.

On new tasks from familiar families, pooling gradient-boosted trees with a fine-tuned 1.7B decision model gives 6.6% regret on Job pods [5.6, 7.6]. On task families held out of training, every approach does much worse, and the leaders change: the decision model trained further with RL and a hand-written rule that scales by input size and reads the manifest tie at 39%. When an out-of-memory failure is as expensive as resubmitting a Job by hand, that rule is the best approach on new code. Models trained on Jobs do read the manifest, and adding Flyte data does not make them better on Jobs.

What we found

  1. 70 MiBReal pods changed the labels. The Flyte runtime we had assumed was 180 MiB measures about 70, and two-thirds of Flyte labels were a cell too high. Init containers in our first release were too small to hold what they staged, so 7% of Job rows described pods that could not start. Both are fixed in this release.
  2. 3 in 4Models trained on Jobs read the manifest. When we change only the staging volume from disk to medium: Memory on a first run, the trained models move their request the right way about three times in four. A model trained only on Flyte tasks does so about one time in five, and rules never do.
  3. +0.6 ptFlyte data does not help with Jobs. A decision model trained only on Jobs is within a point of one trained on both kinds of pod, while one trained only on Flyte tasks is three times worse on Jobs. An adapter that applies the staging accounting recovers a third to a half of that gap.
  4. 39%New code is the open problem. On held-out families the best trained model and a careful rule tie at 39%, and the rule wins when failures are expensive. A novelty gate fixed in advance gets 8.1% on familiar code and 39.3% on new code, but its detector has an easy job here, since new families bring new libraries.
Setup

How the benchmark works

Runs
32,082 usable runs from three corpora (RightSizeMem, RightSizeCPU and RightSizeGPU), each measured in Kubernetes pods for peak memory, CPU over the busiest 15 seconds, and peak GPU memory. Tasks are split 70/10/20 into train, validation and test, and seven whole families are held out as the unseen split.
Two pods per run
The same task body as a job.py with a batch/v1 manifest, or as a Flyte task. A Job stages its inputs with an init container or boto3, onto node disk or a memory-backed volume. Its label is the workload's peak plus what the staging adds; a Flyte task's is the peak plus the 70 MiB runtime.
Approaches
A static request, two kinds of rules, gradient-boosted quantile trees, a zero-shot 27B model, a Qwen3-1.7B decision model with pointer heads (also trained on Jobs only and on Flyte tasks only), that model trained further with GRPO against the cost, pools of the trees with each model, and a novelty gate.
Cost
Out-of-memory kills retry at double the memory, CPU throttling is replayed from the measured series, a too-small GPU retries one machine up, and retries and lateness add penalties. Prices are on-demand list prices.
Oracle
The request the measurements say is right on each axis: the smallest memory cell that holds the need, the CPU cell that covers the busiest 15 seconds, and the GPU that lands on the cheapest machine the run fits.
