RightSize Bench: one model sizes Flyte tasks and Kubernetes Jobs

k8s-1 · 32,082 measured runs, each with a Kubernetes twin
Abstract

RightSize Bench scores approaches that set a task's resource request (memory, CPU, and a GPU or none) by its cost against the cheapest request that would have worked. This release gives each of its 32,082 measured Flyte runs a Kubernetes twin: the same code as a plain job.py in a Job manifest, with its inputs staged by an init container or by boto3, onto node disk or onto a memory-backed volume. The twin's labels are derived from the Flyte measurement by an accounting of the runtime, the boto3 client and the staged bytes; on 176 re-measured runs, 100% land within one memory cell and 90% in the same cell. The same measurement exposed a floor in every RightSize Flyte memory label: ru_maxrss includes the measuring parent's peak.

Trained on both platforms, every decoded approach's regret on Jobs is within 3 points of its regret on Flyte tasks, and a Qwen3-1.7B decision model moves its memory request with the one manifest line that charges staged bytes to memory in 77% of run–twin pairs (hand-written rules: 43%). A model trained on Flyte alone gets Job memory right on 30.5% of test runs against 90.4%, and an adapter that applies the staging accounting raises that to 51% but raises regret. A label-free novelty gate sends runs near the training runs to the pooled trees and RL model, and the rest to the RL model alone. It scores 6.9% regret on 10,190 test rows and 36.8% on 12,832 rows from unseen task families, the best single approach's number on each split, on two independent trainings. Its detector is near-perfect here because the unseen families import libraries no training run imports; on numeric features alone it falls to AUROC 0.67. In dollars, the trees remain the cheapest learned approach on unseen families.

Results

Mean regret against the oracle, by approach

Mean per-run regret: a run's cost under the approach's request divided by its cost under the oracle's, minus 1. Solid: test (10,190 rows, both platforms). Outline: unseen families (12,832 rows). Zero-shot 27B is a ~280-row sample per split. Bars stop at 125%. Replicate 2; 12 of the 18 rows in the full report.

K8s is the Job rows alone. Moves with label: the share of CPU-node run–twin pairs in which the memory request changes in the same direction as the label (up, down or not at all). $ / 1k: dollars per 1,000 test runs (the oracle pays $280). Bold marks the best among these rows.

Four findings

  1. ±3 ptsOne model sizes both platforms. Trained on Flyte runs and their twins, every decoded approach's regret on Jobs is within 3 points of its regret on Flyte tasks. The decision model moves its memory request with the staging in 77% of pairs, and gets Job memory right on 90% of test rows across all four stagings.
  2. 30.5%A Flyte-only model does not transfer. The same model trained on Flyte rows alone gets Job memory right on 30.5% of test rows and moves with the staging in 38% of pairs, below the rules. Moving its distribution through the staging accounting lifts those to 51% and 66%, but its regret on Jobs rises from 18.0% to 20.6%. Transfer needs Job history.
  3. 6.9 / 36.8A novelty gate gets the best of both. The pooled trees and RL model score 6.6% on test and 94.5% on unseen families; the RL model alone 13.9% and 36.8%. Routing each run by its distance to the training runs, with a threshold set on validation so that 5% of familiar runs go to RL, scores 6.9% and 36.8%. Replicate 1: 6.7% and 35.5%.
  4. 0.67The gate is as good as its detector. Unseen families here import libraries no training run does, which makes them perfectly separable. On input sizes and history alone, the detector's AUROC is 0.67 and the gate's unseen regret 68.8%. Unseen regret also moves by up to 25 points between trainings for the argmax and pooled approaches, against about 1 point on test.
Setup

How the benchmark works

Corpus
RightSizeMem v2, RightSizeCPU big-1 and RightSizeGPU big-2 (32,082 usable runs of real task code, measured in pods), each with its twin: 36,106 train, 5,036 validation, 10,190 test and 12,832 unseen-family rows. A twin stays in its run's split.
Twin
The task's body as job.py (paths instead of Flyte files, a __main__ that stages inputs and uploads the result) and a batch/v1 Job with resources: {}. Four stagings, drawn per task: init container or boto3, emptyDir on disk or with medium: Memory. The two volume variants differ in one manifest line.
Labels
Memory: the Flyte need without the 180 MiB Flyte runtime, plus 48 MiB for boto3 and every staged byte on a memory-backed volume, with 5% headroom. CPU: the boto3 download (bytes ÷ 440 MB/s + 0.4 s per object, at 1.8 cores) prepended to the per-second series. GPU: unchanged. Constants from probe runs; checked on 176 runs re-measured as Jobs.
Approaches
Static request; hand-written rules; quantile gradient-boosted trees with Job token flags; zero-shot Qwen 27B; a Qwen3-1.7B decision model with three pointer heads trained on 27,936 rows from both platforms (6.7 h on an L4); that model RL-tuned with GRPO on the bench's cost (1.9 h); log pools of the trees with each; the decision model trained on Flyte rows only, plain, pooled and adapted; and the gate.
Gate
Mean distance to the 10 nearest training runs in the trees' standardized features. At or below the 0.95 quantile of validation runs: the pooled trees and RL model, read by argmax. Above it: the RL model, decoded cost-aware. No family labels are used.
Cost
Round 21's simulator, the same on both platforms: OOM and retry at double, throttling replayed from the CPU series, CUDA OOM and a retry one machine up, retry and lateness penalties, list prices.

Key terms

Oracle
The request the measurements say is right on each axis: the smallest memory cell that holds the need, the CPU cell that covers the busiest 15 seconds, the GPU cell that lands on the cheapest machine the run fits.
Regret
A run's cost to SUCCEEDED, divided by the oracle's cost, minus 1, averaged over runs.
Unseen families
Task families each bench held out of training, which test whether an approach generalizes to new code.
Replicate
One complete training of every learned approach. The bench was trained twice, independently, on the same data.
