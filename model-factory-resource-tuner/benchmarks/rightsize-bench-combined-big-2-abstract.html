RightSize Bench: trees and language models, combined, on the whole request

big-2 · 32,082 measured runs from three benches
Abstract

A Flyte task's resource request is three guesses made before it runs: memory, CPU cores, and a GPU or none. RightSize Bench joins three single-axis benches (RightSizeMem v2, RightSizeCPU big-1 and the new RightSizeGPU big-2) into one corpus of 32,082 measured runs of real task code, and scores every approach on the whole request, in dollars. GPU big-2 spans the cluster's full GPU machine ladder, from one T4 to four L40S, and includes code that shards its model over several GPUs. The headline is mean regret: how much more than the oracle's request a run costs. Approaches see only the code, the input metadata and the task's earlier runs.

This release combines gradient-boosted trees with a Qwen3-1.7B decision model in two ways. Stacking writes the trees' prediction into the model's prompt; pooling multiplies the two models' probabilities with a tuned weight. Stacking and then RL against the bench's cost model reaches 3.2% regret on 5,095 test runs, against 9.8% for the best arm without the trees and 8.0% for round 20's best. On 6,416 runs from task families held out of training, the same arm scores 102.0%, because it follows the trees' GPU estimate on new code. There, RL without the trees is best (35.5%). Only the pool of the trees with the supervised decision model beats that model on both splits (6.9% and 52.2%, against 14.0% and 58.8%). Unseen regret is not comparable with round 20, because the GPU bench's unseen families changed. Multi-GPU nodes mostly did not schedule, and 1,569 GPU runs were censored.

Four findings

  1. 3.2%On familiar code, the trees and RL compound. The stacked decision model, RL-tuned and read by argmax, costs 3.2% over the oracle, a third of the best arm without the trees (RL 1.7B argmax, 9.8%). It also has 13.0% dollar regret and 92.2% of runs with all three axes right.
  2. 102%On new code, the same arm is one of the worst. On unseen GPU tasks it picks the oracle's machine 35.2% of the time, against 77.1% for RL without the trees, and its GPU-row regret is 208%. The trees fail there too (167%), and the stacked model has learned to follow them.
  3. 35.5%On unseen families, RL without the trees is best. The RL-tuned decision model, decoded cost-aware, scores 35.5%, against 48.0% for the hand-written rules and 90.8% for the trees. Every stacked arm scores between 76.9% and 125.8%.
  4. 6.9 / 52.2One hybrid is better than its language model on both splits. Pooling the trees with the supervised decision model (weight 0.4 on the trees) cuts its test regret from 14.0% to 6.9% and its unseen regret from 58.8% to 52.2%. No other hybrid improves on its language model on unseen families.
Setup

How the benchmark works

Corpus
RightSizeMem v2 (14,234 runs, peak memory and mean cores), RightSizeCPU big-1 (9,900 runs, peak memory and the busiest 15 seconds of CPU) and RightSizeGPU big-2 (7,948 usable runs, peak GPU memory, sharding and imbalance), each split by task on its own bench: 18,053 train, 2,518 validation, 5,095 test and 6,416 unseen-family runs.
Request
Memory from 17 cells (256Mi to 64Gi), CPU from 16 (0.25 to 8 cores), and GPU from 18 (none, or 1 to 176 GiB). A GPU cell lands on the cheapest of seven shapes that holds it: T4, L4, A10G, L40S, 4×L4, 8×T4 or 4×L40S. A multi-GPU shape only holds more for code that shards. CPU pods are priced by their dominant share of an m6i.xlarge, and GPU pods at the instance's on-demand price.
Approaches
Rules: a static request; a GPU if the code mentions CUDA, history × margin, else the declared pool size. Trees: 19-quantile gradient-boosted trees per axis plus a needs-a-GPU classifier. Zero-shot: a 27B model asked for JSON. Decision model: Qwen3-1.7B with LoRA and three pointer heads, trained by cross-entropy on 10,500 balanced runs (5.6 h on a T4). RL: that model, tuned by GRPO: 16 requests sampled per prompt from the three heads, rewarded by the simulator, with group-normalized advantages and a KL penalty to the supervised policy (6,000 prompts, 2.0 h on a T4).
Hybrids
Stacked: the decision model trained with the trees' estimate for all three axes in its prompt; training runs get out-of-fold estimates (5 folds by task). Stacked RL: the same RL phase started from the stacked model, with the same estimates in its prompts. Pool: on each axis, p ∝ p_treesw · p_llm1−w, with one w for all three axes and a no-GPU threshold tuned on validation, for the decision model, RL and both stacked models.

Key terms

Oracle
The request the measurements say is right on each axis: the smallest memory cell that holds the peak, the CPU cell that covers the busiest 15 seconds, and the GPU cell that lands on the cheapest shape the run fits, or no GPU for a CPU task.
Regret
A run's cost to SUCCEEDED, including retries and lateness, divided by the oracle's cost, minus 1, averaged over runs. It can go slightly negative on CPU tasks, where a brief throttle can cost less than the oracle's extra cores.
Decision model
An LLM whose language-model head is replaced by a head that scores each option written in the prompt. One forward pass gives a probability for every option; no text is generated (216 ms per request on a T4).
Out-of-fold
A prediction for a training run made by trees fit without that run's task, so the model learns how far to trust the trees on tasks they did not see.
GRPO
Group-relative policy optimization. Each sampled request's reward is compared with the others sampled for the same prompt, so no value network is needed.
Unseen families
Task families each bench held out of training, which test whether an approach generalizes to new code. For GPU big-2 they are recsys_train, knn_search and llm_generate.
