RightSizeCPU Bench

A task's CPU request is a guess made before it runs. Ask for fewer cores than the code uses and the kernel throttles it, so it runs slower; ask for more and the extra cores sit idle. This benchmark measures how well different approaches predict a task's peak CPU, as Union's own monitoring would see it, from the task's code and its input metadata. This page reports the big release, at the scale of the RightSizeMem bench.

Summary

  • With 5,628 training runs, the decision models lead on both splits. The 1.7B decision model predicts the peak within ±25% on 97.9% of test runs; the 4B reaches 97.6% on test and 86.1% on the two unseen families, the best of any approach there.
  • The zero-shot 27B is no longer the strongest approach. It was on the 220-run small release. Here it is close to the decision models on unseen families (83.7%) but scores 68.4% on test, because it misreads code with a serial phase followed by a parallel one (6%).
  • Trees match the decision models on familiar code and fall on new code. gbt-dist scores 94.6% on test and 68.4% on unseen families. On pyarrow's CSV reader it gets 48%, against 86–90% for the models that read the code.
  • The declared pool size is still a strong one-line rule (73.6% test, 79.4% unseen), with the same blind spots as before: 0% on I/O-bound code and 63% on Python thread pools under the GIL.
  • These shares are precise. With 1,634 test and 1,800 unseen runs, a share near 90% has a 95% interval of about ±1.5 points. The zero-shot 27B was scored on a 297 + 300 run subsample (about ±5 points).
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of code, such as a scikit-learn job that fits a random forest. A run is that task executed once on a particular set of input files. Each task in this release runs twice, on inputs of different sizes.
Cores, CPU request
CPU is measured in cores: 1 core is one CPU busy for the whole time, 2.5 cores is the work of two and a half CPUs. A task's CPU request, such as cpu="2", is what it asks the cluster for. Here it also acts as the limit.
Throttling
When a task tries to use more cores than its limit, the Linux scheduler (CFS) pauses it until the next period. Nothing is killed. The work just takes longer: a second that wanted 4 cores under a 2-core limit takes 2 seconds.
Peak CPU (the label)
The highest average core usage in any 15-second window of the run. This is the busiest value Union's task monitoring can show. See Why 15 seconds.
Mean CPU
Total CPU seconds divided by wall-clock seconds. A second, easier label. Peak and mean differ only for code with phases, such as a serial step followed by a parallel one.
Grid, cell
Predictions are chosen from a fixed list of 16 core counts, the way requests are written: 0.25, 0.5, 0.75, 1, 1.25, 1.5, 1.75, 2, 2.5, 3, 3.5, 4, 5, 6, 7, 8. One entry is a cell. The largest gap between neighbours is 25% (4 to 5).
Oracle
An imaginary approach that knows each run's measured peak in advance and asks for the smallest cell that covers it. Nothing can do better on accuracy.
Within ±25% (headline metric)
The share of runs whose predicted peak is within 25% of the measured peak, or within 0.25 core for small peaks. Higher is better. Because no two grid cells are more than 25% apart, the oracle always scores 100%.
Under-predicted
The share of runs whose predicted peak is below the measured peak, by any amount. A prediction of 4 cores for a peak of 4.05 counts as under, and is also within ±25%. These are the runs that would be throttled, most of them briefly.
MAE
Mean absolute error between the predicted and measured peak, in cores. Lower is better.
CPU regret
What the prediction costs, compared with the oracle, when it is used as the CPU limit: core-seconds reserved, plus a penalty for each second the run finishes late because it was throttled. 0% equals the oracle; a slightly negative value means brief throttling was cheaper than the oracle's idle headroom. Full definition under Scoring.
Test split
Runs of tasks whose code no approach saw during training, from the same 9 families used in training.
Unseen families
Runs from two whole families left out of training: DuckDB SQL and pyarrow's CSV reader. Each uses a pool-size API (SET threads, pa.set_cpu_count) that no training family uses.
Driver
What an approach has to understand to get a run right. threads: an explicit pool size the library honours. gil: a Python thread pool whose parallelism depends on whether the work holds the GIL. processes: a process pool, possibly capped by how many chunks of work there are. serial: single-threaded code. io: waiting dominates. phases: a serial phase, then a parallel one.
GIL
CPython's global interpreter lock. Only one thread runs Python bytecode at a time, so 6 threads looping in pure Python use about 1 core. Libraries such as zlib, hashlib and NumPy release the lock while they work, so their threads do run in parallel.
Cold start, history
A run's history is the earlier runs of the same task, with their input sizes and measured CPU. The first run of each task has none (a cold start); the second sees the first.
Arm, decoding
An arm is one approach being compared. Arms that output a probability for each cell need a rule, called decoding, to turn it into one prediction. Here they pick the cell most likely to be within ±25% of the peak. Argmax, the alternative, picks the single most likely cell.
Part 2 · Methodology

Why the label is a 15-second window

A benchmark for right-sizing should predict what the platform will measure, so the label copies Union's own metrics pipeline (read from the unionai/cloud repository):

  • The operator's Prometheus scrapes cAdvisor, the container metrics exporter, every 15 seconds. The kubernetes-cadvisor job inherits the global scrape_interval: 15s.
  • The console's task CPU chart is irate(container_cpu_usage_seconds_total[5m]): the rate between the last two scrapes, which is a 15-second average.

The benchmark therefore samples the workload's CPU time once per second and takes the busiest sliding 15-second average. Sliding, because the platform's scrapes land at an arbitrary moment in the run; the label is the worst any of those moments could see. In this release each workload loops for a time budget of 30, 45 or 60 seconds (half the small release's), so every run spans at least 2 windows (median 3.0, median run 45.6 s).

The dataset: real code, real parallelism

Every workload is generated from one of 11 families of task code. Within a family, a random generator picks the code-level choices that decide how many cores the task can use, and the size of its input files. Each generated task is a complete Flyte task: imports, a TaskEnvironment, and an @env.task function.

The big workload profile

To measure two workloads side by side in one pod (see Measurement), the big release draws pool sizes from 1, 2, 2, 3, 4, 4, 6 and 6, instead of up to 8, so every compute pool fits a 7-core slot. I/O-bound pools still go up to 16 threads, because their threads wait rather than compute, and Python thread pools stay GIL-bound whatever their size. Time budgets are 30, 45 or 60 seconds. The release name selects the profile, and every run records it.

From tasks to runs

This release has 450 tasks per family and 2 runs per task: 9,900 runs. Each run scales the task's input files by a factor between 0.5× and 2× of the family's base size, so a task's two runs are up to 4× apart. The first run of each task has no history; the second sees the first.

Splits

Tasks, not runs, are split, so both runs of a task land in the same split and no approach trains on code it is tested on. A hash of the task id sends 70% of tasks in the 9 training families to train, 10% to validation and 20% to test. The 2 held-out families go entirely to unseen. Validation is used only to tune each approach's settings; test and unseen are scored once.

How each run was measured

The spot node group that runs these pods reached its node limit at about 5 pods in the earlier releases, which would have meant about 60 hours for 10,000 runs. A pod-shape probe found that 15-CPU spot pods land on 16-core nodes, so the big release measures two workloads per pod, each pinned to its own 7 cores:

  1. Pin. A 15-CPU pod runs two slots. Each slot thread sets its own CPU affinity to 7 disjoint cores, and its child processes (input preparation and the workload) inherit it.
  2. Prepare. A child process writes the run's input files to local disk.
  3. Run. The task's module is imported into a fresh Python interpreter and its function is called on those files.
  4. Observe. The pod's cgroup counter would add up both slots, so each slot samples its own process tree once per second, keeping the CPU time of children that have already exited. Without that, the series stalled whenever a pool shut down.

Checked before spending 10,000 runs on it. The same 44 runs were measured both ways: two pinned slots per pod, and one run per pod read from the cgroup as in the earlier releases. All 44 paired labels came within ±25% of the cgroup label, 43 of 44 landed in the same cell, and the median ratio was 1.000 (range 0.97 to 1.45). In the big release itself, the sampled CPU seconds match the kernel's own accounting for each run (median ratio 1.000).

Pods. The 9,900 runs were split into 1,238 shards of 8, with 4 runs per slot. Between 4 and 9 pods ran at a time; measurement took 17.6 hours of wall-clock time. No run was lost.

From series to label. The peak label is the smallest grid cell that covers the busiest 15-second window. The mean label is the smallest cell that covers CPU seconds ÷ wall-clock seconds.

What every approach is allowed to see

Every approach gets the information a scheduler has when a run is submitted, and nothing more: the task's source code, each input file's metadata (only what its format exposes), and the task's earlier runs. No approach sees the generator's hidden choices, the family name or the driver. The prompt format is unchanged from the small release; here is one from that release, for a task that runs pure-Python work on a pool of 2 threads:

The approaches compared

Nine approaches, in four kinds. Every one makes the same two decisions for each run: a peak cell and a mean cell, each one of the 16 core counts. Every one sees the same information (see What every approach is allowed to see), and every tunable setting is chosen on the validation split only. Some approaches are read out two ways, which gives the 12 rows on the leaderboard.

Rules

static
Takes a quantile of the training runs' peaks and asks for that cell for every run. The quantile is tuned on validation (0.5, 0.75, 0.9 or 0.95). big-1 chose the median, 2.0 cores, so every run asks for 2 cores. The mean decision is the median training mean (also 2 cores). It is the floor any approach has to clear.
vpa
What the Kubernetes Vertical Pod Autoscaler does: the largest peak this task has been seen to use, times a margin, rounded up to a cell. The margin is tuned on validation runs that have history (0.6× to 2×); big-1 chose 0.9×. A run with no history, the first of each task, gets the static request. The mean decision is the largest past mean.
code-rule
The simplest algorithm that reads code. A regular expression finds every pool size the source declares: n_jobs=4, max_workers=6, SET threads = 3, set_num_threads(2), threadpool_limits(limits=4), pa.set_cpu_count(4), OPENBLAS_NUM_THREADS"] = "4", POLARS_MAX_THREADS"] = "2". It takes the largest, capped at 8, or 1 core if there is none, then multiplies by a factor tuned on validation (big-1 chose 0.8×) and rounds up to a cell. The mean is 0.8× the peak. It cannot tell a GIL-bound pool from a parallel one, or see a pool capped by its work items or a serial phase.

Features
71 numbers per run, computed from exactly what the LLMs see. Inputs: each file's byte size and whatever its format exposes (row counts, shapes, dtypes), RightSizeMem's input features. Code: whether each of 44 CPU-relevant tokens appears (ThreadPoolExecutor, use_threads=False, zlib.compress, phase 1, …), the largest declared pool size (the code-rule's number), how many pool sizes are declared, the smallest count of work items (n_estimators=, range(k)), log₂ of the largest numeric literal, and the number of lines. History: number of earlier runs, their largest and latest peak, and their largest mean.
Model
scikit-learn's HistGradientBoostingRegressor with the quantile (pinball) loss, 300 boosting rounds, learning rate 0.06, at most 31 leaves per tree. Each model predicts one quantile of log₂(peak cores); the log makes an error of 2× the same size at 1 core as at 4. A separate median model predicts mean cores.
Training
Each quantile model is fitted independently on the 5,628 training runs. gbt fits 6 quantiles (0.5 to 0.95) and keeps the one that scores best on validation; big-1 chose the median. gbt-dist fits all 19 quantiles from 0.05 to 0.95 and has nothing to tune.
Inference, gbt
Predict log₂(peak) at the chosen quantile, take 2 to that power, and round up to the smallest cell that covers it.
Inference, gbt-dist
The 19 predicted quantiles are sorted, so they cannot cross, and joined into a piecewise-linear CDF over log₂(cores), with the tails closed 1.5 doublings past the outermost quantiles. Integrating that CDF over each cell's range gives a probability for each of the 16 cells. The decoder then picks the cell with the highest probability of landing within ±25% of the peak (see Decoding).

LLM approaches: the shared prompt

All four LLM approaches read the prompt shown above: a system message (what the 15-second window is, that unsized pools get one thread, that a limit below the peak throttles), then the task code, this run's input metadata, the task's earlier runs, the two option lists and the answer format, in Qwen3's chat template. The three locally trained models run with thinking turned off. Their prompts are cut from the left to 2,048 tokens, so the option lists and the answer slot at the end are always kept.

Architecture
Qwen3-1.7B, a 28-layer decoder-only transformer, unchanged, with low-rank adapters (LoRA: rank 16, α 32, dropout 0.05) on all seven projection matrices of every layer. About 17M weights are trained, roughly 1% of the model; the base weights stay frozen. The output is the model's own language-model head.
Training
The target is the oracle's answer written as text, {"peak_cpu": "2.5", "mean_cpu": "2"}, followed by the end-of-turn token. The loss is ordinary next-token cross-entropy on those answer tokens only; the prompt tokens are masked out. Logits are computed only for the last few positions, because full-sequence logits over a 151k-token vocabulary do not fit a 16 GB GPU. 3 epochs over the 5,628 training runs: micro-batches of 8 with 2 accumulation steps (effective batch 16), AdamW at 2×10⁻⁴, 5% linear warm-up then cosine decay, gradient clipping at 1.0. That is 1,056 optimizer steps, with fp16 and a loss scaler (the T4 has no native bfloat16) and gradient checkpointing. It took 2.8 h on one T4, ending at a loss of 0.03 per answer token.
Inference, greedy
Generate up to 24 tokens, always picking the most likely next token, then parse the JSON. A margin of k cells can be added on top (k from 0 to 3, tuned on validation; big-1 chose 0). No answer failed to parse. Median 1.5 s per decision on a T4.
Inference, 8 samples
Generate 8 answers at temperature 1 and count how often each peak cell comes up (with a little smoothing). That turns a text generator into a probability for each cell, decoded like every other distribution. The mean is the most common sampled mean. Median 2.7 s per decision: sampling is how a generative model gets a distribution, and it costs one generation per sample.

Decision 1.7B: the pointer head

The decision model asks the same question of the same network with the same adapters and training data. The only change is the output: it does not write an answer. It scores every option in a single forward pass, the shape popularized by TypeSafe's Jev and the Strands Decider.

Architecture
The same Qwen3-1.7B and LoRA adapters, loaded without the language-model head, so the network outputs one hidden state per prompt token. The prompt ends with the two option lists, and everything after the task-specific part is identical for every run. Because prompts are cut from the left, each option's token sits at a fixed distance from the end, found once from the tokenizer. The head is pointer attention, one per decision: the hidden state at the answer slot (the prompt's last token) and the hidden state at each option's token both pass through a shared LayerNorm, are projected to 256 dimensions by a query matrix and a key matrix, and their scaled dot product is that option's score. That is 16 scores per decision, about 2.1M head weights in all. The options are read from the prompt rather than baked into the size of an output layer, so the same head can in principle rank a different list of options. That was not tested here.
Training
Cross-entropy of the 16 peak scores against the oracle's peak cell, plus 0.3 × cross-entropy of the mean scores against the oracle's mean cell. The LoRA adapters learn at 2×10⁻⁴ and the freshly initialised head at 10⁻³. The schedule is the SFT model's: 3 epochs, effective batch 16, 1,056 steps, warm-up then cosine, fp16 on one T4. It took 2.6 h, with the loss falling from 1.62 to 0.78 to 0.50 across the epochs.
Calibration
After training, a single temperature T is fitted on the validation split to minimize the negative log-likelihood of the true peak cell, searched over 0.3 to 5 (Guo et al., 2017). big-1 found T = 1.25, a slightly overconfident model softened. The logits are divided by T before the softmax, not the probabilities.
Inference
One forward pass over the prompt; no tokens are generated. That gives 16 calibrated probabilities for the peak, decoded to the cell most likely within ±25% (the leaderboard's "pointer" row) or to the single most likely cell (the "argmax" row). The mean is the most likely mean cell. Median 154 ms per decision on a T4, 10× faster than greedy SFT and 17× faster than the 27B.

Decision 4B

Identical, on Qwen3-4B: 36 layers, hidden size 2,560, about 33M LoRA weights and 2.6M head weights. To fit a 16 GB T4 in fp16 it trains with micro-batches of 4 and 4 accumulation steps (still an effective batch of 16), and for 2 epochs instead of 3 (704 steps, 3.8 h). Its fitted temperature is 1.14, and a decision takes 345 ms.

Decoding: from probabilities to one cell

gbt-dist, SFT with 8 samples and the decision models all end with a probability pj for each of the 16 cells. One decoder turns those into a prediction for all of them. For every candidate cell m it computes the probability that asking for m lands within ±25% of the peak, Σj pj · hit(m, j), where hit(m, j) is 1 if cell m is within the margin of a peak in cell j. It picks the m with the highest value, with ties going to the larger cell, because an under-prediction throttles while an over-prediction only idles. Argmax instead picks the single most likely j. The two differ when the probability is spread over neighbouring cells: the decoder can pick a cell between two likely ones that is within ±25% of both.

Scoring: accuracy first, cost alongside

The headline is accuracy, because the task is to predict the peak. Cost is reported next to it, because it shows which mistakes matter. Each approach's predicted peak is used as the run's CPU limit and replayed against that run's own measured per-second series:

  1. Each second that wanted u cores under a limit L takes max(1, u ÷ L) seconds. Throttling stretches the work and never kills it.
  2. The run pays L × its stretched duration, in core-seconds.
  3. A late result costs something. Each second of delay adds one oracle core-second per oracle core (the oracle's limit × seconds late).
  4. CPU regret = total core-seconds across all runs ÷ the oracle's total − 1.
Worked example

A run uses a steady 4 cores for 60 seconds. The oracle asks for 4 and pays 4 × 60 = 240 core-seconds.

  • Asking for 5 cores: 5 × 60 = 300 core-seconds, 25% over the oracle. The fifth core sits idle.
  • Asking for 3 cores: each second takes 1.33 s, so the run takes 80 s. 3 × 80 = 240, plus 20 s late × 4 = 80. Total 320, or 33% over.
  • Asking for 2 cores: 120 s. 2 × 120 = 240, plus 60 s late × 4 = 240. Total 480, or 100% over.

Why cost is not the headline. Throttling only stretches time, so for a run that sits at its peak only part of the time, asking for a little less than the peak can be cheaper in core-seconds than asking for the peak. A decoder that minimizes expected cost therefore leans low, which is the opposite of the task. Approaches that output probabilities are decoded for accuracy: the cell most likely to land within ±25% of the peak.

The declared pool size is a strong hint, and sometimes wrong

Each dot is one run: the largest pool size its code declares, against its measured peak. If every pool ran fully in parallel, the dots would sit on the diagonal.

A random sample of 660 of the 9,900 runs of big-1. "none" means the code declares no pool size (one thread here). Dots are spread sideways slightly so overlapping runs stay visible.

How to read this
  • The dashed diagonal is "peak = declared pool". Blue dots (explicit pools) mostly sit on or just under it, which is why the code-rule works on them.
  • Orange dots (thread pools under the GIL) split in two: pure-Python work stays at 1 core whatever the pool size, while zlib and hashlib work reaches the pool size.
  • Red dots (I/O-bound) sit near zero even with 16 threads, because the threads spend their time waiting. Purple dots (phases) peak at the pool size but average less.
  • Green dots (process pools) fall below the diagonal when there are fewer chunks of work than processes.

The leaderboard

Solid bar: test split (1,634 runs). Outline: unseen families (1,800 runs). The zero-shot 27B row is a 297 + 300 run subsample. Higher is better; the oracle scores 100%.

How to read this
  • Each row is one decision rule. The bar length is the share of runs whose predicted peak was within ±25% of the measured peak.
  • The solid bar is new code from familiar families; the outlined bar is code from the two families no approach trained on. A large drop from solid to outline means the approach depends on having seen similar code.
  • The trees drop the most (94.6% to 68.4%). The decision models drop too (97.9% to 83.9%, 97.6% to 86.1%), but stay level with the zero-shot 27B, which has no training to lose.
  • Decoding matters on unseen code: the decision models' argmax rows trail their decoded rows by 5 to 9 points there.
Columns
  • within ±25%: the headline, on each split (higher is better).
  • under: share of runs predicted below the peak by any amount. Accuracy decoding often picks the cell just under a peak, inside the ±25% margin; argmax rarely does (lower is better, but zero is easy if you over-predict everything).
  • MAE: mean absolute error of the predicted peak, in cores (lower is better).
  • CPU regret: cost over the oracle when the prediction is used as the limit (lower is better; negative means brief throttling cost less than the oracle's headroom).
  • mean ±25%: the same accuracy measure for the second decision, mean CPU.
  • Bold marks the best value in each column.

Where each approach goes wrong

Splitting the test runs by driver shows what each approach does and does not understand. Every driver now has at least 164 test runs (33 for the zero-shot subsample).

Share of test runs predicted within ±25%, by driver. Cell shading is proportional to the value.

How to read this
  • The decision models score 96–100% on every driver: they learned the GIL, the process-pool cap, I/O waits and phased code from training data.
  • code-rule is perfect on serial code and 91% on explicit pools, but 63% under the GIL (it reads max_workers=6 on pure-Python threads as 6 cores) and 0% on I/O.
  • zero-shot 27B gets serial code right but phased code wrong (6%): it predicts the average of a serial and a parallel phase, not the parallel peak. This, more than anything, is why it trails on test.
  • The trees learn every driver well (85–100%) on familiar families; their weakness is new code, not any driver.

Cost-optimal decoding, with sharper probabilities

The decision model outputs a probability for each cell, so it can be decoded two ways from the same predictions. The chart decodes it by lowest expected cost, as the penalty for each second of delay grows from 0 to 8 oracle core-seconds, and compares that with decoding for accuracy.

Decision 1.7B, pointer head, test split. Lines: cost-optimal decoding at each delay penalty. Dashed horizontal lines: accuracy decoding, the setting used on the leaderboard.

How to read this
  • Below a penalty of 1, cost-optimal decoding throttles on purpose: over 93% of runs under-predicted and under 42% within ±25%.
  • From a penalty of 1 up, it lands within ±25% on 94–98% of runs, close to accuracy decoding (97.9%). With 5,628 training runs the model's probabilities are sharp enough that both decoders usually pick the same or a neighbouring cell. On the small release the two disagreed far more.
  • The under-prediction share keeps falling as the penalty grows (43% at 1, 4% at 4), at the cost of over-predicting.

What the big release supports

  • The pinned-pair measurement holds at scale. 9,900 runs measured with no losses in 17.6 hours, with labels that matched one-run-per-pod cgroup labels on the 44-run check.
  • Given enough data, a 1.7B decision model is the best CPU predictor on familiar code (97.9%), ahead of trees (94.6%) and SFT (94.9% greedy), with the lowest MAE (0.24 cores).
  • On new code, size and reading the source matter more than data. The 4B decision model (86.1%), the zero-shot 27B (83.7%) and the 1.7B (83.9%) are close; the trees (68.4%) are not.
  • The zero-shot 27B's weakness is specific: phased code, at 6%. A prompt that names the busiest window more plainly might fix it; that was not tried.
  • Not yet shown: whether a decision model trained on more families closes the unseen gap. Every remaining gap is on the two held-out families.

Assumptions and limits

  • Workloads are short kernels of real tasks: 30–60 seconds, 2–4 platform windows. A run with only 2 windows has fewer chances for a sliding peak than a long task.
  • Pools are at most 6 threads for compute (16 for I/O waits) inside a 7-core slot. Peaks above 7 cores are out of this release's range.
  • Two workloads share a pod. They have disjoint cores, but share the memory bus and caches, which can slow memory-heavy workloads slightly. The 44-run check bounds this for the label (median ratio 1.000), not for run time.
  • The throttling model stretches each second by u ÷ L. Real CFS throttling works in 100 ms periods and can add latency spikes the model does not capture.
  • The code-rule and the trees' 44 code tokens were written by the person who wrote the generator, which makes both baselines generous.
  • Unseen families are only two, both with an explicit pool-size API.
