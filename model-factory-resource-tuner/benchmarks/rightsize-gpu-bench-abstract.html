RightSizeGPU Bench: choosing a GPU from code

Initial results · small release (small-1) · a 5× larger release is running
Abstract

A GPU task picks its device before it runs. If its peak GPU memory does not fit, it dies with a CUDA out-of-memory error and is retried on a bigger GPU; if the GPU is larger than needed, the cluster pays for idle memory. RightSizeGPU Bench measures how well different approaches predict a PyTorch task's peak GPU memory, which decides the cheapest GPU that holds it (T4 at 15 GiB, L4 at 22 GiB, L40S at 44 GiB on this cluster), and its mean GPU utilization. The small release has 128 runs of generated PyTorch task code from 8 families, each measured on a T4 with NVML, the library Union's GPU monitoring reads, and each lasting 2–3 minutes so it covers at least 4 of the platform's 30-second samples. Every approach sees only the code, the input metadata and the task's earlier runs, and is scored on the share of runs whose predicted peak is within ±20% of the measured one.

With 60 training runs, no approach predicts GPU memory reliably yet. The best is a rule on input size at 54.5% of test runs, and a fine-tuned 1.7B model at 50.0% on two families held out of training; a single static request manages 9.1%. Dollars barely separate approaches, because 124 of 126 usable runs fit on a T4, the cheapest GPU, so any prediction up to 15 GiB costs the same. Utilization barely varies either: 108 of 126 runs averaged 90–100%. These results establish that the benchmark measures what the platform measures, end to end, in 40 minutes and 5.7 T4-hours. A release 5 times larger is running to rank the approaches.

Four findings

  1. 55% / 50%GPU memory is the open problem at this size. The size rule leads on test (54.5%) and fine-tuned SFT on unseen families (50.0%), and the history-based rule is level with both. The 1.7B decision model, trained on only 60 runs, put most of its probability on one size for every run, so its two decodings score identically. It needs the larger release before it says anything.
  2. 124 of 126On this cluster the device choice is almost free. Nearly every run fits on a T4, so a prediction of 4 GiB and one of 12 GiB cost the same. An earlier scoring that decoded for lowest cost made every probabilistic approach predict 15 GiB for everything. Memory accuracy, which a scheduler needs to pack and share GPUs, is therefore the headline, and the device and dollars follow from it.
  3. 108 of 126Utilization saturates. GPU_UTIL counts the share of time any kernel is running, so a constant "90–100%" is right for about 9 in 10 runs. Only the data-loader family with per-pixel Python augmentation and some recommender runs leave the GPU idle. The zero-shot 27B model does worst here (41% within 10 points on unseen families): it assumes small models idle the GPU, which by this metric they do not.
  4. 7 runsConvolutional nets fill the GPU. cuDNN's algorithm search grows into whatever memory is free, so 7 runs peaked at the T4's full 15 GiB and still succeeded. A platform reading peak memory for such a task sees the GPU's size, not the task's need. These runs are scored on device choice only.
Setup

How the benchmark works

Workloads
8 families of PyTorch code: a tabular MLP, a CNN, a GPT-style language model, transformer-encoder inference, a two-tower recommender, a CNN starved by its CPU data loader, a blocked similarity matrix, and nearest-neighbour search. A generator varies model width and depth, batch, sequence length, vocabulary, mixed precision, gradient checkpointing, optimizer, and what is kept on the GPU. Each task runs twice, on inputs 0.5× to 2× its base size, for 120 to 180 seconds.
Labels
Each run executes alone on a T4. NVML is sampled every 0.5 seconds: memory.used (what DCGM_FI_DEV_FB_USED reports, including the CUDA context and PyTorch's cached memory) and utilization.gpu. The memory label is the smallest of 12 sizes (1 to 44 GiB) covering the peak; runs that ran out of memory are re-measured on an L40S. Utilization is labelled in 10-point buckets.
Splits
Split by task: 60 train, 12 validation and 22 test runs from 6 families, plus 32 runs from 2 families held out entirely (the recommender and nearest-neighbour search). 2 runs that failed even on the 44 GiB L40S are excluded.
Approaches
Rules: one static request; the task's largest past peak times a margin; a power law of input size. Trees: gradient-boosted quantile regression on 70 features, and the same trees read as a distribution. Autoregressive LLMs: a zero-shot 27B model, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision model: the same LoRA setup with a head that scores each option written in the prompt. All fine-tuning on one T4.

Key terms

Peak GPU memory
The most GPU memory in use at any moment of the run. A run needs a GPU whose usable memory covers it.
Within ±20%
The predicted peak is within 20% of the measured peak, or within 0.5 GiB for small peaks. The headline metric.
Device ladder
T4 (15 GiB, $0.53/h), L4 (22 GiB, $0.98/h), L40S (44 GiB, $2.24/h). A prediction runs on the cheapest GPU that holds it. The A10G (22 GiB, $1.21/h) is never the cheapest.
GPU regret
Dollars to finish every run, counting a failed attempt up to the point of its peak, the retry on the next GPU up, and one oracle-priced run of delay per OOM, divided by the oracle's dollars, minus 1.
GPU utilization
The share of time a GPU kernel was running, averaged over the run. It does not measure how much of the GPU each kernel used.
Why 2–3 minutes
Union's dcgm-exporter samples the GPU every 30 seconds, so a run needs a few minutes for the platform to see it. Keeping runs short keeps the benchmark's GPU usage small.
