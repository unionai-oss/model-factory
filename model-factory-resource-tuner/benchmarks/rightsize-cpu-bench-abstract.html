RightSizeCPU Bench: predicting peak CPU from code

Initial results · small release (small-1) · a 4× larger release is running
Abstract

A task's CPU request is set before it runs. Below the task's real peak, the kernel throttles it and it finishes late; above it, cores sit idle. RightSizeCPU Bench measures how well different approaches predict a task's peak CPU: the busiest 15-second average, which is exactly what Union's task monitoring can show, because Prometheus scrapes container CPU every 15 seconds. The small release has 220 runs of generated Flyte task code from 11 workload families, each run executed alone in a 9-CPU pod and measured from the container's cgroup. Every approach sees only the source code, the input files' metadata and the task's earlier runs, and is scored on the share of runs whose predicted peak lands within ±25% of the measured one.

Peak CPU turned out to be a property of the code: a task's two runs, on inputs up to 4× apart, agree to within 0.7% at the median. So approaches separate by how well they read code. A single static request is within ±25% on 35% of test runs. Gradient-boosted trees reach 73% on test but fall to 48% on two families held out of training. A one-line rule that reads the largest declared pool size reaches 81% and 95%, but fails thread pools held back by Python's GIL (25%) and I/O-bound code (0%). A zero-shot 27B model reaches 79% and 93% with the lowest error of any approach (0.43 cores), and a 1.7B decision model trained on only 116 runs reaches 71% and 83%. With 52 test runs, differences under about 10 points are within noise.

Four findings

  1. 0.7%Peak CPU is decided by the code, not the input. The two runs of a task differ by 0.7% at the median (11% at the 90th percentile). What sets the peak is a pool size written in the code, such as n_jobs=4 or SET threads = 6, and whether that pool can really run in parallel. Trees on input features cannot see this, which is why they lose most on unseen families (73% to 48%).
  2. 79% / 93%A zero-shot 27B model is the strongest approach on balance. Without training, it has the lowest error (0.43 cores on test, 0.50 on unseen) and the lowest cost on test (15.4% over the oracle), and it handles both explicit pools and the GIL. Its weak spot is code with a serial phase followed by a parallel one (1 of 8 right): it predicts the average rather than the peak.
  3. 25% / 0%Reading the declared pool size is a strong rule with predictable failures. The code-rule is perfect on serial, process-pool and phased code, but scores 25% on pure-Python thread pools (8 threads under the GIL use about 1 core) and 0% on I/O-bound code. Its 95% on unseen families reflects those two families, which both honour their declared pool.
  4. 71% / 83%A small decision model learns CPU from 116 runs. Qwen3-1.7B with a pointer head that scores each option is ahead of the trees on unseen code (83% against 48%). Choosing the option most likely to be within ±25% beats picking its single most likely option by 8 to 15 points. Decoding it for lowest cost instead would under-predict 60% of runs, because a throttled second costs less than an idle core.
Setup

How the benchmark works

Workloads
11 families of task code: NumPy BLAS, polars, DuckDB SQL, scikit-learn ensembles, pandas, Python thread pools, process pools, PyTorch on CPU, pyarrow CSV, I/O-bound fetch loops, and a serial phase followed by a parallel one. A generator varies the choices that decide parallelism (pool sizes, GIL-bound or GIL-releasing work, chunk counts, batch sizes). Each task runs twice, on inputs 0.5× to 2× its base size, and loops for 60 to 90 seconds.
Labels
Each run executes alone in a 9-CPU spot pod. Its CPU is read every second from the container cgroup's cpu.stat, the counter cAdvisor exports. The label is the smallest of 16 core counts (0.25 to 8) that covers the busiest sliding 15-second window. Every run spans at least 4 windows.
Splits
Split by task: 116 train, 12 validation and 52 test runs from 9 families, plus 40 runs from 2 families held out entirely (DuckDB SQL and pyarrow CSV). Settings are tuned on validation; test and unseen are scored once.
Approaches
Rules: one static request; the task's largest past peak times a margin; the largest pool size the code declares, times a factor. Trees: gradient-boosted quantile regression on 71 numeric features, and the same trees read as a distribution over cells. Autoregressive LLMs: a zero-shot 27B model, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision model: the same LoRA setup with a head that scores each core count written in the prompt. All fine-tuning on one T4 GPU.

Key terms

Peak CPU
The highest average core usage in any 15-second window of the run: the busiest value Union's monitoring can show.
Within ±25%
The predicted peak is within 25% of the measured peak, or within 0.25 core for small peaks. The headline metric. No two of the 16 options are more than 25% apart, so the oracle always scores 100%.
Throttling
A task asking for more cores than its limit is paused by the scheduler, so its work takes longer. It is never killed.
CPU regret
Core-seconds reserved (limit × stretched duration) plus one oracle core-second per oracle core for each second late, summed over runs, divided by the oracle's total, minus 1.
GIL
Python's global interpreter lock. Threads running pure Python share one core; libraries such as zlib, hashlib and NumPy release it and run in parallel.
Unseen families
The two families no approach trained on. They test whether an approach generalizes to new code and new pool-size APIs.
