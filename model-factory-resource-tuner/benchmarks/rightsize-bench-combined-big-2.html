RightSize Bench

A task's resource request is three guesses made before it runs: how much memory, how many CPU cores, and whether it needs a GPU and which machine. This benchmark scores approaches on the whole request at once, in dollars, against the cheapest request that would have worked. Release big-2 swaps in a new GPU corpus that spans the cluster's whole GPU machine ladder, and adds two ways of combining the gradient-boosted trees with the language models.

Summary

  • Stacking the trees into the decision model, then tuning it with RL, gives the lowest test regret of any release so far. Read by argmax, it costs 3.2% more than the oracle on test runs. The best arm without the trees costs 9.8% (RL 1.7B, argmax), and round 20's best was 8.0%. It also has the lowest dollar regret (13.0%) and the highest first-attempt success (97.8%), and 92.2% of its runs have all three axes right.
  • The same arm is one of the worst on unseen task families: 102.0% regret. The GPU axis causes it. On unseen GPU tasks it picks the oracle's machine 35.2% of the time, against 77.1% for RL without the trees. RL from a stacked start learns to follow the trees' estimate, and the trees fail on new GPU code (167.1% GPU regret).
  • On unseen families, RL without the trees is best: 35.5% decoded cost-aware, against 48.0% for the hand-written rules and 90.8% for the trees.
  • Only one hybrid beats its language model on both splits: the trees pooled with the supervised decision model (6.9% test and 52.2% unseen, against 14.0% and 58.8%). Every other hybrid is better on test and worse on unseen families.
  • Unseen regret cannot be compared with round 20. The GPU bench's unseen families changed, and now include two multi-GPU families. Memory and CPU rows are the same runs as in round 20 and can be compared.
  • The GPU corpus is thinner at the top than planned. Multi-GPU nodes mostly did not schedule, and 1,569 GPU runs were censored, most of them large sharded runs.
Part 1 · Definitions

Terms used on this page

request
One choice on each of three axes: a memory cell, a CPU cell, and a GPU cell or "none". Each axis uses its own bench's grid.
machine shape
A GPU instance type the cluster can provision, such as one T4 or four L40S. A GPU cell lands on the cheapest shape that holds it.
oracle
The request each run's measurements say is right: the smallest memory cell that holds the measured peak, the CPU cell that covers the busiest 15 seconds, and the GPU cell that lands on the cheapest shape the run fits (or no GPU for a CPU task).
regret
A run's cost under the approach's request, divided by its cost under the oracle's, minus 1, averaged over runs. 0% is the oracle; 100% is twice its cost. Each run counts once, however much it costs. Lower is better.
first attempt ok
Share of runs whose first attempt succeeds: no host OOM, no CUDA OOM, and a GPU when the task needs one. Throttling does not count as a failure.
all axes right
Memory fits and is at most one cell above the oracle, CPU is within ±25% of the busiest 15 seconds, and the GPU choice lands on the oracle's machine. A GPU task is scored on the GPU choice only.
source
Which bench a run came from: mem (RightSizeMem), cpu (RightSizeCPU) or gpu (RightSizeGPU). No approach is told the source.
test / unseen
Test runs are new tasks from task families the approaches trained on. Unseen runs (OOD) come from families held out of training on each bench.
argmax / decoded
Two ways to turn a model's probabilities into one request. Argmax takes the most likely cell on each axis. Decoded uses each bench's cost-aware decoder (see Decoding).
hybrid
An approach that combines the trees (gbt-dist) with a language model. There are two kinds on this page, stacked and pooled.
stacked
The trees' prediction is written into the decision model's prompt, and the model is trained with it there (see Stacking).
out-of-fold
A prediction for a training run made by trees that were fit without that run's task. It is as wrong as the trees would be on a new task from a familiar family.
pooled
The trees' probabilities and a decision model's probabilities are multiplied together, with a weight, and renormalized (see Pooling). Nothing is retrained.

What is new in big-2

  1. A new GPU corpus, GPU big-2. In big-1, 94.8% of usable GPU runs fit a T4, so the device choice was nearly trivial. GPU big-2 has larger workloads and new families, measured over every GPU shape the cluster provisions, including multi-GPU machines. Three families shard their model over every visible GPU. In GPU big-2, 74.7% of usable runs fit a T4.
  2. The GPU label is the oracle's cell. It is the cell that lands on the cheapest shape the run fits, not the cell that holds the raw peak. For sharded code the two can differ: a run whose share does not fit four L4s has to ask past 88 GiB to land on eight T4s.
  3. The CPU corpus is pinned to big-1 and memory stays at v2. The memory and CPU rows are the same runs as in round 20.
  4. Two hybrids of trees and language models: a stacked decision model, RL from that stacked model, and a per-axis opinion pool of the trees with each decision model. That adds 12 rows to the leaderboard.

The dataset: three measured corpora, one schema

Every run is real task code executed in a pod and measured, collected by the three single-axis benches. The combined bench reads their published corpora as factory sources and rewrites them to one schema. A run keeps the labels its bench measured, and the axes its bench did not measure are left unscored.

On a shape a run was not measured on, fit is modelled: a single-GPU run fits if its whole peak fits one GPU; a sharded run fits if its share, (peak − 0.5 GiB) × imbalance ÷ n + 0.5 GiB, fits each GPU. One cost model for all three axes

Each axis fails the way it fails on its own bench, all in one simulation. The cost is the dollars it takes to get the run to SUCCEEDED, including retries and lateness.

  1. Memory below the peak: the pod is OOM-killed when the run reaches its peak, then retried with double the memory.
  2. CPU below the busiest window: the run is throttled. Its measured per-second CPU series is replayed under the limit, and each second at u cores takes max(1, u ÷ limit) seconds. Memory-bench runs have no series, so their mean cores are used instead.
  3. GPU too small: a CUDA OOM at the peak, then a retry on the next shape up that the run fits under the fit model above. No GPU for a GPU task: it fails at start (no CUDA device), and the platform retries it on a T4. A GPU for a CPU task: it runs, at the GPU instance's price for the whole run.
  4. Delay costs something: each retry adds one oracle cost, and each hour late adds one oracle hourly price. Every attempt also pays 0.02 h of start-up.
Worked example

A one-hour CPU task needs 4Gi of memory and a steady 2 cores. The oracle asks for 4Gi and 2 cores: a dominant share of 0.5, so $0.096/h, or about $0.098 with start-up.

  • Asking for 8Gi and 2 cores costs the same. Memory is still not the dominant share, so the extra memory is free here (0% regret).
  • Asking for 4 cores doubles the share: about 100% regret.
  • Asking for 1 core halves the price, but the run takes 2 hours, and the hour late costs one oracle hour: about 99% regret.
  • Asking for 2Gi kills the run at its peak (here half-way through), and the retry runs at 4Gi. Together with the retry penalty that is about 151% regret.
  • Asking for a T4 runs it on a $0.526/h GPU instance: about 450% regret. This is the most expensive mistake a request for a CPU task can make on a T4, and a larger GPU cell costs more.

What every approach is allowed to see

The same information as each single-axis bench: the task's source code, the metadata of this run's inputs (file sizes, formats, row counts, shapes, dtypes), and what earlier runs of the same task measured. That last part is peak memory, peak and mean cores, peak GPU memory and GPU utilization, whichever that task's bench recorded. Nothing tells an approach which bench a run came from, or its task family. Whether a task needs a GPU, and whether its code shards, has to be read from the code. A test pins this boundary: none of the features or prompt fields can see the run's own measurements.

The hybrids see nothing more. The trees' prediction they use is computed from the same inputs, so it carries no information the boundary does not already allow.

Rules

static
One request for every run: a training quantile of memory need and of CPU need (each 0.5, 0.75, 0.9 or 0.95, tuned on validation), and no GPU. big-2 chose the 0.9 quantile for memory and the median for CPU, as big-1 did. It never asks for a GPU, so every GPU task fails at start and is retried on a T4.
rules
What a platform team would write. GPU: if the code mentions CUDA ("cuda", torch.cuda, .to(device), device =), ask for a GPU sized from the task's largest past GPU peak × a margin, or a training quantile of GPU peaks on a first run. Memory: the largest past peak × a margin, or the static cell. CPU: the largest past peak × a margin; with no history, the largest pool size the code declares (RightSizeCPU's code rule), else 1 core. big-2 chose margins of 1.5× for memory and 1.0× for CPU and GPU, and the median GPU peak for first runs.

Gradient-boosted trees (gbt-dist)

Features
The union of the three benches' features: input metadata, each bench's code tokens and code numbers (declared pool sizes, work items, model sizes, batch sizes), four CUDA flags, and history over the unified schema.
Model
For each axis, 19 HistGradientBoostingRegressor quantile models (q = 0.05 to 0.95, pinball loss, 300 rounds, learning rate 0.06, 31 leaves) on log₂ of the need. The memory and CPU models train on the CPU-task rows and the GPU models on the GPU-task rows. A HistGradientBoostingClassifier predicts whether the task needs a GPU.
Inference
Each axis's 19 quantiles become a piecewise-linear CDF and then a probability for each cell. The GPU distribution is P(no GPU) = 1 − P(needs GPU), with the rest spread over the GPU cells. The request is then decoded per axis (see Decoding). The trees are also the "trees" half of every hybrid.

zero-shot 27B

Prompt
One system message for all three decisions: memory is a hard limit, CPU below the busiest 15 seconds throttles, unsized pools get one thread, GPU memory lands on the cheapest machine that holds it (with every shape's size and price), a multi-GPU machine only helps code that spreads its model over every GPU, a GPU task with no GPU fails at start, and a GPU on a CPU task is paid for the whole run. Then the code, the inputs, the history, the three option lists, and {"memory": …, "cpu": …, "gpu": …} as the answer format.
Inference
qwen38-27b on the cluster's shared vLLM, at temperature 0 with up to 1,024 tokens. The last JSON object with a usable memory answer is parsed, and each value is rounded up onto its grid. Unparseable answers fall back to 4Gi, 1 core and no GPU, and are counted: 82 of 586 on big-2. It is scored on a family-stratified sample: 286 test runs and 300 unseen runs.

Decision 1.7B: one forward pass, three pointer heads

The same pointer decision model as the single-axis benches, with a third decision. It reads the same prompt as the 27B and generates nothing. It scores every option of every axis in one forward pass.

Architecture
Qwen3-1.7B with LoRA adapters (rank 16, α 32, dropout 0.05) on all seven projections of every layer, loaded without its language-model head. Each option's token sits at a fixed distance from the end of the prompt, because prompts are cut from the left to 2,048 tokens and the options come last. The head is a shared LayerNorm plus one query projection and one key projection per axis. An option's score is the scaled dot product of the answer slot's projected state with that option token's.
Training
The sum of three cross-entropies against the oracle's cells, with an axis left out where it was not measured (memory and CPU on GPU runs). 2 epochs over the 10,500 balanced training runs: micro-batches of 8 with 2 accumulation steps, AdamW at 2×10⁻⁴ for the adapters and 10⁻³ for the head, 5% warm-up then cosine decay, fp16 with a loss scaler and gradient checkpointing on one T4. It took 5.6 h, with the loss going from 2.66 in epoch 1 to 1.36 in epoch 2.
Calibration
One temperature per axis, fitted on validation by the negative log-likelihood of the oracle's cell: 1.14 for memory, 1.09 for CPU and 0.94 for GPU.

Decoding: from probabilities to one request

gbt-dist, every decision model and every pool end with a probability for every cell of every axis. The decoded rows turn those into a request with each bench's own decoder:

  • GPU first: no GPU when P(none) is at least a threshold tuned on validation (0.3 for every arm on big-2). Otherwise, the GPU cell is chosen from the remaining probability by RightSizeGPU's decoder.
  • Memory: RightSizeMem's Bayes decoder, the cell with the lowest expected cost once an OOM's retry is priced in. It leans toward over-asking.
  • CPU: RightSizeCPU's decoder, the cell most likely to land within ±25% of the busiest window.

The argmax rows take the most likely cell on each axis. For a supervised model, that is the cell most likely to be the label. It ignores that asking one cell too low can cost far more than asking one cell too high.

RL 1.7B: training on the cost itself

The supervised model learns to imitate the oracle's cells. Imitation cannot see two things the cost model cares about. First, the axes interact: on a GPU node, memory and CPU are free, while on a CPU node a GPU is the most expensive mistake there is. Second, asking low costs more than asking high, by an amount the label does not carry. The RL arm starts from the supervised model and maximizes the bench's own reward directly: minus the run's cost ratio under the same simulator that scores the leaderboard, capped at 20.

for each batch of 8 prompts:                                   (6,000 training prompts, 1 epoch, 375 steps)
    one forward pass  →  P(memory), P(cpu), P(gpu)  per prompt
    sample K = 16 joint requests per prompt from the three heads     (no text is generated)
    reward_k  = − min(cost(request_k) ÷ oracle cost, 20)          the leaderboard's simulator
    advantage = (reward_k − mean over the 16) ÷ std over the 16      group-normalized, as in GRPO
    loss      = − mean( advantage × Σ_axis log P(chosen cell) )
                + 0.05 × KL( current policy ‖ supervised policy )
    a GPU task's memory and CPU terms are left out (they do not change its reward)
Method
GRPO (group-relative policy optimization) without generation. Each prompt's 16 sampled requests are a group, and each request's advantage is its reward relative to the rest of its group, so no value network is needed. Sampling 16 requests costs nothing beyond the one forward pass, because the policy is three categorical distributions, not a sequence of tokens.
Prompts
6,000 training runs, balanced across the three sources: half of them runs the supervised model did not train on, and half that it did.
Settings
AdamW at 3×10⁻⁵ for the adapters and 10⁻⁴ for the head, micro-batches of 8 with 2 accumulation steps, 5% warm-up then cosine decay, KL coefficient 0.05 against the supervised policy's distributions (computed once, before any update). 2.0 h of RL on one T4.
Read-out
The same calibration and decoding as the supervised model. The calibrated temperatures hit the calibrator's cap of 5.0 for memory and CPU (4.5 for GPU). The RL heads are sharp, and they are no longer trying to predict the label.

Stacked 1.7B: the trees' estimate in the prompt

The trees and the language models fail differently. The trees read numbers exactly but cannot read code they have no feature for. The language models read the code but read numbers as tokens. Stacking gives the decision model the trees' answer as one more piece of its prompt, and lets training decide how far to trust it.

The hint
For each axis, the trees' two most likely cells with their probabilities, and the trees' decoded pick for all three axes. The GPU part gives P(no GPU) first, and the two most likely GPU cells only when P(no GPU) is below 99%. Code: bench_all/prompting.py hint_text.
Out-of-fold hints
A training run's hint comes from trees fit without its task: the training runs are split into 5 folds by task (a hash of the task id, so both runs of a task share a fold), and each fold's hints come from trees fit on the other four. Validation, test and unseen runs get hints from trees fit on all of train. Without this, the model would learn to trust trees that had already seen the answer. Code: bench/hybrid.py crossfit; bench_all/stations.py all_hints, hinted_all_corpus.
Training
The same model, settings and 10,500 balanced runs as decision 1.7B. It took 6.1 h. The loss went from 1.46 in epoch 1 to 1.00 in epoch 2, lower than the plain model's 2.66 and 1.36: the hint makes the label easier to predict.
Calibration
1.14 for memory, 1.14 for CPU and 0.99 for GPU.

Stacked RL 1.7B

The same RL phase as RL 1.7B, started from the stacked model instead of the plain one. The stacked arm saves its hints with the model, so every RL prompt carries the same trees' estimate as in supervised training. Same 6,000 prompts, settings and 375 steps; 2.2 h on one T4. The calibrated temperatures are 5.0 (the cap) for memory and CPU and 2.4 for GPU. Code: bench_all/stations.py rl_all_policy with base_arm="stack-jev-pointer".

Pool: a weighted product of two distributions

The pool needs no new training. It takes the trees' calibrated probabilities and a decision model's calibrated probabilities over the same cells, and combines them on each axis:

for each axis (memory, cpu, gpu):
    p_pool(cell) ∝ p_trees(cell)^w · p_llm(cell)^(1 − w)          a logarithmic opinion pool, renormalized
w ∈ {0, 0.1, …, 1}, one w shared by the three axes
no-GPU threshold ∈ {0.3, 0.5, 0.7, 0.8, 0.9, 0.95, 0.98}
pick (w, threshold) with the lowest mean regret on val, then decode (and read by argmax)

w = 0 is the decision model alone and w = 1 is the trees alone. Where both put weight on a cell, the pool does too. Where one gives a cell almost no probability, the pool does not pick it. Code: bench/hybrid.py log_pool; bench_all/stations.py pool_all.

Each hybrid against its language model

A hybrid is worth having if it beats both of its members. The trees are the same member for all of them: 15.4% on test and 90.8% on unseen families. Each row below compares a hybrid with the language model it was built from, read out the same way.

Mean regret. Δ is the hybrid minus its language model, in points; negative is better. Stacked RL is compared with RL from the plain model. pool-stack-jev-pointer-argmax is identical to stacked 1.7B argmax (w = 0) and is left out.

How to read this
  • On test, nine of the eleven hybrids beat their language model, by up to 17.5 points. The pool of stacked 1.7B is unchanged (w = 0), and the pool of stacked RL read by argmax is worse (5.0% against 3.2%).
  • On unseen families, only one hybrid is better than its language model: the pool of the trees with the plain decision model (52.2% against 58.8%), which is also 7.1 points better on test. Its argmax read-out misses by 0.3 points on unseen. The others are worse by up to 54 points.
  • Some hybrids are worse on unseen families than both of their members: stacked 1.7B (94.6% decoded, 125.8% argmax), stacked RL argmax (102.0%) and its pool (106.2%), against 90.8% for the trees.

Where the regret comes from

Splitting each split by the bench a run came from shows which axis each approach gets wrong.

Mean regret by source. Test: 2,316 mem, 1,634 cpu, 1,145 gpu runs. Unseen: 2,323 mem, 1,800 cpu, 2,293 gpu runs. First run: 2,182 test runs with no history; has history: 2,913. Shading grows with regret, capped at 100%.

How to read this
  • Stacked RL argmax is the best or near-best on every test slice: 5.9% on memory rows, −5.1% on CPU rows, 9.3% on GPU rows. On runs with history it scores −0.1%, i.e. the oracle's cost.
  • Negative regret is possible on CPU rows. The oracle asks for the cell that covers the busiest 15 seconds. Asking one cell lower throttles that window briefly, and that can cost less than the core-hours it saves.
  • Unseen GPU rows separate the approaches. The stacked rows score 157–208% there and the trees 167.1%. RL argmax scores 41.9% and RL decoded 45.2%; the rules score 48.4%.
  • Unseen CPU rows still favour reading the declared pool size. The rules score 16.7% and RL decoded 24.9%; every other learned approach scores 31–118%. The zero-shot 27B scores 1.0% on its sample of these runs.

The GPU axis: picking the machine

No approach puts a CPU task on a GPU, on either split. Every approach except the static request and the zero-shot 27B gives every GPU task a GPU. What remains is whether the GPU cell lands on the right machine.

GPU rows only (1,145 test, 2,293 unseen). "Machine right" is the share of GPU runs whose request lands on the oracle's shape. Regret is the mean over GPU runs, as in the table above.

How to read this
  • On test GPU runs, the hybrids pick the right machine most often (86–94%), against 77–86% for the decision models alone.
  • On unseen GPU runs it reverses. The trees get the machine right 40.6% of the time, and the stacked models 35–48%. RL argmax gets it right 77.1% of the time, and the rules 77.3%.
  • So the stacked models follow the trees' GPU estimate on new code. RL from the stacked start did not undo this. Read by argmax it went further (39.2% → 35.2% machine right); decoded, it stayed at 48%. The RL prompts are training runs, where the trees are usually right, so following the hint is rewarded.

How to read this

  • The GPU rows got harder for every approach: the trees went from 10.4% to 15.4%, and the rules from 8.2% to 26.1%.

What this release supports

  • On code like the training set, the trees and the RL policy compound. Stacking the trees' estimate into the decision model and then tuning with RL reaches 3.2% regret, a third of the best single arm.
  • On new code, both hybrids learn to trust the trees too much. Stacking learns its trust from out-of-fold hints that are usually right, and the pool weight is tuned on validation runs from familiar families. Neither tells the model when the trees are out of their depth.
  • The pool of the plain decision model with the trees is the safe hybrid. It halves the decision model's test regret (14.0% to 6.9%) and also cuts its unseen regret (58.8% to 52.2%). Its validation split includes memory and CPU rows, where the trees hold up better.
  • The next step is to tune that trust on held-out families: cross-fit the hints by family rather than by task, so a hint is as wrong in training as on new families, and tune the pool weight on a family-held-out validation split. That was not run.

Assumptions and limits

  • The GPU corpus under-samples its top end. 1,569 GPU runs were censored, concentrated where multi-GPU shards never got a node (lm_finetune 433, llm_generate 358, encoder_infer 211, recsys_train 210). These are the large, sharded runs this release was built to add. The capacity, not the workloads, was the limit.
  • Fit on unmeasured shapes is modelled. Single-GPU runs that outgrew a T4 were measured on an L40S rather than an L4, and multi-GPU fit uses the share formula above with a default imbalance of 1.25 where none was measured.
  • 48 GPU runs were lost when a large run's host memory outgrew the T4 pod and took its shard-mates with it. This slightly thins the host-memory-heavy end.
  • The oracle is the label, not the cost minimum. It asks for the cell that covers the busiest 15 seconds, and a slightly smaller CPU request can cost less, which is how CPU-row regret goes negative.
  • Prices are list prices: an m6i.xlarge dominant share for CPU pods and on-demand GPU instance prices. Spot discounts and bin-packing are not modelled.
  • A GPU task's host memory and cores are not scored. They come with the instance, so the request for them costs nothing either way.
  • Memory-bench runs have no per-second CPU series. Their throttling is modelled from mean cores, which understates bursts.
  • The zero-shot 27B is scored on about 300 runs per split (about ±5 points), and 82 of its 586 answers were unparseable.
  • One training seed per arm. The gaps between the top test rows (3.2%, 5.0%, 6.9%, 7.1%) have not been checked against seed-to-seed variation.
