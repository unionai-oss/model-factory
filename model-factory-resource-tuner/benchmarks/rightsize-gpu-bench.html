RightSizeGPU Bench

A GPU task has to pick its device before it runs. If its peak GPU memory does not fit, it dies with a CUDA out-of-memory error and is retried on a bigger GPU; if the GPU is bigger than needed, the cluster pays for memory nobody uses. This benchmark measures how well different approaches predict a PyTorch task's peak GPU memory, and how busy it keeps the GPU, from its code and input metadata.

Summary

  • The benchmark runs end to end. 128 PyTorch runs were measured with NVML, the library Union's GPU monitoring reads, in one factory materialization: 40 minutes on T4 GPUs, with runs that ran out of memory re-measured on an L40S.
  • No approach predicts GPU memory reliably yet. With 60 training runs, the best share within ±20% of the measured peak is 54.5% on test (a rule on input size) and 50.0% on unseen families (a fine-tuned 1.7B model). The 1.7B decision model predicted one value for every run; it needs the larger release.
  • On this cluster's GPUs, the device choice is almost free. 124 of 126 usable runs fit on a T4, the cheapest GPU, so any prediction up to 15 GiB costs the same. That is why memory accuracy, not dollars, is the headline.
  • GPU utilization barely varies. 108 of 126 runs averaged 90–100%, because the metric counts any time a kernel is running. A constant "90–100%" is right for about 9 in 10 runs, so this label does not yet separate approaches.
  • Convolutional nets fill the GPU. cuDNN's algorithm search grows into whatever memory exists; 7 runs peaked at the T4's full 15 GiB and still succeeded. Their peak is the device's size, not the task's need, so they are not scored on memory accuracy.
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of PyTorch code, such as training a small GPT-style model. A run is that task executed once on a particular input file. Each task in this release runs twice, on inputs of different sizes.
GPU memory
Memory on the GPU itself, separate from the pod's RAM. What the platform measures (DCGM_FI_DEV_FB_USED) includes the CUDA context, the model, its gradients and optimizer state, activations, and memory PyTorch's caching allocator holds in reserve.
Peak GPU memory (first label)
The most GPU memory in use at any moment of the run, in GiB, sampled every 0.5 seconds. A run needs a GPU whose memory covers it.
GPU utilization (second label)
The share of time a GPU kernel was running (DCGM_FI_DEV_GPU_UTIL), averaged over the run, in 10-point buckets (0–10%, …, 90–100%). It does not measure how much of the GPU each kernel used.
CUDA OOM
Out of memory on the GPU. The run fails partway through and, in this benchmark, is retried on the cheapest GPU with more memory.
Grid, cell
Memory predictions are chosen from 12 sizes: 1, 1.5, 2, 3, 4, 6, 8, 10, 12, 15, 22 and 44 GiB. The 15, 22 and 44 GiB cells are the usable memory of each GPU on the cluster, so "fits a T4" is a cell boundary.
Oracle
An imaginary approach that knows each run's measured peak in advance, picks the smallest cell that covers it, and so runs on the cheapest GPU that fits.
Within ±20% (headline metric)
The share of runs whose predicted peak memory is within 20% of the measured peak, or within 0.5 GiB for small peaks. Higher is better. Runs that filled the device are left out of this metric (see "Fills the device").
Within one cell
The prediction is the oracle's cell or one of its neighbours. A looser accuracy measure.
MAE
Mean absolute error between the predicted and measured peak, in GiB.
Device
The GPU a prediction selects: the cheapest one whose usable memory covers the predicted peak. See Device ladder.
GPU regret
Dollars spent to get every run to finish, including failed attempts and a delay penalty for each OOM, divided by the oracle's dollars, minus 1. 0% equals the oracle. Full definition under Scoring.
Fills the device
A run whose peak reached at least 95% of the GPU's memory and still succeeded. cuDNN and PyTorch's allocator use spare memory opportunistically, so such a peak reflects the GPU, not the task. 7 runs in this release.
Within ±10 points
For utilization: the middle of the predicted bucket is within 10 percentage points of the measured mean utilization.
Test split, unseen families
Test: runs of tasks whose code no approach saw in training, from the 6 training families. Unseen: runs from two whole families left out of training, a two-tower recommender (recsys_train) and nearest-neighbour search (knn_search).
Driver
What decides a family's peak memory. params: weights, gradients and optimizer state (Adam keeps two extra copies). activations: batch × sequence × width × depth, or logits over a vocabulary. data: whether a dataset or the outputs are kept on the GPU. blocks: the block size of a chunked computation. input_bound: the GPU waits on a CPU data loader.
Arm, decoding
An arm is one approach. Arms that output a probability for each cell are decoded to the cell most likely to be within ±20% of the peak. Argmax picks the single most likely cell.
Part 2 · Methodology

Why runs last two to three minutes

The benchmark predicts what Union's GPU monitoring will show, so the measurement copies that pipeline (read from the unionai/cloud repository):

  • GPU metrics come from NVIDIA's dcgm-exporter. Its Helm chart (version 4.7.1) is installed without a collection interval, so the upstream default holds: it samples the GPU every 30 seconds. Prometheus scrapes it every 15 seconds, which cannot be finer than the exporter's own 30.
  • The console's GPU memory and utilization charts are DCGM_FI_DEV_FB_USED and DCGM_FI_DEV_GPU_UTIL. DCGM_FI_PROF_SM_ACTIVE, a profiling metric, is also enabled.

Each workload loops for a time budget of 120, 150 or 180 seconds, so every run covers at least 4 DCGM samples (median 5.2). That is long enough for the platform to see a sustained value, and far below the 20–30 minute ceiling set for this benchmark, which keeps GPU usage small. The benchmark itself samples the same NVML counters every 0.5 seconds, so it catches peaks DCGM's 30-second samples could miss.

The dataset: real PyTorch code

Every workload is generated from one of 8 families of PyTorch task code. Within a family, a random generator picks the choices an ML engineer would reason about when sizing a GPU, and the size of the input file. Each task is a complete Flyte task. If no GPU is present the code runs on CPU, so the benchmark's own tests can execute it.

From tasks to runs

This release has 8 tasks per family and 2 runs per task: 128 runs. Each run scales the task's input file by a factor between 0.5× and 2×. The first run of each task has no history; the second sees the first.

Splits

Tasks are split, so both runs of a task share a split. A hash of the task id sends 70% of tasks in the 6 training families to train, 10% to validation and 20% to test; the 2 held-out families go entirely to unseen. Validation tunes each approach's settings; test and unseen are scored once.

How each run was measured

  1. Prepare. A child process writes the run's input file to local disk. Integer token files are drawn below the code's vocabulary size, so embedding lookups are valid.
  2. Run. A fresh Python interpreter imports the task's module and calls its function, one workload per GPU.
  3. Observe. A sampler reads NVML every 0.5 seconds: the device's memory.used, what DCGM_FI_DEV_FB_USED reports, and utilization.gpu, what DCGM_FI_DEV_GPU_UTIL reports. The child also reports PyTorch's own max_memory_reserved as a cross-check.

Two passes. Pass 1 runs on T4 pods (g4dn.xlarge, 3 CPUs and 13 GiB requested), 26 shards of 5 runs. A run that hits a CUDA OOM is marked as needing a bigger GPU and re-measured in pass 2 on an L40S (one shard of 4). In this release 2 GPT-style runs needed more than a T4 and succeeded on the L40S, and 2 encoder runs failed on both and were excluded.

What NVML adds. NVML's peak exceeds PyTorch's own reserved memory by a median of 398 MiB: the CUDA context and loaded kernels, which a request has to cover too. Memory peaks come early, a median 2–5% into the run, during the first forward and backward pass.

Labels. The memory label is the smallest of the 12 cells that covers the peak. The utilization label is the 10-point bucket of the run's mean utilization.

Scoring: memory accuracy first, dollars alongside

Each prediction picks a GPU, and the run is replayed against its measured peak:

  1. If the peak fits the chosen GPU, the run pays one nominal task-hour at that GPU's price, plus 5% for start-up (image pull, CUDA initialization, data load).
  2. If it does not fit, the run dies with a CUDA OOM at the point its peak was measured (at least 2% of the run) plus start-up, and is retried on the cheapest GPU with more memory, up to 4 attempts.
  3. Each OOM adds a delay penalty of one oracle-priced run.
  4. GPU regret = total dollars across all runs ÷ the oracle's dollars − 1.
Worked example

A run peaks at 18 GiB, 3% of the way in. The oracle picks an L4: $0.978 × 1.05 = $1.03.

  • Predicting 12 GiB picks a T4. It dies at 3%: $0.526 × 0.08 = $0.04. The retry on an L4 costs $1.03, and the OOM penalty another $1.03. Total $2.10, or 104% over the oracle.
  • Predicting 30 GiB picks an L40S: $2.242 × 1.05 = $2.35, or 129% over.
  • For a run that peaks at 3 GiB, predicting 4 GiB and predicting 12 GiB both pick a T4 and both cost exactly the oracle's $0.55. That is why dollars cannot tell these approaches apart on this cluster.

Why accuracy is the headline. 124 of the 126 usable runs fit on a T4, so under cost, every prediction up to 15 GiB is equally good. The first scoring of this release decoded distributions by lowest expected cost, and every distributional approach collapsed to the 15 GiB cell. Memory accuracy is what a scheduler needs to pack GPUs, share them, or move to a cluster with a different ladder, so it is the headline, and the device and dollars follow from it.

Almost everything fits on a T4

How to read this
  • A bar to the left of the T4 line means that family's runs fit on the cheapest GPU. Only the GPT-style family's largest runs cross it (16.9 GiB, which needs an L4).
  • The CNN and recommender bars stop at the T4 line because some of their runs filled the device: cuDNN and the allocator grew into the free memory. Their true need is lower.
  • Within a family, the 90th-percentile peak is 2.5× (MLP) to 18× (CNN) the 10th-percentile peak. Memory is decided by the code (batch, width, precision, what is kept on the GPU), so knowing the device is not the same as knowing the memory.

Utilization is nearly always high

Usable runs by mean GPU utilization, in the 10-point buckets approaches predict.

How to read this
  • 108 of 126 runs averaged 90–100%. GPU_UTIL counts the share of time any kernel is running, so a small model that keeps one kernel queued reads as busy as a large one.
  • The low bars are the data-loader family with per-pixel Python augmentation (the GPU waits on the CPU) and some recommender runs with large sparse tables.
  • Because a constant "90–100%" is right for about 9 in 10 runs, utilization accuracy does not separate approaches here. SM activity (DCGM_FI_PROF_SM_ACTIVE), which measures how much of the GPU's compute is in use, would be a better label, but NVML cannot read it on a T4.

  • Each row is one decision rule; the bar is the share of runs whose predicted peak memory was within ±20% of the measured peak.

What the small release supports

  • The measurement is sound and cheap. 128 runs measured with the same counters the platform reads, each covering at least 4 DCGM samples, in 40 minutes and 5.7 T4-hours.
  • Dollars are not a useful headline on this cluster, because the cheapest GPU holds almost every run. Memory accuracy is.
  • Memory accuracy is still open. The best approaches reach about half the runs within ±20%, and the size rule, SFT and history-based rules are all in the same range. The learned models need the larger release before they say anything.
  • The zero-shot 27B model is weakest on utilization (68% and 41% within 10 points, against 91% and 88% for a constant). It assumes small models leave the GPU idle; by this metric they do not.
  • Peaks that fill the device need their own label. A platform reading peak memory for a CNN sees the GPU's size. The benchmark records "fills the device" and scores those runs on device choice only.

Assumptions and limits

  • Sample size. 22 test runs and 30 scored unseen runs. Differences under about 20 points are within noise.
  • Measured on a T4. Peak memory carries over to other GPUs approximately (cuDNN picks different algorithms per GPU, and fills whatever memory exists). Utilization does not carry over: a faster GPU waits more for the same data loader.
  • One nominal task-hour per run in the cost model. The workloads run for 2–3 minutes; regret is a ratio and does not depend on length.
  • Prices are on-demand list prices for single-GPU shapes; spot prices and multi-GPU packing would change dollars but not memory accuracy.
  • The trees' 40 code tokens were written by the person who wrote the generator, which makes that baseline generous.
