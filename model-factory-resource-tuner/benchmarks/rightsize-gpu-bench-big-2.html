RightSizeGPU Bench

A GPU task has to pick its machine before it runs. If the GPU memory is too small, the run dies with a CUDA out-of-memory error and is retried on a bigger machine. If it is too big, the run pays for memory it never touches. This benchmark measures how well different approaches predict a PyTorch task's peak GPU memory and GPU utilization from its code, its inputs and its earlier runs. This page reports the second big release, big-2. Its workloads span every GPU machine the cluster provisions, including multi-GPU nodes, and it adds two ways of combining the trees with the language models.

Summary

  • The machine choice is no longer nearly trivial. 74.7% of usable runs fit a T4, against 94.8% in big-1. The rest need an L4 (6.5%), an L40S (14.9%) or a multi-GPU node (3.5%).
  • But the top of the ladder is censored. The 4xL4 pool never scheduled a measurement, half the 8xT4 shards and nearly all 4xL40S shards timed out in the queue. 1,569 runs ran out of memory on the largest machine they reached and have no peak. They are mostly the large sharded runs this release was built to add. Only 10 of 1,202 test runs need a multi-GPU machine.
  • In distribution, the best hybrids beat both of their members. The trees' probabilities pooled with the stacked 1.7B decision model put 74.8% of test runs within ±20% of the peak, against 71.9% for the trees and 58.2% for the decision model alone. Writing the trees' prediction into the prompt (stacking) lifts the decision model by 15 points, to 73.4%.
  • On unseen families the trees collapse to 9.8% and pull every hybrid down, to 5–28%. The 4B decision model alone is best at 42.1%. Even a static request (16.6%) beats the trees there.
  • For dollars, the hybrids keep the trees' habit of asking big. On unseen families they run out of memory on 2.6–7.0% of first tries, against 15–25% for the language models alone. The lowest cost on unseen families is the pool of the trees with the 1.7B decision model (84.7% over the oracle). On test it is a pool read by argmax (23.4%).
Part 1 · Definitions

Terms used on this page

Task, run
A task is one piece of PyTorch code, such as fine-tuning a language model. A run is that task executed once on a particular input file. Each task runs twice, on inputs of different sizes, and the second run sees the first as history.
Peak GPU memory (first label)
The most GPU memory in use at any moment of the run, in GiB, as NVML reports it (what DCGM_FI_DEV_FB_USED shows). It includes the CUDA context, weights, gradients, optimizer state, activations, and what PyTorch's allocator holds in reserve. For a run spread over several GPUs it is the single-GPU equivalent: the per-GPU peaks summed, less the extra CUDA contexts, so the same run measured on 8 T4s or on one L40S gets the same label.
GPU utilization (second label)
The share of time a kernel was running (DCGM_FI_DEV_GPU_UTIL), averaged over the run and over the GPUs it used, in 10-point buckets.
Machine, shape
One of the seven GPU node types on the cluster, from one T4 to four L40Ss. See the machine ladder.
Sharded
Code that spreads its model over every GPU it can see: layers placed in runs across GPUs, or embedding-table rows split between them. Only sharded code gains from a multi-GPU machine. Other code uses one of its GPUs and pays for all of them.
Imbalance
How much more than an even share the busiest GPU of a sharded run holds. Measured when a run was measured on several GPUs; 1.25 otherwise.
Grid, cell
Memory predictions are one of 17 sizes: 1, 1.5, 2, 3, 4, 6, 8, 10, 12, 15, 22, 32, 44, 64, 88, 120 and 176 GiB. 15, 22 and 44 are the memory of one T4, L4 and L40S; 88, 120 and 176 the total of a 4xL4, an 8xT4 and a 4xL40S.
Oracle
Knows each run's peak in advance and picks the cheapest machine it fits.
Within ±20% (headline)
The predicted peak is within 20% of the measured peak, or within 0.5 GiB for small peaks. Higher is better.
Within one cell
The cell that covers the peak, or a neighbour.
OOM
Share of runs whose first machine was too small (a CUDA out-of-memory error).
GPU regret
Dollars to get every run to finish, including failed attempts and a delay penalty per OOM, divided by the oracle's dollars, minus 1. Lower is better. See Scoring.
Fills the device
A run whose peak reached at least 95% of a GPU's memory and still succeeded. cuDNN and PyTorch's allocator grow into free memory, so the peak is the GPU's size, not the task's need. These runs count for cost and utilization, not for memory accuracy.
Censored
A run that ran out of memory on the largest machine it reached, so its peak is unknown. Only a lower bound is known. Censored runs are not scored.
Test, unseen
Test: runs of new tasks from the 7 training families. Unseen: runs from three families held out of training: a two-tower recommender (recsys_train), nearest-neighbour search (knn_search) and LLM generation with a KV cache (llm_generate).
Hybrid: stacked, pooled
Two ways to combine the trees (gbt-dist) with a language model. Stacked: the trees' prediction is written into the model's prompt, and the model is trained with it. Pooled: the two probability distributions over cells are multiplied, with a weight. See Hybrids.
Part 2 · Methodology

The machine ladder

A memory prediction becomes a machine: the cheapest GPU node on the demo.hosted cluster whose total GPU memory covers it. big-1 had three single-GPU shapes. big-2 uses every GPU node pool the cluster has. Prices are on-demand, per node-hour, in us-east-1.

The 40 runs that fit nothing are single-GPU runs that peaked between 44.0 and 45.0 GiB on an L40S: more than the 44 GiB the ladder counts as usable, and not sharded, so no multi-GPU machine helps.

When does a multi-GPU machine hold a run?

Most runs were measured on one GPU. Whether they fit a machine they were not measured on is modelled (grid.fits). Code that is not sharded must fit on one GPU, whatever the machine. Sharded code on n GPUs puts a share of its memory on each, and the busiest GPU must hold its share:

per_gpu_need = (peak − 0.5 GiB) × imbalance / n + 0.5 GiB

  0.5 GiB    the CUDA context and allocator reserve every used GPU carries
  imbalance  busiest GPU ÷ even share; measured on several GPUs, else 1.25
             (embeddings sit on the first GPU, the LM head on the last)
  fits       per_gpu_need ≤ the machine's memory per GPU
Worked example
  • A sharded fine-tuning run peaks at 60 GiB with the default imbalance of 1.25. On a 4xL4 each GPU needs (60 − 0.5) × 1.25 / 4 + 0.5 = 19.1 GiB, which fits in 22. The oracle picks the 4xL4 at $4.602 an hour.
  • The same code without sharding needs one GPU with 60 GiB. No machine on the ladder has one, so it fits nothing.
  • A request is read as total memory: asking for 32 GiB lands on an L40S (44 GiB, $2.242), 64 or 88 GiB on a 4xL4, 120 on an 8xT4, 176 on a 4xL40S. A sharded run whose share does not fit a 4xL4 has to ask past 88 GiB to reach an 8xT4.

The dataset: real PyTorch code

Every workload is generated from one of 10 families of PyTorch task code. Within a family, a generator varies the choices an ML engineer reasons about when sizing a GPU (width, depth, batch, sequence length, precision, what is kept on the GPU, block sizes, how many layers are trained, the optimizer), and the size of the input file. Each task is a complete Flyte task. For big-2 the single-GPU families were scaled up so a share of runs needs an L4 or an L40S, and three families are sharded.

The driver names what an approach has to read to get the memory right. The held-out families each teach a skill the training families show in another form: optimizer state (mlp, gpt), block sizes (blocked_gemm), layers spread over GPUs (lm_finetune), inference (encoder_infer).

The release has 500 tasks per family and 2 runs per task: 10,000 runs. Runs loop for 45, 60 or 90 seconds (median wall time 64 s), so each covers at least one of DCGM's 30-second samples. Tasks are split by a hash of their id: 70% of the 7 training families' tasks to train, 10% to validation, 20% to test; the 3 held-out families go entirely to unseen.

big-2 counts runs that filled the device (432) as usable: they are scored on cost and utilization but not on memory accuracy, which leaves 1,145 test and 2,293 unseen runs scored on memory. big-1 excluded such runs (219) along with 165 lost re-measurements and 50 runs that exceeded 44 GiB. Of big-2's 51 failed runs, 48 were lost with their shards (see How it ran) and 3 hit a cuBLAS allocation error.

How each run was measured

Each run is a fresh Python interpreter that imports the task's module and calls it. A sampler reads NVML's memory.used and utilization.gpu on every GPU the run can see, every 0.5 seconds. A run that hits a CUDA OOM needs a bigger machine, so the measurement climbs, and the climb depends on whether the code is sharded:

single-GPU code   T4  →  4xL4, one run per L4  →  4xL40S, one run per L40S  (after 1 h queued: single L40S)
sharded code      T4  →  8xT4, the run across all 8 T4s  →  4xL40S, the run across all 4
  1. Pass 1, T4. 1,667 shards of 6 runs each on T4 pods (g4dn.xlarge). 1,659 succeeded. 8 shards (48 runs) failed all three attempts because the pod, not the GPU, ran out of memory: a large mlp_tabular run's host RAM outgrew the pod's 13 GiB and took its five shard-mates with it.
  2. Pass 2, 4xL4 and 8xT4. Single-GPU runs that ran out of memory on the T4 go to a 4xL4 node, four at a time, one per GPU: 118 shards, and all of them timed out in the queue. Sharded runs go to an 8xT4 node, each run across all eight GPUs: 459 shards, of which 229 timed out.
  3. Pass 3, L40S. Single-GPU runs still out of memory wait an hour for a 4xL40S node, then fall back to single-L40S nodes. No 4xL40S shard of this kind (0 of 157) got a node; 469 single-L40S shards succeeded. Sharded runs go to a whole 4xL40S node: 6 of 340 shards got one.
  4. Labels. The memory label is the smallest of the 17 cells that covers the single-GPU-equivalent peak; the utilization label is the 10-point bucket of the mean. A run that ran out of memory on the last machine it reached is censored.

The result: 7,056 usable runs measured on a T4 and 1,324 on an L40S. Single-GPU runs past a T4 were measured on an L40S, not an L4, because the 4xL4 pass never ran. 815 runs were measured across an 8xT4 node and 18 across a 4xL40S node.

What every approach is allowed to see

What a scheduler has at submission: the task's source code, each input file's metadata (bytes, format, shape, dtype), and the task's earlier runs (peak GPU memory, mean utilization, machine and wall time). No approach sees the generator's hidden choices, the family or the driver. The LLMs read these as a prompt that ends with the two option lists (gpu_memory, gpu_util) and a JSON answer format. The system prompt lists the seven machines with their memory and price, and says that a multi-GPU machine only helps code that spreads its model over every visible GPU. The trees read the same information as 82 numbers, including 50 PyTorch API tokens (10 new in big-2, such as device_count(), RowSharded, requires_grad_(False) and Adafactor), the sizes of Linear layers, a width² × layers parameter count, the batch slice, and the history.

Rules

static
One request for every run: a quantile of training peaks, tuned on validation. Utilization: the training median.
vpa
The largest peak this task has used, times a margin tuned on validation, rounded up to a cell. With no history, the static request. Utilization: the last observed value.
size rule
Peak memory as a power law of total input bytes, fitted as a quantile of the training runs. With history, the nearest past run rescaled by the input-size ratio, times a margin.

Gradient-boosted trees

Model
scikit-learn HistGradientBoostingRegressor with the pinball loss (300 rounds, learning rate 0.06, 31 leaves) on log₂ of peak GiB. gbt fits quantiles 0.5 to 0.95 and keeps the one best on validation, then rounds up to a cell. gbt-dist fits all 19 quantiles from 0.05 to 0.95 and turns them into a probability per cell through a piecewise-linear CDF. Utilization is a separate median-regression model. gbt-dist is also the tree member of every hybrid.

zero-shot 27B

A hosted 27B Qwen model (qwen38-27b on the cluster's shared vLLM) at temperature 0. The system prompt lists the machine ladder with prices and explains the OOM retry. The last JSON object in its answer is parsed and rounded up to an option. Scored on a sample of about 300 runs per split (294 test, 300 unseen).

SFT 1.7B: fine-tuned to write the answer

Architecture
Qwen3-1.7B (28 layers, hidden size 2,048) with LoRA adapters (rank 16, α 32, dropout 0.05) on all seven projections of every layer; about 17M trained weights. The output is the model's own language-model head.
Training
Next-token cross-entropy on the oracle's answer, {"gpu_memory": "22GiB", "gpu_util": "90-100%"}, with the prompt masked out and logits computed only for the answer window. 3 epochs, AdamW at 2×10⁻⁴ with warm-up and cosine decay, fp16 with a loss scaler and gradient checkpointing on one T4.
Inference
Greedy: generate the answer and parse it, with a margin of k cells tuned on validation. 8 samples: generate 8 answers at temperature 1 and count each memory cell as a probability, then decode.

Architecture
The same Qwen3 and LoRA adapters, loaded without the language-model head. Each option's token sits at a fixed distance from the end of the prompt, because prompts are cut from the left to 2,048 tokens. A shared LayerNorm and a query and key projection (to 256 dimensions) per decision score every option against the answer slot in one forward pass.
Training
Cross-entropy on the memory cell plus 0.3 × cross-entropy on the utilization bucket. The 1.7B trains for 3 epochs; the 4B (36 layers, hidden size 2,560) for 2, with micro-batches of 4 and 4 accumulation steps to fit a 16 GB T4.
Calibration
One temperature fitted on validation by negative log-likelihood.
Inference
One forward pass gives 17 memory probabilities and 10 utilization probabilities. No tokens are generated.

Hybrids: combining the trees and the language models

The trees and the language models fail in different places. In big-1 the trees were best on familiar families (71.3% within ±20%) and worst on unseen ones (25.7%), and the decision models were the reverse (63–65% and 45–51%). The trees read numbers exactly but know nothing about code they have no feature for. The language models read the code but treat numbers as tokens. big-2 tries two ways to get both.

Stacked (stack-<arm>): the trees' prediction in the prompt

  1. Fold the training tasks. Split the training tasks into 5 folds by a hash of the task id. Both runs of a task land in the same fold.
  2. Predict out of fold. For each fold, fit gbt-dist on the other four folds and predict this one. Every training run then has a prediction from trees that never saw it or its sibling run. Validation, test and unseen runs get predictions from trees fit on all of train.
  3. Write the prediction into the prompt, as a short section just before the options:
### A tree model's estimate
Gradient-boosted trees fit on other tasks' measured runs (they read the input sizes, the API names
and numbers in the code, and this task's earlier runs) put gpu_memory at <cell> <p>%, <cell> <p>%,
<cell> <p>%; their pick: <cell>. Their gpu_util: <bucket>.

### Options
…
  1. Train the language model as before on these prompts: SFT 1.7B, decision 1.7B and decision 4B, each with the same recipe as its plain version. The three cells shown are the trees' three most likely.
Why it is built this way
  • Out of fold, because trees predicting rows they were fit on are nearly always right. A model trained on those hints would learn to copy them. Out of fold, it sees how often the trees are wrong on new tasks.
  • Before the options, because the pointer head reads each option at a fixed distance from the end of the prompt. Everything from ### Options on is unchanged, so those distances hold (tests/test_hybrid.py).
  • The catch: the folds are by task, not by family. The model learns how far to trust the trees on families the trees know.

Pooled (pool-<variant>): multiply the two distributions

gbt-dist and every language-model read-out that gives a probability per cell (SFT with 8 samples, both decision models, and the three stacked versions) are combined in a logarithmic opinion pool:

p(cell) ∝ p_trees(cell)^w · p_llm(cell)^(1 − w)

  w = 0     the language model alone          w = 1     the trees alone
  w         tried at 0, 0.1, … , 1; the one with the most validation runs within ±20% is kept
  util      taken from whichever member gets the bucket right more often on validation

A log pool is a weighted geometric mean. A cell keeps much probability only if both members give it some, so one confident member cannot put mass where the other gives none. Nothing is retrained: the pool is built from the arms' saved predictions, then decoded like any other arm, both ways. The tuned weights are in Hybrid results.

Decoding: two read-outs

gbt-dist, SFT with 8 samples, the decision models and every hybrid end with a probability for each of the 17 cells. The decoded rows pick the cell most likely to be within ±20% of the peak (ties go up). The argmax rows pick the single most likely cell. The two behave differently at the top of the ladder. The large cells are wide, and a within-±20% window rarely gathers enough probability there, so the accuracy decoder tends to stay low. Argmax asks for the bigger machine when that cell is the most likely one.

Scoring: memory accuracy first, dollars alongside

  1. The request lands on the cheapest machine whose total GPU memory covers it.
  2. If the run fits that machine (by the fit model above), it pays one nominal task-hour at the machine's price, plus 5% for start-up.
  3. If it does not fit, it dies with a CUDA OOM at the point its peak was measured, and is retried on the cheapest machine with more total memory, up to 4 attempts.
  4. Each OOM adds a delay penalty of one oracle-priced run.
  5. GPU regret = total dollars ÷ the oracle's dollars − 1.
Worked example

The sharded run from the ladder example peaks at 60 GiB, 6% of the way in. The oracle picks a 4xL4: $4.602 × 1.05 = $4.83.

  • Predicting 44 GiB picks an L40S. One 44 GiB GPU cannot hold 60 GiB, so the run dies at 6% ($0.25 with start-up). The next machine up is the 4xL4 ($4.83), and the OOM penalty adds another $4.83: 105% over the oracle.
  • Predicting 120 GiB picks an 8xT4: $8.22, 70% over.
  • For a run that peaks at 3 GiB, predicting 4 or 12 GiB both pick a T4 and cost the oracle's $0.55. Dollars only separate approaches on the quarter of runs above 15 GiB, which is why accuracy is the headline.

  • On test, the hybrids lead: the pools at 71.8–74.8% and the decoded stacked decision models at 71.8–73.4%, level with or above the trees (71.9%). The single language models sit at 48–58%, the history and size rules at 37%, the zero-shot 27B at 31.6% and the static request at 12.1%.

  • With 1,145 and 2,293 runs, a share near 60% has a 95% interval of about ±3 and ±2 points.
Columns
  • ±20%: the headline. 1 cell: the peak's cell or a neighbour. MAE: GiB. machine: share of runs whose first machine is the oracle's.
  • OOM and $ regret: the cost side (lower is better). util ±10: utilization within 10 points.
  • Bold marks the best value in each column.

Hybrids win in distribution and lose on new families

Share within ±20%, decoded read-outs. Each row is one language model; the columns are it alone, it stacked, it pooled with the trees, and its stacked version pooled with the trees. The trees alone: 71.9% on test, 9.8% on unseen.

How to read this
  • In distribution, six of the nine hybrids beat both members, and two more are within 0.1 point of the trees; only stacked SFT (65.0%) falls clearly short. Stacking lifts the 1.7B decision model by 15 points (58.2% to 73.4%) and the 4B by 16. That is more than on RightSizeCPU (under 1 point), because here the trees are the stronger member.
  • On unseen families every hybrid is worse than its language model alone, by 6 to 31 points. The stacked models learned to follow the hint, because in training the out-of-fold hint was usually right. The pool weight was tuned on validation, which is in distribution, where the trees are the better member.
  • The plain 1.7B pool holds up best on unseen families (27.7%). Its tuned weight on the trees is the lowest of the three plain pools (0.7, against 0.9 for the other two).

Validation share within ±20% at the pool weight w on the trees: w = 0 is the language model alone (read through the pool), w = 1 the trees alone. The chosen w maximizes validation; ties go to the larger w. "util from" is the member whose utilization bucket the pool uses.

How to read this
  • For the plain language models, validation rewards leaning on the trees: w = 0.7 for the 1.7B, 0.9 for the 4B and SFT. The stacked models already carry the trees' view, so their pools settle lower (0.3–0.6).

Cold and warm runs

Share within ±20%. Cold: the first run of a task, with no history. Warm: the second run, which sees the first run's measured peak. Test: 619 cold and 583 warm runs; unseen: 1,333 and 1,057.

How to read this
  • The hint overrides the task's own history on new families. On warm unseen runs, the 4B decision model alone reaches 77.6%, and the history rule (vpa) 55.5%, because the first run's peak is a strong clue. The stacked 4B reaches 21.0% and the trees 12.0%: they follow the trees' estimate instead of the measured history.
  • On cold unseen runs nothing works well: every approach is at or below 15%.

Accuracy decoding and dollars

OOM rate and GPU regret, decoded and argmax read-outs of the same distribution.

How to read this
  • Decoding for accuracy still under-asks at the top of the ladder: on test the decoded stacked decision models and pools run out of memory on 11.6–15.1% of first tries and cost 44–50% over the oracle. Read by argmax, the same distributions run out of memory on 3.6–5.2% and cost 23–28% over. The lowest test regret is the pool of the trees with the stacked 1.7B, read by argmax (23.4%); the trees' point prediction (gbt) costs 26.4%.
  • On unseen families the hybrids are cheaper though less accurate. They run out of memory on 2.6–7.0% of first tries, against 15–25% for the language models alone, because they keep the trees' habit of asking big. The plain 1.7B pool, decoded, has the lowest unseen regret of any arm (84.7%); the 4B decision model alone costs 98.6%.
  • Unseen regret is high for every arm because the unseen split holds most of the multi-GPU runs, where a wrong first machine is expensive.

By family

Share within ±20%, by family, for single approaches and decoded hybrids. Training families are scored on validation and test runs together; the three unseen families on all their runs. Cell shading is proportional to the value.

How to read this
  • The trees fail hardest on recsys_train (6%) and knn_search (8%). The 4B decision model gets 40% and 45% there.
  • llm_generate is new code and new hardware at once. The language models do best: the zero-shot 27B 42% (on a sample), the 4B decision model 40%, SFT with 8 samples 39%. The trees reach 17%.
  • The largest gains from stacking are on blocked_gemm (36% to 73% for the 1.7B decision model) and lm_finetune (44% to 74%), where the trees are strong (69% and 76%) and the plain decision model is not.

What changed from big-1

Share within ±20%. big-1: 1,413 test and 2,411 unseen runs scored on memory, on a three-machine ladder, with recsys_train and knn_search unseen. big-2: 1,145 and 2,293, seven machines, with llm_generate also unseen. The workloads changed, so this compares the benchmark's difficulty as much as the approaches.

How to read this
  • On test, the trees held (71.3% to 71.9%) while every language model lost 5–9 points. The language models had 4,204 training runs instead of 5,021, spread over a wider range of peaks and 17 cells instead of 12.
  • On unseen families nearly every approach lost, the trees most (25.7% to 9.8%). The 4B decision model kept the lead (50.5% to 42.1%). Only the static request gained (10.3% to 16.6%).
  • The machine choice now matters. In big-1 95% of runs fit a T4, so the cost side barely separated approaches. In big-2 test regret ranges from 23% to 117%.

What big-2 supports

  • The trees and the language models can be combined profitably in distribution. The best stacked and pooled arms beat both members on test, by up to 3 points over the trees and up to 20 over the language model alone.
  • Neither combination knows when the trees are out of their depth. Both learn how far to trust the trees from data where the trees are right, so on unseen families the hybrids follow the trees down. The language model alone is the better choice for new code (42.1% for the 4B).
  • For cost on new code, a hybrid's caution helps. The plain 1.7B pool has the lowest unseen regret (84.7%).
  • Not yet shown: cross-fitting the trees by family rather than by task, and tuning the pool weight on a family-held-out validation split, so the hint is as wrong in training as on new families. And whether the conclusions hold once the multi-GPU runs are measured rather than censored.

Assumptions and limits

  • The top of the ladder is under-sampled. 1,569 runs (15.7%) are censored: 1,001 of them sharded. The 4xL4 pool never scheduled a shard (all 118 timed out after 2 hours, 3 times), 229 of 459 8xT4 shards timed out, and 4xL40S scheduled 6 of 340 whole-node shards and none of 157 per-GPU shards. The capacity, not the workloads, was the limit. Only 10 test runs and 209 unseen runs need a multi-GPU machine, so the multi-GPU part of the ladder is barely tested in distribution.
  • Single-GPU runs past a T4 were measured on an L40S, not on the L4 that would be their cheapest fit. Peak memory carries over approximately; utilization does not.
  • Fit on machines a run was not measured on is modelled, with an imbalance of 1.25 for sharded runs measured on one GPU.
  • 48 runs were lost when large mlp_tabular runs exceeded the pod's host memory and took their shard-mates with them, slightly thinning the host-RAM-heavy end.
  • The hybrids' trust in the trees was learned in distribution: folds by task, and a pool weight tuned on in-distribution validation.
  • One nominal task-hour per run in the cost model, and on-demand list prices.
  • Runs are 45–90 seconds, covering 1–3 DCGM samples.
  • The trees' 50 code tokens were written by the person who wrote the generator, which makes that baseline, and every hybrid built on it, generous.
  • Unseen families are only three.
