RightSizeGPU Bench: GPU memory from PyTorch code, on the whole machine ladder

Big release 2 (big-2) · 10,000 measured runs · trees × LLM hybrids
Abstract

A GPU task's machine is chosen before it runs. Too little GPU memory and the run dies with a CUDA out-of-memory error and is retried on a bigger machine; too much and it pays for memory it never uses. RightSizeGPU Bench measures how well different approaches predict a PyTorch task's peak GPU memory and mean GPU utilization, as Union's GPU monitoring reads them, from the task's code, its input metadata and its earlier runs. The big-2 release has 10,000 runs of generated Flyte task code from 10 families, three of which spread their model over every GPU they see. Runs were measured with NVML every 0.5 seconds on a T4, and those that ran out of memory climbed a ladder of seven machines, up to four L40Ss; 8,380 are usable. The headline is the share of runs whose predicted peak is within ±20% of the measured one; dollars after out-of-memory retries are reported alongside. The release also tests two ways to combine gradient-boosted trees with language models: writing the trees' prediction into the model's prompt (stacked), and multiplying the two probability distributions (pooled).

A quarter of usable runs need more than a T4 (big-1: 5%). But multi-GPU capacity mostly did not come: 1,569 runs, mostly the largest sharded ones, ran out of memory on the biggest machine they reached and are censored, and only 10 test runs need a multi-GPU machine. On 1,145 test runs, the trees pooled with a stacked Qwen3-1.7B decision model predict the peak within ±20% on 74.8%, above the trees alone (71.9%) and the decision model alone (58.2%). On 2,293 runs from three families held out of training, the trees fall to 9.8% and pull every hybrid down to 5–28%; a Qwen3-4B decision model alone leads at 42.1%. The hybrids are cheaper on those families, though: they keep the trees' habit of asking big and run out of memory on 2.6–7.0% of first tries, against 15–25% for the language models alone.

Five findings

  1. 74.7%The machine choice is no longer nearly trivial. That share of usable runs fits a T4, against 94.8% in big-1. 6.5% need an L4, 14.9% an L40S and 3.5% a multi-GPU node; only the three sharded families reach one, up to 127.5 GiB.
  2. 74.8%In distribution, the best hybrids beat both members. The trees pooled with the stacked 1.7B decision model lead on test. Stacking alone lifts the 1.7B decision model by 15 points, to 73.4%, because the trees are the stronger member here.
  3. 42.1%On new code, the language model alone is better. The 4B decision model leads on the unseen families; the trees reach 9.8%, below a static request (16.6%), and every hybrid is 6–31 points below its language model. Both hybrids learned how far to trust the trees on families where the trees are right. On unseen runs with history, the 4B alone scores 77.6% and the stacked 4B 21.0%: the hint overrides the measured earlier run.
  4. 84.7%For cost on new code, a hybrid's caution pays. The plain pool of the trees and the 1.7B decision model has the lowest unseen regret of any arm (the 4B alone: 98.6%). On test, the pools and stacked models read by argmax cost 23–28% over the oracle, the lowest 23.4%.
  5. 1,569The top of the ladder is censored. The 4xL4 pool never scheduled a measurement, 229 of 459 8xT4 shards and nearly all 4xL40S shards timed out in the queue. A third of all sharded runs have no measured peak, so the multi-GPU shapes are barely tested: 10 test runs and 209 unseen runs need one.
Setup

How the benchmark works

Workloads
10 families of PyTorch task code: a tabular MLP, a CNN fed by a CPU data loader, a CNN, a GPT-style language model, a transformer encoder for embeddings, a blocked all-pairs similarity, LM fine-tuning, a two-tower recommender, nearest-neighbour search and LLM generation with a KV cache. The fine-tuner, the recommender and the generator place their layers or embedding rows on every visible GPU. 500 tasks per family, each run twice on inputs 0.5× to 2× its base size, for 45 to 90 seconds.
Machines
T4 (15 GiB, $0.526/h), L4 (22 GiB, $0.978/h), A10G (22 GiB, $1.212/h, never cheapest), L40S (44 GiB, $2.242/h), 4xL4 (4 × 22 GiB, $4.602/h), 8xT4 (8 × 15 GiB, $7.824/h), 4xL40S (4 × 44 GiB, $10.493/h). A multi-GPU machine only holds more for sharded code; fit is modelled per GPU.
Labels
Peak GPU memory from NVML (what DCGM's FB_USED reports), summed over the GPUs a run used, as the smallest of 17 cells from 1 to 176 GiB that covers it, and mean utilization in 10-point buckets. Measurement climbs: single-GPU code T4 → 4xL4 → L40S, sharded code T4 → 8xT4 → 4xL40S. 7,056 usable runs were measured on a T4, 1,324 on an L40S, 815 across an 8xT4.
Splits
By task: 4,204 train, 584 validation and 1,202 test runs from 7 families, plus 2,390 runs from 3 families held out entirely (recsys_train, knn_search, llm_generate). Runs that filled the device are kept for cost but not memory accuracy.
Approaches
Rules: a static request; the task's largest past peak times a margin; a power law in input size. Trees: gradient-boosted quantile regression on 82 features, and the same at 19 quantiles read as a distribution. Autoregressive LLMs: a zero-shot 27B, and Qwen3-1.7B fine-tuned with LoRA to write the answer. Decision models: the same LoRA setup on Qwen3-1.7B and 4B with a head that scores each option in the prompt in one forward pass.
Hybrids
Stacked: the trees' top three cells and pick are written into the prompt before the options, and the LLM is trained with them. Training runs carry out-of-fold predictions (5 folds by task), so the model sees the trees' errors on tasks they were not fit on. Pooled: p ∝ ptreesw · pLLM1−w, with w tuned on validation (0.3–0.9).

Key terms

Peak GPU memory
The most GPU memory in use at any moment of the run, including the CUDA context and the allocator's reserve; for a run on several GPUs, the per-GPU peaks summed less the extra contexts.
Within ±20%
The headline: the predicted peak is within 20% of the measured peak, or 0.5 GiB for small peaks.
Sharded
Code that spreads its model over every visible GPU. Only sharded code gains from a multi-GPU machine.
Censored
A run that ran out of memory on the largest machine it reached; its peak is unknown and it is not scored.
Decoded, argmax
Two read-outs of a probability per cell: the cell most likely within ±20% of the peak, or the single most likely cell.
Unseen families
The three families no approach trained on; they test generalization to new code.
