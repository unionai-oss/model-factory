Resource tuner · RightSize · round 21 results

What RightSize sees, and what it would save

RightSize picks a task's memory, CPU and GPU before it runs. Three kinds of model make that pick: gradient-boosted trees, an autoregressive LLM, and a decision model. Each reads a different version of the same task. The best combination of them is then priced against how overprovisioned a customer's workloads are today.

No model sees the measurement. All three see the same three inputs: the task's source code, the metadata of this run's inputs (bytes, shape, dtype), and what earlier runs of the task used. None of them sees the workload family's name or the generator's settings.

Input
Input sizes and shapes as log2 numbers, 160 yes/no flags for API strings in the code (torch.autocast, GradScaler, n_jobs= …), numbers pulled out of the code by regex (the VOCAB, D, LAYERS triple, the batch slice), and the history's peaks scaled to this run's input size.
Output
A quantile distribution over each axis's cells (17 memory, 16 CPU, 18 GPU). One small model per axis.
Strength
Reads numbers exactly. For this task, g_log_d2_layers = log2(1536² × 24) ≈ 25.8 grows with the parameter count, which largely sets the memory.

Blind spot: a flag records that a string appears in the code, not what it does. import torch.utils.checkpoint is in this code but never called. Code that wraps the same work in a new API, or a workload family with no features written for it, looks like noise to the trees. That is why they reach 71.9% within ±20% on test GPU families and 9.8% on unseen ones.

A literal reading, found while building this page: npy_itemsize is 8 here because the dtype table has no int32 entry and defaults to 8 bytes.

The same prompt, read once, scored against every option

        
The decision model starts from the same LLM and the same prompt, with its LM head removed. A pointer head compares the hidden state at the answer slot (the prompt's last token) with the hidden state at each option's own token in the Options lines. Every axis gets a probability for every option in one forward pass, and no text is generated.

The full prompt, as for the autoregressive model. What changes is the readout.

            
Output
Three calibrated distributions (memory, CPU, GPU-or-none) from one forward pass.

            
RL
The rl-pointer variant starts from this model. It is then trained on the cost simulator's reward (minus the run's regret), so it learns which mistakes cost the most: under-asking, or putting a GPU on a CPU task.

          

          

            
Why a pointer: the options are read from the prompt, not built into the head, so the same head can rank a different list of machines. On unseen families, the 4B decision model is the most accurate GPU arm (42.1% within ±20%, against 9.8% for the trees).

          

        

      

    


    

      

        

          
Stacked: the trees' answer goes into the prompt

          
A stacked arm adds one sentence to the user message, and the LLM is trained and evaluated with it. Training rows get the trees' out-of-fold prediction (5 folds by task), so the LLM learns how far to trust trees that have not seen the run.

          
Gradient-boosted trees fit on other tasks' measured runs (they read the input sizes, the API names and numbers in the code, and this task's earlier runs) estimate memory ‹cell› ‹p›, ‹cell› ‹p›; cpu ‹cell› ‹p›, ‹cell› ‹p›; gpu P(no GPU) ‹p›, else ‹cell› ‹p›, ‹cell› ‹p›. Their pick: memory ‹cell›, cpu ‹cell›, gpu ‹cell›.

          
This is the template from bench_all/prompting.py; the ‹slots› are filled from the trees' distribution.

        

        

          
Pooled: the two distributions are blended

          
A pooled arm needs no retraining. For each axis it multiplies the two calibrated distributions, p ∝ ptreesw · pLLM1−w, with w tuned on the validation split. Options both models think likely gain probability; an option either one rules out drops. The savings model below uses pool-rl-pointer, where w = 0.6.

3 · Which model to price

    
pool-rl-pointer: the best on test and unseen families together

    
On the combined bench (memory + CPU + GPU, rsa-big-2), each model's dollar cost is divided by the cost of the oracle's right-sized request. That includes the OOM retries and slowdowns its mistakes cause. A multiple of 1.00× is perfect. The models below are ranked by their worse split, since a customer has both kinds of workload. pool-rl-pointer is the only model that stays under 1.9× on both.

5 · Read this before quoting a number

    
Assumptions and limits

    
    
      
  • The overprovisioning multiples are assumptions, not measurements of any customer. The presets lean on public, vendor-published figures. Datadog's 2023 container report says over 65% of Kubernetes workloads use less than half the CPU and memory they request, which is a multiple of 2× or more. CAST AI's benchmark reports put average use at 10–13% of provisioned CPU and 20–23% of memory. That figure includes idle node capacity, which changing requests alone may not reclaim.
    • 
      
  • The bench's workloads are synthetic. 32,082 runs from generated task families, measured on demo.hosted. Real tasks will not match their mix of sizes, and for GPU pods the size mix sets most of the dollars.
    • 
      
  • Unseen families are where RightSize is weakest. On them it costs 1.88× right-sized overall. Its savings depend mostly on how much of a customer's work looks like the training set, so a new customer's first month sits nearer the 0% end of that slider. Training on their history moves it the other way.
    • 
      
  • The largest GPU runs are under-sampled. 1,569 of the largest runs were censored because the cluster rarely scheduled 4×L4 or 4×L40S nodes. Multi-GPU savings are the least certain.
    • 
      
  • A simple rule does better on unseen CPU and memory workloads. Sizing from history times a margin costs 1.37× there, against 1.57× for pool-rl-pointer. A production version would fall back to that rule when a workload looks new.
    • 
      
  • The cost model is the bench's own. Pods are priced at on-demand us-east-1 rates by their dominant share of a node (GPU pods at the instance price), with a penalty for each retry and each hour of slowdown. Spot pricing, bin-packing and commitments are not modeled.
